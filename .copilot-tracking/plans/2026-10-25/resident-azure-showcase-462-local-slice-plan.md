## Authority and bounds

Local implementation, local tests, a local SQL Server container owned by this task and one local commit. No push, PR, heavy full gate, Azure/Graph/M365/live SQL access, secret read/list/generation, job start, resource or provider creation or deployment. Cloud, G1 to G4 and the full gate stay open and are reported, not claimed.

## Decision: smallest secure local slice

Three layers with a one-way dependency (adapters depend on the domain, never the reverse):

1. Domain, `core/resident_showcase.py`, pure and dependency free: email normalisation; admission of view rows into an identity map (at most 25, fail closed); scrypt password verifier; HMAC session codec bound to a boot nonce; CSRF token; sliding-window login limiter; positive-allowlist `showcase_view`; `ShowcaseConfig` with finite expiry and fail-closed environment validation. It reuses only read-only public constants from `resident_preview` (`BANNER` text is not reused; showcase has its own banner; `HELP`, `UNAVAILABLE`, `STAGE_TEXT`). It does not call `resident_view`, `Grant`, `Store` or `safe_start`.
2. Adapters: `core/resident_showcase_sql.py` (the only SQL reader: one parameterised read of `[resident_showcase].[v_resident_case]`, no DDL, no write, no `MssqlStore`) and `api/resident_demo/app.py` (stdlib HTTP, cookies, CSRF, headers, limits, logging).
3. Composition: `api/resident_demo/__main__.py` (reads environment, builds reader, verifier, codec, map; refuses to start on any gap), `api/Dockerfile.resident-demo` (non-root 10001) and `infra/sql/resident-showcase.sql` with `infra/scripts/resident_showcase_sql.py` (dry-run by default; applying is a private job step that stays gated).

#444's loopback fixture harness (`safe_start`, `FORBIDDEN_ENV_PREFIXES`, Host check, `resident_preview` package) is not edited and not imported by the showcase.

## Decisions (what is built now)

1. Identity source. The database owns the boundary. Table `[resident_showcase].[allowed_case]` (case id, provenance reference, `valid_from`, `valid_to`, `revoked`) ships empty; owner-approved rows are inserted later by a gated step. View `[resident_showcase].[v_resident_case]` joins it to `dbo.cases` and exposes only: case id, normalised email, count of cases sharing that normalised email across all `cases`, provenance, grant window and revoked flag, and the display fields address, town, postcode, stage, closed, and measures (JSON array only). Staff notes, names, phones, safeguarding, finance, contractor and every other path are not selected.
2. Admission (domain, re-checked on every fetch). A row is admitted only if provenance is non-blank, the grant is not revoked and is current, the normalised email is on the synthetic domain list (`example.com` only), the email count is exactly 1, the address is a single `local@domain` without whitespace, and fewer than 26 rows were supplied. Any other row is excluded and counted by reason without its value. More than 25 rows, or an unreadable row shape, fails the whole map closed. An empty map means ready=false and no login.
3. Password. The app never holds the plaintext. It receives a scrypt verifier (`scrypt$N$r$p$salt$hash`) and a 32-byte session key from environment variables that the cloud platform fills from named vault references (`ZF_DEMO_PASSWORD_VERIFIER`, `ZF_DEMO_SESSION_KEY`). No key reference, no start. Tests use constants whose text says they are fake and are produced inside the test. No real password is generated here. Unknown email, wrong password, revoked and ambiguous all do the same work and give the same generic 401.
4. Sessions. `__Host-zfdemo` cookie (Secure, HttpOnly, SameSite=Strict, Path=/), 30-minute absolute expiry capped by the showcase expiry, HMAC-SHA256 over a per-process boot nonce, so a restart invalidates every session; logout revokes in process; no sliding renewal. The client never supplies a case id, header or cookie that chooses identity: the token carries an opaque handle that maps server-side to the case.
5. CSRF. `GET /` sets a signed `__Host-zfdemo-csrf` cookie; login and logout need the matching `X-CSRF-Token` header, a same-origin `Origin` (or `Sec-Fetch-Site: same-origin`) and JSON content type.
6. Abuse. 5 failures per source and 60 global per 10 minutes then 429 with `Retry-After`; body at most 2 KiB; 8 concurrent requests (503 above); 10 second socket timeout; a 30 second per-case view cache so repeated sign-ins cannot generate unbounded SQL. Logs hold event class and a salted-hash prefix only. Behind the platform proxy the per-source key can be spoofed only if `ZF_DEMO_TRUST_PROXY=1`; the global window still protects the 10 DTU database.
7. Deployment config fails closed: `ZF_DEMO_EXPIRES_AT` required, UTC, in the future and not after `2026-10-26T12:00:00Z`; allowed host names required; SQL server and database required with auth `msi` (or `password` only when the server is loopback, for the local test); refuses any `ZF_STORE`, `ZF_ENTRA*`, `ZF_AI*`, `AZURE_OPENAI*` or `ZF_DATA` setting so employee, AI and staff-store configuration can never be mixed in. After expiry every route except `/healthz` returns 503 and `/healthz` reports expired.
8. Display. Every view is built field by field from the row: home (address, town, postcode), measures (at most 20, bounded text), progress and next step (from `STAGE_TEXT`, unknown stage gives the existing honest fallback), closed note, fixed help and fixed unavailable list. No appointments (no source data in the view, so none are invented). Banner: "Synthetic demo - not a real resident service. This sign-in uses a shared demo password and does not prove who you are."
9. Web. Fluent 2 token CSS and plain-language copy follow the merged resident preview: skip link, one h1, labelled email and password fields (`autocomplete` `username` and `current-password`, `spellcheck` off, paste allowed, no autofocus), inline error with `role="alert"` and focus moved to it, live region for loading, visible focus, reduced motion, no `transition: all`, native buttons, ellipsis characters, `translate="no"` on the email. Current guideline source fetched this step. No claim of WCAG conformance or human accessibility testing.
10. Not built, by scope: Bicep module, Container App, identity, role assignments, vault writes, the retrieval client, the owner allowlist rows, the credential. Each remains a gated cloud step.

## Test strategy (focused only; no heavy gate)

* Core unit tests with constructed synthetic rows: admission (every exclusion reason, 25 limit, 26 fails closed), verifier, session (tamper, expiry, boot nonce change, logout), CSRF, limiter, view allowlist with canary fields, config failures.
* API tests over a real loopback socket with an in-memory fake reader: login success, wrong password, unknown, forged cookie, expired, cross-case, replay after logout, CSRF failure, Host spoof, oversize body, rate limit, security headers, no case id in URL, no error text leakage, 503 after expiry.
* Local SQL Server (own container, loopback port, `sa` password generated for the container only and held in memory/process environment of the test run, not stored): real `cases` DDL from `mssqlstore.TABLES`, apply the SQL file, a `WITHOUT LOGIN` stand-in user proves SELECT on the view only, denial on `dbo.cases`, any write, DDL and prohibited paths; an empty allowlist yields no rows; duplicate email, non-example domain, revoked and expired rows are handled.
* Browser check (Playwright, chromium, loopback helper listener only) with real sign-in, forged 401, cross-case deny and logout.
* Docker: build `Dockerfile.resident-demo`, run non-root, check refusal without configuration, and `/healthz`, then remove only the exact containers and images this task created.
* ruff, ruff format check and mypy for core and api; existing resident-preview, dependency rule and role endpoint inventory tests to show #444 and staff are untouched.

## Critique amendments (2026-10-25, after the single independent critique, before implementation)

Critique execution: once, verdict REVISE, five findings (PC-001 to PC-005), see `.copilot-tracking/reviews/plans/2026-10-25/resident-azure-showcase-462-local-slice-plan-critique.md`. All five are compatible with the owner's decisions and are applied directly. The text above stays as written; these amendments govern where they differ.

* PC-001 (SQL ownership): schema `resident_showcase` is created `AUTHORIZATION dbo`, and the table and view are owned by `dbo`, so the view reads `dbo.cases` through an unbroken ownership chain. The showcase principal gets `GRANT SELECT ON OBJECT::[resident_showcase].[v_resident_case]` only, no database role membership (db_datareader, db_datawriter and db_ddladmin are forbidden), `DENY SELECT, INSERT, UPDATE, DELETE, ALTER ON OBJECT::dbo.cases` and `DENY INSERT, UPDATE, DELETE, ALTER, EXECUTE, CONTROL` on the schema `resident_showcase` (the view stays readable because chained access skips checks on the referenced base table). The local SQL test acts as the principal (`EXECUTE AS USER`) and asserts: view SELECT works; direct SELECT, INSERT, UPDATE, DELETE on `dbo.cases` and on the allowlist table fail; CREATE TABLE and DDL fail; the principal has no role membership (query of `sys.database_role_members`) and no effective permission outside the single view (query of `sys.fn_my_permissions`).
* PC-002 (email equivalence): one grammar and one canonical form for both sides. Canonical form is trim then lower-case of an ASCII address matching `^[a-z0-9._+-]{1,64}@example\.com$`. The Python side does not apply NFKC (that removes any normalisation gap): a non-ASCII or non-matching address is excluded as `email_form`, and a login input that does not match is denied generically. The view computes the canonical email as `LOWER(LTRIM(RTRIM(JSON_VALUE(body, '$.resident.email')))) COLLATE Latin1_General_100_BIN2` only when `ISJSON(body) = 1`, otherwise NULL, and the duplicate count is taken over every row of `dbo.cases` (not only the allowlisted ones) using that same expression, so a collision with a non-allowlisted case counts. Local SQL tests: case variants, Unicode lookalikes, missing, malformed-JSON, non-string and array values, and a collision with a non-allowlisted case.
* PC-003 (cookies): the Secure `__Host-` cookie policy is the same in deployment and local tests. The local browser origin is `http://127.0.0.1:<port>`, which Chromium treats as potentially trustworthy and so stores Secure cookies for. The browser check asserts the browser stored both cookies and that the next request returned them (an authenticated view succeeds only if so). If that fails, the fallback is a local self-signed TLS origin, never a weaker cookie, and the result is recorded in the review.
* PC-004 (proxy): `ZF_DEMO_TRUST_PROXY` is removed. The limiter key is always the connection peer address. Behind the platform ingress that is the ingress hop, so the per-source window effectively merges into one shared window with the global one; this is stated and accepted for a demo, and forwarded headers never influence it. A test proves spoofed `X-Forwarded-For` does not change the key.
* PC-005 (cache and revocation): the 30 second view cache is removed. The identity map (email to case handle) is built at start to enforce the 25 bound and to avoid a lookup on unknown emails, but authorisation is never taken from it: login and every protected request re-read the case row through the view (`fetch_by_case`) and run the full admission check, so revoked, expired, duplicate-after-start or removed rows are denied on the next request (maximum staleness zero). Adding allowlist rows after start needs a restart (stated). Load protection is the 8-request concurrency cap, body limit, session requirement and login limiter. Tests revoke or expire a row mid-session and prove the next request is denied.
