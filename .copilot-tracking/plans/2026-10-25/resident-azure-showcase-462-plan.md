## Decision

Build a separate cloud/demo composition, not a relaxation of #444. Smallest secure delivery:

* `core/resident_demo.py`: pure domain. Identity map builder, credential verifier, session token, login limiter, view adapter. No I/O except through injected readers.
* `api/resident_demo/` (`__main__`, `app.py`, `web/`): stdlib HTTP server like #444's, separate entry point `python -m zava_forward.api.resident_demo`, separate image `src/api/Dockerfile.resident-demo` (non-root 10001), imports no staff routes and no Entra code. Reuses #444's `resident_view` and `Grant` unchanged. #444's `safe_start`, loopback guard and forbidden-environment rules are not edited.
* Read-only reader: one parameterised SELECT over `cases` for the mapped cases, through a connection that never calls `MssqlStore` schema/migration/audit code.
* Infra: one new Container App `ca-cutover-test-resident-demo` in the existing `cae-cutover-test-demo`, new user-assigned identity `id-cutover-test-resident-demo`, KV references, tagged `ama-issue=462` and expiry. Delivered by a bounded incremental ARM/Bicep deployment limited to `ama` with what-if first.

## Decisions on the owner's constraints

1. Mapping: server-owned. The identity map is built at start-up and on a bounded refresh from the verified source of fake emails (research Finding 3). A row is admitted only if (i) the case carries the synthetic provenance marker, (ii) the normalised (NFKC, trimmed, lower-cased) email domain is on a reserved/owner-approved synthetic list, (iii) the email is unique across all cases, (iv) the case is in the explicit owner-approved showcase set (a count-bounded allowlist, default at most 25 cases, selected by the owner or by a documented deterministic rule). Any duplicate, missing or ambiguous email is excluded and reported by count only; if the verified source is absent the app refuses to start login (fails closed) and reports gap G2. Emails are never invented, and no database write adds them.
2. Credential: generated by an operator-run script using `secrets.choice` over at least 24 characters from a 70+ symbol set (at least 140 bits), in memory only. Two vault secrets are written via the existing SecureString ARM mechanism (`credential_arm.py` pattern): `resident-demo-password` (plaintext, readable only by the owner path, never referenced by the app) and `resident-demo-password-verifier` (scrypt hash string, N=2^15, r=8, p=1, 16-byte salt, read by the app through a Key Vault reference). A third secret `resident-demo-session-key` (32 random bytes) signs session tokens. All three carry an expiry no later than 2026-10-26T12:00Z plus a margin set by the owner and are removed at stop. The value is never written to a file, argument, environment variable, log, tracking, session SQL, memory or PR; the script prints only secret names, versions and lengths. Rotation is replacing the version.
3. Owner retrieval: the owner reads `resident-demo-password` from the private path by one of the two documented routes: (a) a dedicated, time-bound, scoped Key Vault Secrets User assignment on that one secret plus the existing private-network route, (b) a private job run by the coordinator that prints nothing but is delivered via the owner's own secure channel. Which route is possible is gap G4; the plan documents the steps and values-free checks, never the value.
4. Session: HMAC-SHA256 signed token `v1.<case-handle>.<issued>.<expiry>.<nonce>.<mac>`, `__Host-` cookie, `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, 30 minute absolute expiry, no sliding renewal; server clears on logout and keeps a bounded in-memory revocation set by nonce for the single replica (max 1). Key rotation invalidates all sessions. The case handle is an opaque HMAC of the case id with the session key, resolved server-side through the map; the client never supplies a case id, header or cookie authority, and the case id never appears in any URL.
5. CSRF: login and logout are POST only with a double-submit token tied to a pre-login signed cookie plus an `Origin`/`Sec-Fetch-Site` same-origin check; no state-changing GET.
6. Abuse control: constant-time work for unknown and known emails (dummy verification), identical generic message and status for wrong password, unknown, ambiguous and locked, per-source and global sliding windows (default 5 failures per 10 minutes per source, 60 global failures per 10 minutes, then 429 with `Retry-After`), bounded body size, request timeouts, 8 concurrent request cap protecting the 10 DTU database, and a short read cache (30 seconds) so a loop of sign-ins cannot generate unbounded SQL. Logs record event class and a salted hash prefix of the source only, never email or password. Single replica makes in-memory counters authoritative; a restart resets them, which is accepted and stated.
7. Display: positive allowlist only, field by field from #444's catalogue (`home`, `measures`, `progress`, `next_step`, `appointments`, `help`), and no raw record, free text, notes, safeguarding, finance, staff identity, contractor, chat, memory or error text. Appointments keep honest offered-versus-confirmed wording. Every page carries the banner "Synthetic demo - not a real resident service. Sign-in here is a shared demo password and does not prove who you are". Errors are fixed strings. No actions, consent, uploads, downloads, messages or AI.
8. Shared password: documented as cross-identity by design; the page, README and PR say so. This is demo authentication; no production identity, enrolment or security acceptance is claimed. The static `Cache-Control: no-store`, CSP (`default-src 'none'` plus self script/style), `Referrer-Policy: no-referrer`, `X-Content-Type-Options`, `frame-ancestors 'none'` and HSTS are set.
9. Database access: preferred, a SQL principal created for the new identity with SELECT only on a single database-owned view that projects the allowlisted JSON paths and the mapping columns; the base table is denied. The view is a schema object, not business data, but it is still a database change; it needs explicit owner/coordinator approval (G3). Fallback if refused: SELECT on `cases` (id and body) for one principal, with all minimisation done in code; this is a worse boundary and is recorded as a residual risk, not silently used.
10. Preservation: no change to `ca-cutover-test-api`, `ca-cutover-test-demo-api`, employee Entra configuration, SQL S0, business records, the Front Door or any existing role. No paid AI, no new environment, no private endpoint.

## Cost and stop plan

Before step 6: record resources, cumulative accrued incremental spend, remaining cap and the finite resource list above with Azure retail price evidence. Unknown headroom blocks spending. Stop conditions: projected incremental plus accrued exceeds remaining cap; any resource outside the finite list is needed; the authority window ends 2026-10-26T12:00Z (the cap does not reset then); health or abuse indicators; any secret exposure (rotate and stop). Stop action: scale to zero then delete only the Container App, identity, role assignments, SQL principal/view and three secrets this task created (and purge soft-deleted secrets it created), each by exact name and tag verified before deletion. Never delete the resource group or any existing resource.

## Acceptance evidence and review focus

Actual login with a mapped fake email returns that case only; wrong password, unknown, ambiguous, forged, expired, replayed after logout, key-rotated, cross-case, staff routes, canary fields, CSRF failure, rate limit and Host spoofing all deny with generic outcomes; unchanged employee login tests. The review must run the real login and forged 401 and cross-case deny, not accept root 200.

## Residual limits

No real resident identity assurance; human accessibility testing and professional approval remain open; in-memory limiter resets on restart; a shared password means any holder can sign in as any listed demo resident; rubric and PR gates rely on #444 resolution.

## Critique amendments (2026-10-25, after the single independent critique, still before implementation)

Verdict REVISE; execution once; see `.copilot-tracking/reviews/plans/2026-10-25/resident-azure-showcase-462-plan-critique.md`. The text above is original and unchanged; these amendments supersede it where they differ.

* Decision 9 amended: the database-owned allowlist view is mandatory. The base-table `cases` fallback is removed; if the view cannot be approved or created, deployment is blocked. Tests prove the resident principal cannot SELECT `cases` or prohibited paths and cannot write or run DDL.
* Decision 4 amended: every session token MAC covers a random per-process boot nonce, so restart or scale to zero invalidates all sessions; logout also revokes in the live process. A restart-after-logout negative test is required.
* Decision 2 amended: secret expiry and scheduled cleanup are at or before 2026-10-26T12:00Z with no margin; extension needs a new explicit owner authorisation first.
* Cost and stop plan amended: gap G3 includes create and delete/revoke authority for every RBAC assignment, SQL principal and view, with deterministic names and post-delete readback queries instead of tags for SQL objects.
