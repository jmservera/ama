## Plan (authored 2026-11-10T04:50Z, before any source write)

Objective: deliver one NEW default-off, manual-review-only sensor review draft interface, so an existing approved-rule `ReviewTaskCandidate` can be persisted as an unapproved `PROPOSED` draft, read back through a need-to-know projection and shown in the existing employee sensor panel. It is not an existing generic task API, creates no work, ownership, handoff, model dispatch, ranking, hold, hazard or consent change, and activates no rule. Refs #111; no closing keyword, no criterion ticked. This phase stops here; Implement and Review resume later in order.

Disposition: INDEPENDENT of #135 and #1300 for the module and its tests. Three small shared edges (`projection.py`, `server.py`, `ops.js`) are named below, none a #135-owned hook. No edit to `store.py`, `sqlstore.py`, import projection, exception register, feeds or `tools/`.

## Exact new interface

| Layer | Exact name |

| Module (new) | `src/core/src/zava_forward/core/sensor_review_draft.py` |
| Storage | case-local list `case["sensor_review_drafts"]` (JSON `live.json`, SQLite/MSSQL `cases.body`), no new table, no new top-level `data` key |
| Write (Python, production) | `draft_from_retained(store, user, case_id, window, as_of, policy=None, *, env=None, at=None)` only; the policy is resolved server-side and a caller never supplies a signal or approval |

| Read (served) | `GET /api/cases/{id}/sensor-drafts` |
| Access projection | `read_drafts` view allowlist plus a `projection.redact_staff_detail` pop of `sensor_review_drafts` so generic staff case detail never carries it |

No `/api/me` change. Acceptance is reconciled: with the flag off, existing responses are byte-unchanged and the only new traffic is that one GET from the sensor panel |

Constants: `CASE_KEY="sensor_review_drafts"`, `SCHEMA="sensor-review-draft-v1"`, `STATE="PROPOSED_UNAPPROVED"`, `DRAFT_ROLES=("Quality Inspector","Retrofit Programme Manager")` (a test asserts equality with `assistants.REGISTRY["quality-evidence"]["roles"]` and `ops.js SENSOR_ROLES`), `MAX_DRAFTS=20`.

Draft record (all fields immutable once written):

* `schema`, `state="PROPOSED_UNAPPROVED"`, `manual_review_only=True`, `approval_verified=False`, `activation=None`.
* `task_key`, `task_type`, `queue`, `home_id`, `rule_id`, `approval_reference` (as supplied, labelled unverified), `policy_version`, `analysis_version`, `input_digest`, `summary`, and the five no-effect flags, copied from `as_dict(candidate)` exactly.
* `lineage`: `window_start`, `window_end`, `as_of`, `threshold_label`, `sufficiency`, `outcome`, `expected`, `valid`, `coverage`, `longest_high_hours`, `high_nights` from the `Signal`. No raw readings, no resident or contact data.
* `created_by` (user name and role), `created_at` (ISO, injectable `at` for tests), `label` fixed plain-language text ("Proposed for a person to review. Not an approved task. Exercise rule, not a sourced standard.").
* `draft_digest`: SHA256 of the canonical JSON of every field above except itself. Read re-computes it; a mismatch yields `state="INTEGRITY_MISMATCH"` with only `task_key`, never the body.

## Behaviour

1. Gate order in every public function: `enabled(env)` (else `PermissionError`, served 403; read returns `{"state":"disabled"}`) then current staff revalidation mirroring `assistants.authorize` (staff row present, not revoked or disabled, role unchanged, role in `DRAFT_ROLES`, well-formed scope, `case_ids` and `areas` contain the case; else `PermissionError`) then case exists (`KeyError`, served 404, only after scope passes so existence is not leaked) then data reads. Denied callers cause no retained-store read and no write. Reads then recheck current consent as `assistants._sensors_granted` does and fail closed: unknown or withdrawn consent returns `{"state":"consent-withheld"}` with no summary, lineage or digest.
2. `_record_draft_synthetic` calls the existing `review_task_candidate(signal, policy)`. `None` returns `{"created":False,"refusal":code}` where code is `SIGNAL_<SUFFICIENCY>` (insufficient, stale, declined), `NO_REVIEW_SIGNAL`, or `NO_APPROVED_RULE` (checked in that order), plus `signal.reasons`. Refusals write nothing and append no audit. Also refuses when `signal.home_id != case_id` and, with code `FUTURE_READINGS`, when the window ends after the trusted `as_of` (guard lives in this module; existing analysis files unchanged).
3. Under `store.lock`: `c = store._case(case_id)`; find existing draft with same `task_key`; if found return `{"created":False,"existing":True,"draft":view}` and do NOT call `save()` or `audit()` (idempotent reopen, original `created_at/by/lineage` untouched even though the replay's `as_of` differs). A different `task_key` (changed digest, window or policy) appends a new draft and never edits the old one. At `MAX_DRAFTS` a new key returns refusal `DRAFT_LIMIT_REACHED` (no eviction). Append, `store.save()`, then `store.audit(...)` (save first so a failed save leaves no audit). Backend recovery: on any exception before save returns, restore the pre-call list value and re-raise. JSON: `save` is a whole-file rewrite, not atomic with audit; a failure after save but before audit loses only the audit line, documented as a residual, not claimed atomic. SqlStore/MssqlStore: `ConflictError`, `GateError`, `PermissionError` roll back and `_discard()`; for other failures call the store discard path and drop pending audit so `_finish` cannot commit it; `CommittedReloadError` after commit is reported as outcome unknown and the retry is safe because same `task_key` is idempotent. Tests cover failure before save, at save, and after commit.
4. `draft_from_retained` runs gate 1 (including staff revalidation), builds `SensorConsumer(store)` (a JSON store or `ConsumerError` returns refusal `RETAINED_READINGS_UNAVAILABLE`, no write), calls existing `analyse_retained` then `record_draft`. `policy=None` means `AnalysisPolicy()` (no approval), so the served path refuses (precedence: unavailable, stale, insufficient, no signal, then `NO_APPROVED_RULE`; fixture decides which) until a real, separately human-approved policy source exists. That source is explicitly out of scope and not designed.
5. `read_drafts` returns only allowlisted fields (the record above minus `draft_digest`, plus `case_id`, `state:"ok"`), newest first, up to `MAX_DRAFTS`. Unknown keys are dropped.
6. Constructed approvals exist only in tests via the private seam, with `approver_role="SYNTHETIC TEST ONLY"` style labels and `approval_reference` beginning `SYNTHETIC-TEST-`; nothing in product code builds a `RuleApproval`.
