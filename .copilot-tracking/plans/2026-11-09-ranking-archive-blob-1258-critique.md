# Issue 1258 Blob JSON persistence plan critique (2026-11-09)

Refs #1258. One critique of the final-candidate plan (`.copilot-tracking/plans/2026-11-09-ranking-archive-blob-1258-plan.md`) by an independent read-only subagent (rubber-duck). Executed once. Verdict: Revise, seven Significant findings, no Blocking. The plan author's dispositions follow; none needs an owner decision and none relaxes the owner's Blob decision or any contract.

| ID | Severity | Finding | Disposition |
| --- | --- | --- | --- |
| PC-001 | Significant | Retry after an uncertain write is idempotent only for the identical snapshot; Store recomputes the snapshot and date | Accepted. The claim is limited to the identical snapshot. A changed input gives a different record name and is a new record, never an overwrite. A test covers a changed-input retry. The audit entry carries the hash prefix so an operator can match the unconfirmed attempt. |
| PC-002 | Significant | Selecting Blob opens a separate archive; folder history is not migrated | Accepted as an explicit scope limit. Migration of existing folder records is not authorised (owner decision does not approve migrating existing JSON). Blob starts a fresh archive; any folder records remain in place, unread, and are named as an unresolved history dependency for the coordinator and owner. No claim of continuity is made. |
| PC-003 | Significant | Conflict classification ambiguous | Accepted. 201 or 200: created. 412: exists. 409 with `x-ms-error-code` equal to `BlobAlreadyExists` (case-insensitive header name) or absent: exists, validated by a read. 409 with any other code: definite refusal. After exists, a 404 on the read or an unreadable body is a definite refusal, not success. Each is tested, including mixed-case headers. |
| PC-004 | Significant | Token acquisition failure is a different boundary from a PUT failure | Accepted. Headers are built before dispatch; a failure there is a sanitised definite refusal and nothing was sent. Only a failure after dispatch (transport error, 408, 5xx) is uncertain. Tested through the adapter, Store, API and runner. |
| PC-005 | Significant | A subclass would inherit `put` and `delete` | Accepted. `BlobRankingArchive` uses composition over an `AzureBlobDocumentStore` instance (for its URL, SAS, token and transport only) and exposes only `create`, `read` and `names`. A test asserts the class has no `put`, `delete` or `list_ids`. |
| PC-006 | Significant | Leakage through the runner `path` output and chained exceptions | Accepted. The `path` value for Blob is the opaque record name only. Transport exceptions are caught and re-raised without chaining (`from None`) with fixed text. Tests use sentinel SAS, token and URL values and check results, CLI output, exception text and captured logs. |
| PC-007 | Significant | Metadata wire details unspecified | Accepted. `record_sha256` is the SHA-256 of the exact stored bytes (the UTF-8 canonical record). Metadata response headers are normalised to lower case. Tests alter the bytes, drop and alter metadata, and use mixed-case headers on both retry and verify. |

All dispositions are applied to the plan by the "Critique dispositions" section there. The critique is not repeated for this task; later findings from Review become follow-up work.
