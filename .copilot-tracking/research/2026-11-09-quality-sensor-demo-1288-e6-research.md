## Findings in scope (exactly these two)

* F1 High: `Assistants.begin_call` reserves `active_until = now + lease` and nothing re-checks it. `Lane.request` can stall after admission and before mint or transport; on resume it sends regardless of the lease, the operator expiry or another caller having reclaimed the slot. Two independent processes with their own local semaphores can then both transmit under `active_calls=1`. Totals (`used_calls`, uncertain token liability) stay finite; the defect is the physical capacity and dispatch window.
* F2 Medium: `test_role_endpoint_inventory` fails (22 tests, 1 failure) because the three simulation routes `/api/assistants/simulation/quality` (GET), `/observe` and `/request` (POST) are not in `GET_ENDPOINTS`/`POST_ENDPOINTS`. This is this workstream's defect, not an unrelated baseline.

## Evidence

* `ai.Ai._request` order today: seal verify, data hold, size, meter `reserve`, `_token()`, `consumption.dispatch_check(rid)` (financial contract only), then `urllib.request.urlopen(req, timeout)`. The timeout is per socket operation, not total. Nothing inspects the assistant ticket at the moment bytes are written.
* `assistants.DispatchGate` (ordinary tasks) states the same limit in its docstring: a process suspended between the check and a real send could still transmit, so a real `Ai` is never given captured readings. The ordinary path claims and sends in the same call, so it has no admission-to-send stall window of the kind `Lane.request` has.
* `_reserve` counts `assistant_attempts.active_until > now` against `active_calls` inside one serialized transaction (BEGIN IMMEDIATE on SQLite, SERIALIZABLE on SQL Server). That count is the only cross-process physical-capacity signal; it is shared by every process using the same store.
* `urllib` `HTTPSHandler.do_open` builds its connection from a class; `http.client.HTTPConnection.send` calls `connect()` and then `sendall`. A connection subclass therefore owns the exact point before the first request byte is written, after DNS, TCP and TLS handshake.
* Candidate mypy under the pinned profile (mypy 2.4.0, `strict = true`): core 61 errors in `sensor_consumer.py` and `sensor_view.py`; api 569 errors in `tests/test_quality_sensors.py` and `tests/test_quality_sensors_c7.py`. E5 used a "changed files only" proxy; the owner rejects it. These are pre-E5 candidate typing debts that must be reconciled with green main, not waived.

## Design

Fence at the transport, in the same shared store the admission uses.

1. `Assistants.fence_send(attempt, capability)` (one transaction): refuse unless the attempt row is still `reserved` or `sending` with `active_until > now`, `disabled(db, capability)` is clean (this includes suspension, release admission and `ZF_ASSIST_EXPIRES`), then restamp `active_until = now + timeout + HOLD_GRACE` and `outcome='sending'`. The restamp holds the shared physical slot for the whole bounded send window, so another process cannot reserve it while this one may transmit. A caller whose lease lapsed and whose slot was reclaimed is refused, because its row is no longer unexpired.
2. `ai.Ai` gets a transport-owned send fence: `ai_consumption.SEND_FENCE` context variable and a connection subclass whose `send()` calls the fence after connect and immediately before the first byte, aborts with `DispatchWithdrawn` if the fence refuses or took longer than a small margin (monotonic), and a total-deadline timer that closes the socket at `timeout`. Total send-and-read time is therefore bounded by the window the fence restamped.
3. `Lane.request` sets the fence from its `CallTicket` and refuses up front with the manual route when the Ai transport cannot honour a fence (`send_fence_supported` false) or the store is not the shared SQL authority store. No fence, no real-provider send.
4. Accounting stays conservative: a refused late caller ends with `suspended-before-dispatch`; its reservation and `used_calls` remain as finite liability (no refund without proof), its durable slot is released at once, and the physical slot is released once.

Exact supported deployment boundary: every process that may dispatch must admit through the same assistant authority store (one SQLite file on one host, or one SQL Server database) using `begin_call`. Separate stores, separate databases or environments hold separate caps; that is out of scope and must not be configured for one provider. Residual (named, not minimised): an OS-level freeze of the sending thread between the last in-process check and the kernel write cannot be excluded in user space, and a freeze that outlasts the restamped window followed by a send is not prevented by this mechanism. A provider-side or proxy-side fence token would be the only complete answer and needs an explicit owner decision; it is not inferred from this correction grant. Therefore the fence is stated as closing the admitted-then-stalled caller (the stalled caller is refused atomically in the shared store, with zero socket for a stall before the request starts and zero request bytes for a stall before the send) while the physical-cap guarantee against a freeze inside the send path remains a documented limit. Real-provider dispatch stays unavailable unless the transport declares the fence and the deployment boundary holds; no provider is admitted or activated by this cycle. A local semaphore, lease renewal or another last check alone is not claimed to prove this, and a same-service test is not claimed to prove cross-process behaviour; the two-process tests below do.
