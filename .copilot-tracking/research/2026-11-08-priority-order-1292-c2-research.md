## Verification of findings

* F1 (High, confirmed). `_sync` calls `_repair_zero_ordinals` (a `COUNT` probe, outside any transaction), then `_db_seq()`, then separate `SELECT ... FROM recommendations WHERE seq > ?`. An old writer commits `created_ord=0` plus a `meta.seq` bump atomically. A commit after the probe and before the sequence read makes the reader load the zero row (sorting first) and publish its sequence, after which the equal-sequence early return serves the wrong newest recommendation indefinitely. The existing old-writer tests insert before the synchronisation, never between statements. Also confirmed: `save` repairs zero rows inside SQL but its `cur == self._seq` shortcut does not refresh a cached `_rec_ord`.
* F2 (High, confirmed). `_queue_candidates` opens `BEGIN IMMEDIATE`, then runs `_sync` inside it. A repair there changes SQL and `meta.seq` uncommitted, the cache publishes that sequence and the repaired ordinals, and a later failure in `_refresh_queue_membership` rolls SQL back without restoring the cache. Another old write can reuse the rolled-back sequence number, and the next read takes the equal-sequence early return. Nothing in the queue path needs the cache loaded inside the transaction: `_refresh_queue_membership` reads only SQL; only `self.version` in the key and the returned case objects use the cache.
* F3 (High, confirmed). The backfill sort key leads with the body `created` second (`datetime.now()`, naive, not monotonic). With a complete audit, a backward clock step (A at 10:00:00, later B at 09:59:59) puts B before A; the batch reports no ambiguity and its `order` text states the opposite of the code.
* F4 (High, confirmed). When audit is absent or broken, same-second rows get permanent ordinals from `(created, seq, id)`; editing the older A raises its `seq`, so B is ordered before A and `latest_priority` returns A with an ordinary `200`. Ambiguity is only written to `meta`; `Store.latest_priority`, `_rec_view` and `server.py` (line 602) never consult it. This is the original defect, now with a record nobody reads.
* F5 (Medium, confirmed). The audit table has no link to the transaction that inserted a recommendation: `audit.seq` is its own counter and `recommendations.seq` is the global write counter. `save` rolls back on non-conflict exceptions without discarding the unsaved recommendation (`except BaseException` branch), and `_finish` (outermost lock exit) flushes pending audit entries in a separate transaction. So an `ai_run_end priority_recommendation <id>` event can be committed while its recommendation is still cached and unsaved; a later unrelated `save` (for example `log_call`) inserts it after a newer recommendation. The event is then evidence of intent, not of commit.
* F6 (Medium, confirmed). `verify_entries` is called without digests, and `audit_head` lives in the same database, so a self-consistent rechain passes. `Store.verify_ledger` uses `ledger.read_digests(self.digest_dir)` and `ledger.verify_years` with year digests. In `_initialize`, `digest_dir` is assigned after `_migrate_recommendations`, so the digests cannot even be located at migration time.
* F7 (Medium, confirmed, conditional). The earlier candidate (C0, `16375e3ca`) backfilled all rows with `(created, seq, id)`, writing only `meta.rec_order_legacy`. C1/C2 only analyse `created_ord = 0`. A database first opened by C0 has positive ordinals, no zero rows and therefore no audit consultation and no batch record. No evidence exists that any such database is a live one.
* F8 (Medium, confirmed). Every non-empty repair reads, hashes and verifies the whole audit table and re-parses and rewrites the whole `rec_order_backfills` JSON, all inside the write section (SQLite 5 s busy timeout, SQL Server 15 s application lock). Cost is O(batches x audit) plus quadratic cumulative history.
* F9 (Medium, confirmed). `require_task_owned_loopback` accepts any loopback host with password auth. A shared local SQL instance or a loopback tunnel passes, and both fixtures then create and drop databases on it.

## Design conclusions

* Reader protocol (F1, F2). Optimistic, dialect-neutral, no probe: read `seq` (s1); fetch changed cases and recommendations; read `seq` again (s2). If s2 differs, retry (bounded). Cached state is built only from a fetch that no commit interleaved with, because every writer, old or new, bumps `meta.seq` in the same atomic commit as its rows. If the fetched recommendations include `created_ord = 0`, repair in its own `BEGIN IMMEDIATE` section and retry. A zero ordinal is therefore never cached, so `_rec_ord` and the equal-sequence shortcut cannot hold one, and the stale `_rec_ord` after a `save` repair cannot occur. Exhausting retries raises (fail closed).
* Queue path (F2). Synchronise before the transaction, then inside `BEGIN IMMEDIATE` compare `meta.seq` with the cache; if it moved, roll back (nothing is written yet) and retry. No cache state is ever published from uncommitted SQL, so the `writing` flag is removed.
* Ordering evidence (F3, F5, F6). Provable order is the transaction-aligned creation event only when (a) the chain verifies from genesis and against `audit_head`, (b) every available independent digest (`read_digests`) and year digest (`verify_years`) still matches, and (c) the event does not contradict the one independent commit-order signal in the schema: for an unedited row (`rowversion = 1`) `seq` is its insertion sequence, which must not disagree with audit order. Edited rows have no independent commit signal; their audit position is accepted as audit-supported and recorded as such, not as proof. An audit position outranks body `created` (clock reversal is proven by audit, never by timestamp). Rows without trusted evidence keep the heuristic position and are flagged unresolved when their same-second group (same employee, non-`ai_task`) cannot be proven, or when audited rows show a timestamp inversion.
* Prevention (F5). A failed non-conflict `save` now drops its unsaved recommendations and their pending creation events so neither is persisted or flushed later.
* Unresolved is visible (F4). Heuristic rows that cannot be proven are listed in `meta.rec_order_unresolved` (ids, no cap, merged not rewritten). `latest_priority` returns the record with `order_confirmed=false`, an explanatory note and `actionable=false` when the newest record is unresolved, so a guess is never shown as confirmed latest and nothing is acted on until the named data owner decides. Resolution is a data-owner action; this change provides no resolution authority and invents no order.
* C0-migrated databases (F7). At migration, `rec_order_legacy` present without any C1 or C2 batch evidence identifies a C0 heuristic backfill (ordinals `1..rows`). Ordinals are not rewritten. Rows of same-employee same-second groups whose current order contradicts or lacks proven audit order are added to the unresolved list and one `source=c0-review` batch is recorded.
* Bounded work (F8). The verified audit evidence (positions, count, head) is computed outside the writer section and cached per process; under the lock only entries appended since are chain-verified incrementally from the cached head. Failure is cached per `audit_head`. Batch records are one meta key per batch (`rec_order_batch:<n>`, counter `rec_order_batches`) so history is never re-parsed or rewritten; the previous `rec_order_backfills` list, when present, is left untouched.
* Test fixture admission (F9). Loopback and password remain necessary and are checked first. Additionally the fixture requires a task manifest written by the admitted setup (`ZF_SQL_TASK_MANIFEST`): regular file owned by the current user, not group or world writable, recent, naming loopback host and port equal to the environment, and the SHA-256 of the one-time password equal to the environment password. A shared loopback listener or tunnel has no matching manifest, and a manifest cannot be satisfied without the task-generated password. All checks run before any connection or DDL. This is admission evidence, not proof a container exists; no SQL run happens in this correction.
