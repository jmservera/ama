## Question

Gate g2182 (`~/g2182/o/0052-project-api.log`) timed out at 1800 s with no CPU contention. The project-api shard hung in `ChatApiTests.test_agenda_confirmation_isolation_cancellation_and_authentication` during cleanup `DemoTestCase.stop`, at `self.server.shutdown()` (`socketserver.py:255`, `__is_shut_down.wait()`). The test passes alone in 0.8 s.

## Evidence

* The log traceback shows only the main thread waiting for `serve_forever` to signal exit. `BaseServer.shutdown` sets a flag that `serve_forever` checks once per `select` wake-up (0.5 s), so a wait that never ends means the serving thread is not back at its loop test.
* Every other path out of `serve_forever` sets the event in a `finally`. The remaining stall point is `accept()` inside `_handle_request_noblock`: the listening socket of `_Server` is blocking, and accept(2) documents that a readiness event can outlive its connection (removed by an asynchronous network error), after which accept blocks for the next connection. With no further client, the serving thread sleeps forever and `shutdown()` deadlocks.
* The test client opens and closes many short connections, including requests answered with 4xx/401, which is the window for an aborted queue entry.
* Solo stress: 400 consecutive runs of the test passed in 316 s with no hang, so the race needs the abort window; a plain scheduler race in `shutdown()` was ruled out by reading `socketserver.py` (the event is set in `finally`; the flag is checked after `clear()`).
* The same unguarded blocking listener exists in `resident_demo/app.py`, `resident_preview/app.py` and `server.py`.

## Planning readiness

Ready. Disposition: executed. Fix: make the listening socket non-blocking so a stale readiness raises `BlockingIOError` (an `OSError` that `_handle_request_noblock` already swallows), and force accepted sockets back to blocking. Regression test: `_handle_request_noblock` on an idle listener returns promptly instead of blocking.
