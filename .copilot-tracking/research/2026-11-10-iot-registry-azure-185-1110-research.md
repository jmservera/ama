## Repository facts (read at base)

* `device_identity.Registry` protocol: `create(device_id, run_id) -> None`, `run_of(device_id) -> str | None` (None means absent), `delete(device_id, run_id)` (atomic only-if-tagged, else no-op), `list_run(run_id) -> Sequence[str]`. Provision creates the Registry identity before it issues a credential; the protocol has no thumbprint and no auth-update. This unresolved pair contract stays open (not solved here).
* Provisioning treats any adapter exception as an unknown write: it rereads `run_of`; owner equal to the run adds the device to rollback; a foreign owner or None does not. Teardown refuses when `run_of` returns anything other than None or the run, so an unmarked existing device must be reported as non-None and not equal to the run.
* `device_provision` ships no adapters; `--apply` refuses without a named owner and both adapters. This task does not change it.
* Core `pyproject.toml`: extras `sql`, `blob`, `dev` (ruff 0.17.1, mypy 2.4.0). The local RPI gate installs `src/core[dev]` (`tools/rpi-checks.py`). So the SDK must be in the `dev` extra for the transport tests to run and not skip. `src/core/requirements.in/txt` is the hash-locked production set (blob only); this optional source increment does not change it.

## Selected SDK and verified contract (public official sources and installed-SDK inspection, 2026-11-10)

Throwaway venv `/tmp/sdkprobe` (not global, not in the repository). Selected: `azure-iot-hub==2.7.0` (PyPI latest; MIT; requires azure-core, msrest 0.7.1, uamqp 1.6.11).

* Python wheel factory: `IoTHubRegistryManager.from_token_credential(url, token_credential)` exists. The constructor builds an `azure.iot.hub.auth.AzureIdentityCredentialAdapter` over the supplied credential for HTTPS (scope `https://iothubs.azure.net/.default`) and an AMQP `SendClient` for cloud-to-device messages. Construction calls `get_token` once (verified by a fake credential). No connection string or key is used on this path. Entra only; the adapter must never fall back to `from_connection_string`.
* Undeclared dependency: `azure.iot.hub` imports `six`, which `azure-iot-hub 2.7.0` and `azure-core 1.41.0` do not declare. Importing fails with `ModuleNotFoundError: six` in a clean venv. The extra must pin `six` explicitly (verified `six 1.17.0` imports and works).
* `create_device_with_x509` calls `devices.create_or_update_identity(device_id, device)` with no conditional header. The official IoT Hub REST overview (https://learn.microsoft.com/en-us/rest/api/iothub/, page dated 2025-03-11) states the PUT table: `If-Match` absent: 201 Created when missing and **200 OK (unconditional overwrite) when the device exists**; `If-Match: *` on a missing device 412; `If-None-Match: *`: 201 Created when missing, **412 Precondition Failed when it exists**. Therefore the SDK convenience method is an upsert and is rejected; create-only needs `If-None-Match: *`.
* `create_or_update_identity(id, device, if_match=None, custom_headers=None, raw=False, **operation_config)` accepts `custom_headers`; the spike confirmed the header path. So a supported create-only request is `protocol.devices.create_or_update_identity(id, Device(...), custom_headers={"If-None-Match": "*"})` using SDK models and the SDK's own serializer, authentication and transport. Create-only semantics are therefore established from official documentation plus the SDK's public parameters; the service behaviour itself is documented and unobserved here.
* Status handling in the SDK: `create_or_update_identity` and `get_identity` accept only 200; `delete_identity` accepts only 204; any other status raises `msrest.exceptions.HttpOperationError` with `.response.status_code`. The documentation says a successful create can be 201 and a successful delete of an existing device 200, so the SDK raises on those documented successes. The adapter must classify by status code, never by "an exception happened", and must treat 201 on create and 200/204 on delete as success, 404 on read as absence.
* DELETE precondition (same REST page): `If-Match` absent or `*` deletes whatever exists; `If-Match: "xyz"` deletes only on an exact ETag match and returns 412 otherwise; deleting a missing resource returns 204. `IoTHubRegistryManager.delete_device(device_id, etag=None)` defaults the ETag to `"*"` and quotes via `_ensure_quoted`. The adapter must always pass an exact non-wildcard ETag and never use the default.
* `get_devices(top)`: the protocol layer takes `top`; any value outside 1 to 1000 is 1000; the operation has no continuation token. A returned list of 1000 therefore cannot be proven complete. The adapter must treat `len >= 1000` as incomplete and refuse. Twin queries (continuation tokens) are excluded by the ADR 0003 twin exclusion.
* Device resource fields: `deviceId`, `etag`, `generationId`, `status`, `statusReason` (128 UTF-8 characters), `authentication.type` (`selfSigned` for thumbprint X.509), `x509Thumbprint.primaryThumbprint`/`secondaryThumbprint`, `capabilities.iotEdge`. `statusReason` is public identity metadata that survives the device being disabled, needs no twin and is a suitable exact run marker. The documented `generationId` distinguishes a deleted and recreated device; the ETag changes on any modification.
* Transport and retry (msrest 0.7.1): `protocol.config.connection.timeout` default 100 seconds; `protocol.config.retry_policy.retries` default 3 with transparent urllib3 retries, applied when the lazily created thread-local session is first initialised. The spike with `requests.adapters.HTTPAdapter.send` patched showed: the real SDK serialises the request, sets `Authorization: Bearer <token>` from the injected credential, honours `config.connection.timeout=7`, and honours `retry_policy.retries=0` (adapter `max_retries.total == 0`). Every write the adapter sends is conditional (`If-None-Match: *`, `If-Match: "<etag>"`), so even a transparent transport retry cannot overwrite or delete a foreign or recreated identity.
* Closing: `IoTHubRegistryManager` has no `close`; its `__del__` calls `amqp_svc_client.disconnect_sync()`. msrest `SDKClient.close()` closes the HTTP session. The adapter closes only a manager it created.

## Design implications (decisions, with the refused alternatives)

1. Create-only by documented `If-None-Match: *`; 412 or 409 maps to a fixed conflict code and the existing identity is never adopted, overwritten or touched. Refused: the SDK convenience method (silent upsert), a prior-absence read followed by an unconditional write (race-prone).
2. Ownership is exactly `statusReason == "zava-forward:sim-run:v1:" + run_id`, not the `SYN-` prefix and not configured membership. An existing device without the exact marker reports a fixed non-run owner string that cannot be a valid run ID. Foreign identities are never deleted.
3. Delete is read-then-conditional: read the device, require the exact marker, a non-wildcard ETag and a generation ID, then delete with `If-Match: "<etag>"` once. A 412 refuses (stale, recreated or modified). Any other uncertain failure never retries; a readback decides between absent (done) and an explicit unknown-outcome error. Missing or foreign at read time is a non-destructive no-op.
4. `list_run` returns the marker-matched IDs from one bounded `get_devices(top=1000)` and refuses with an incomplete code when 1000 are returned. Refused: reporting a possibly truncated set as complete.
5. Errors are fixed sanitised codes raised outside the handler with no chain; the SDK response, token, thumbprint and exception text never leave the adapter.
6. Inputs: finite `EnrollmentSpec` (run ID, known `SYN-` IDs, public uppercase hex SHA-1 or SHA-256 thumbprints, unique), a hub hostname that exactly matches `<name>.azure-devices.net`, and one of an injected token credential (adapter builds and owns the manager lazily at first use) or an injected trusted pre-built manager (never owned). No ambient credential, subscription, environment or network access at import, construction, dry run or close. Devices are created disabled; no enable path exists.
7. Lazy optional import with `importlib`; a missing SDK or `six` gives a fixed `SDK_MISSING` code at first use only.

## Unobserved and out of scope (must not be claimed)

* Real service behaviour: `If-None-Match: *` 412, 201 versus 200 on create, delete success status, ETag format, `get_devices` payload completeness and the 1000 cap, `statusReason` round trip, thumbprint-only-primary acceptance, and the RBAC/permission model are documented or inferred, not observed. Local tests use the real SDK serialisation and request path against a transport simulator that models the documented REST table; that is a contract test, not Azure proof.
* Whole #185 live credential issuance, Key Vault storage, certificate issuance, rotation, mount access, revocation, teardown, role assignments, device-identity/credential pairing and CLI apply remain open. A fake token, a fictional owner or the module existing supplies no permission.
