===== slide-005 (main) One controlled route from evidence to action
  [None] PROPOSED CONTROL FLOW • CONCEPTUAL, NOT DEPLOYED
  [None] One controlled route from evidence to action
  [None] 05  /  PROPER WARM     •     TARGET CONTROL DESIGN—NOT A DEPLOYED TOPOLOGY • E08/E09/E10
  [None] WORKBOOK + SOURCE DATA / Validated one-way import
  [None] CONTROLLED API / Identity • access • approvals
  [None] SHARED CASE + EVIDENCE / Azure SQL + versioned Blob
  [None] STAFF WORKBENCH / Read case • request gated action / Human review before change
  [None] WORKFLOW RULES / Own • route • check • audit
  [None] BOUNDED AI • NO WRITE / Permitted inputs / Cited draft / flag to staff
  NOTES (134 spoken words; 203 total incl. evidence): This is one product with a controlled flow. Workbooks enter through validated, one-way import. Staff read a shared case and request actions through role-specific workbench views; the API checks identity, case access, evidence versions and required approvals before SQL state changes. Deterministic workflow routes tasks and gates.
Bounded AI receives permitted inputs and can return a typed choice, cited draft or concern to staff. It has no write credentials and cannot advance a case. A person reviews before any controlled change, then acts through the API. If AI fails, staff use the manual route without bypassing controls. Conflicting identifiers are quarantined, not silently merged.
This is a target design, not a deployed topology. Production identity, workload separation, private access, monitoring and recovery need separate proof. Narrow AI/SQL feasibility does not verify every component shown.
