### PC-001 [High]: Publication can proceed without disposing original Review findings

* Related IDs: P02-T01, P02-T02; acceptance criterion for genuine original Review
  and conditional exact-candidate publication.
* Evidence: P02-T01 in
  .copilot-tracking/details/2026-10-23/issue126-cost-refresh-phase-details.md
  says to route findings to later coordinator work. P02-T02 then permits push
  and draft creation if the complete gate passes. src/README.md explicitly
  separates local verification from independent review and publication
  permission.
* Concern: No rule distinguishes known out-of-scope activation/acceptance
  blockers, which may remain disclosed, from an original Review finding
  against this documentation candidate's accuracy, privacy or authority
  boundary. The latter could therefore survive a passing technical gate and
  be deferred until after publication.
* Impact: Conditional draft publication could publish an independently
  identified material defect even though the RPI sequence technically ran.
* Smallest useful change: Require an explicit disposition of every original
  Review finding before commit/gate/publication. Correct in-scope defects
  directly or stop publication on an unresolved material candidate defect;
  retain separately documented activation/whole-issue blockers without
  treating them as accepted. Preserve the original Review and do not repeat
  it. Any subsequent correction invalidates an earlier gate and requires the
  complete gate on the final commit.
* Action owner: Planning parent, then implementing parent for disposition.
* Exact resolving evidence: P02-T01/P02-T02 contain this dependency, and the
  eventual changes/disposition record maps each original Review finding to
  a correction or an explicit publication blocker, distinguishing deferred
  out-of-scope acceptance risks. The final receipt binds the corrected head.
* Decision route: Direct planner correction. No user response is required to
  require truthful review disposition; any later divergent scope request
  remains a separate decision.

<!-- rpi:critique id=PC-002 -->
### PC-002 [Medium]: The single signed-in draft task has bounds but no observable evidence chain

* Related IDs: FR3, P01-T02; Research Q3 and C4; staged signed-in feedback
  requirement.
* Evidence: P01-T02 in
  .copilot-tracking/details/2026-10-23/issue126-cost-refresh-phase-details.md
  lists sign-in/role, SQL persistence/restart, one Blob result and one AI
  draft, but does not name the synthetic task or say how these observations
  establish one usable signed-in result. The referenced API guide explicitly
  distinguishes actual authenticated role binding from a redirect.
* Concern: An implementer can satisfy the proposed checklist with unrelated
  SQL, Blob and AI observations, leaving the signed-in task/feedback claim
  untestable. "One real AI draft" alone does not identify which existing
  capability, synthetic input or result is to be checked.
* Impact: The supposedly minimum proposal can hide an unknown dependency or
  produce infrastructure smoke-test evidence presented as owner-testable
  workflow evidence.
* Smallest useful change: Describe one narrow existing synthetic draft task
  and its proposed evidence checkpoints: authenticated application 200 and
  expected role, explicit synthetic input, one real bounded model attempt,
  draft-only result visible for owner inspection, the owned SQL state that
  must survive restart, and the private result object associated with that
  run. Mark these proposed/not observed; if the existing task path cannot
  yet be identified, list that exact technical precondition as unresolved.
  Do not add a feedback subsystem, human pilot capture, quality floor,
  evaluation denominator or broader parity prerequisite.
* Action owner: Planning parent.
* Exact resolving evidence: P01-T02 specifies the single task and pass/fail
  observations, or explicitly names the unresolved task-path blocker; the
  future addendum can then reproduce those boundaries without claiming
  execution or usability.
* Decision route: Direct planner correction within the already requested
  minimum demo. Actual task approval and execution remain separately blocked.

<!-- rpi:critique id=PC-003 -->
### PC-003 [Medium]: Cleanup is referenced but its terminal state is not specified

* Related IDs: FR3, P01-T02; expiry and retained-liability requirements.
* Evidence: P01-T02 in
  .copilot-tracking/details/2026-10-23/issue126-cost-refresh-phase-details.md
  correctly gives latest start 2026-10-25T08:02Z, a two-hour envelope and
  retained-liability pricing, but only delegates rollback/stop conditions to
  later owner approval. The current addendum requires owned-only cleanup,
  retained history, retention charges through expiry and explicit recording
  of anything left behind.
* Concern: The new smaller proposal does not state which actions end the
  attended window, who verifies them, or how SQL history, the result object,
  any temporary model/configuration change and residual charges are treated.
  A six-hour margin is not a cleanup outcome.
* Impact: The proposed two-hour duration can be mistaken for the end of all
  incremental billing or permission/configuration changes; cleanup can also
  be read as permission to remove retained resources or history.
* Smallest useful change: Add a proposed authorized-operator closeout
  checklist covering no more AI attempts/jobs, rollback of only separately
  approved temporary changes, owned result-object disposition subject to
  retention, preservation of SQL histories/identities/retained estate, and
  a terminal status with timestamp and priced residual liabilities. State
  that the two-hour envelope includes its planned closeout and that the
  six-hour margin is not additional execution time. Unknown cleanup cost
  or unavailable operator remains an activation blocker.
* Action owner: Planning parent; an authorized operator would own later
  execution and verification only after separate approval.
* Exact resolving evidence: P01-T02 names the proposed closeout owner,
  terminal evidence, retention/liability treatment and time boundary.
  Neither the revised plan nor resulting documentation authorizes deletion,
  role changes or any other Azure operation.
* Decision route: Direct planner correction preserving existing constraints.
  Any actual mutation/retention choice still needs separate owner approval,
  not a new decision for this documentation continuation.
