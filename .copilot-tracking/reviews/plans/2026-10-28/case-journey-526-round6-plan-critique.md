### PC-003 [Medium]: Retry readiness does not distinguish committed success from reload failure

* Related IDs: Pending proposal requirement; AC1-AC3; P01-T02/P01-T03.
* Evidence:
  .copilot-tracking/details/2026-10-28/case-journey-526-round6-phase-details.md:25-30
  says to restore readiness after failure/success and separately preserve
  uncertain committed forms, but gives no transition oracle for these actions.
  src/api/src/zava_forward/api/web/assistants.js:31-38 awaits API success and
  then reload inside one catch. Generic refresh at
  src/api/src/zava_forward/api/web/app.js:608-615 similarly catches a failed
  redraw after the mutation has succeeded. Research explicitly identifies this
  boundary; neither acceptance criteria nor allocated matrix names its test.
* Concern: Unconditionally releasing the pending key and restoring the old
  card's readiness in finally can make a consumed proposal revision actionable
  again when its mutation succeeded but refresh failed. A quality redraw failure
  can similarly leave an old save control appearing safely retryable.
* Impact: Incorrect retry guidance and duplicate dispatch remain possible even
  after field invalidity and ordinary pending exclusion are fixed.
* Smallest useful change: Define distinct local-validation, definitive refusal,
  confirmed mutation success, reload failure after success and uncertain
  transport outcomes. Consume equal submitted drafts once success is confirmed,
  regardless of reload success; preserve later drafts. Do not revive consumed
  proposal revisions or advertise safe retries of committed/uncertain actions
  until current authoritative state is obtained. Report reload problems as
  status, not Reason/JSON errors. Retain existing resident/challenge safeguards.
* Action owner: Planning parent for explicit transitions and test rows;
  implementer for mutation-versus-reload handling.
* Exact resolving evidence: Revised details and acceptance matrix distinguish
  these outcomes. Held-response tests confirm API success followed by reload
  failure reconciles equal live/recovery/cache values, retains later values,
  leaves neither valid field aria-invalid and prevents a second stale dispatch.
  A definitive refusal preserves drafts and restores only legitimately
  retryable controls. Cover proposal and quality paths within existing owners.
* Decision route: Direct planner correction implementing the already requested
  no-duplicate/error-ownership contract; no divergent behavior decision.
