### PC-001 [High]: Incorrect `required_when` key and unpersisted rule definitions in `validation` break `pack_freshness` rule-diff and transitive stale propagation

* Related IDs: FR-2, FR-3, FR-4, AC-3, AC-4, AC-5, Q4, C2, C6, C10, P01, P01-T01, P01-T02
* Evidence: .copilot-tracking/details/2026-11-14/issue-98-field-validation-2142-phase-details.md, src/core/src/zava_forward/core/forms.py, src/core/src/zava_forward/core/form_review.py, src/core/src/zava_forward/core/form_validation.py
* Concern: Two concrete defects in P01-T01 prevent exact dependent-only stale propagation in pack_freshness: (1) P01-T01 step 5 specifies transitive propagation via required_when["field"], whereas forms._schema (src/core/src/zava_forward/core/forms.py:201) and form_review._report (src/core/src/zava_forward/core/form_review.py:381) store field["required_when"] as a list of condition dicts with keys {"field_id", "equals"}; indexing "field" either raises TypeError/KeyError or silently skips conditional-requirement dependents. (2) P01-T01 step 4 requires diffing saved["validation"] and current["validation"] for added, removed, or modified rules (kind, param, message, status), yet the draft in src/core/src/zava_forward/core/form_validation.py:143 and 174 stores only (rule_id, field_id, status, reason) in validation["results"] and (id, version, approval) in validation["rule_set"]. If a rule's param or message changes without changing its Pass/Fail outcome (for example, tightening min from 50 to 60 when the confirmed value is 80) or retargets field_id / sum addends under the same rule_id, saved["validation"] lacks kind, param, and message to detect the change or identify both prior and current affected fields. In addition, if current["content_sha256"] != saved["content_sha256"] while stale_fields is empty (such as after rejecting an unconfirmed field or a Superseded byte-identical schema), P01-T01 returns status="Stale" without ensuring reasons is non-empty.
* Impact: Conditional-requirement dependents fail to propagate staleness or raise runtime errors, rule parameter/message updates that preserve rule status falsely evaluate as Current or omit affected fields, and metadata-only pack drift can return status="Stale" with an empty reasons list.
* Smallest useful change: Update P01-T01 so that (a) each entry in validation["results"] within PACK_BODY_KEYS persists rule_id, field_id, kind, deepcopy(param), message, status, and reason; (b) pack_freshness compares saved and current validation["results"] keyed by rule_id across (field_id, kind, param, message, status), marking both saved and current field_ids when a rule is added, removed, or modified; (c) fixed-point transitive propagation checks any(c["field_id"] in stale_set for c in field["required_when"]) plus sum rule addends -> target field_id (across active and saved sum rules for existing schema fields); and (d) any digest, input_version, schema_digest, schema_impact, or rule_set drift appends a human-readable reason whenever status == "Stale". Update P01-T02 item 6(b) to assert that a rule param tightening that stays Pass still marks the target field and its required_when / sum dependents stale while leaving unrelated fields unaffected.
* Action owner: planning_parent
* Exact resolving evidence: Revised P01-T01 and P01-T02 in .copilot-tracking/details/2026-11-14/issue-98-field-validation-2142-phase-details.md specifying kind/param/message in validation["results"], c["field_id"] iteration over field["required_when"], non-empty Stale reasons, and the Pass-preserving rule-change test assertion.
* Decision route: Direct planner correction; no user decision required.

### PC-003 [Medium]: Overbroad `"Value lacks reviewer confirmation."` `Fail` emission on blank/wrong-type fields and underspecified `_check_rules`, `HUMAN_ONLY`, `attachment_id`, and `README.md` invariants

* Related IDs: FR-1, FR-2, FR-3, AC-1, AC-2, AC-3, AC-4, AC-6, Q1, Q2, Q3, C2, C3, C4, C10, P01-T01, P01-T02, P02-T01

* Concern: Four edge-case ambiguities in P01-T01 and P02-T01 conflict with existing form_review contracts: (1) P01-T01 instructs recording a "Fail" open issue ("Value lacks reviewer confirmation.") whenever a draft row claims Accepted/Corrected without passing _confirmed. In form_review._report (src/core/src/zava_forward/core/form_review.py:345-356) and src/core/README.md:647, however, a reviewer-confirmed whitespace-only string correction legitimately fails _confirmed's nonblank filter while remaining Unknown (never Fail), an accepted raw string on an integer field already emits "Fail": "Wrong schema value type.", and a value failing _reviewer_confirmed already emits "Value lacks reviewer confirmation." Appending "Value lacks reviewer confirmation." on all non-_confirmed Accepted/Corrected rows would misclassify blank strings as Fail, mislabel wrong-type acceptances, or duplicate _report's existing issue; additionally, evidence integrity must verify isinstance(evidence, dict) with non-None "source" and "locator" (not merely row.get("evidence") == last["new"].get("evidence"), which passes if both were wiped to {}). (2) _check_rules omits rejecting rules whose target field_id (or sum addend) has category in forms.HUMAN_ONLY (src/core/src/zava_forward/core/forms.py:20; src/core/src/zava_forward/core/form_validation.py:86), omits exact key-set enforcement (SET_KEYS, APPROVAL_KEYS, BOUND_KEYS, RULE_KEYS = {"rule_id", "field_id", "kind", "param", "message"}) and at-most-one sum rule per field_id, does not note that APPROVAL_KEYS permits None/empty approver and evidence_ref during _check_rules so unapproved rule sets reach _approval_gaps and return Not evaluated (AC-1) rather than ValueError, and does not specify Decimal equality for equals/one_of on number fields (100 vs 100.0) while keeping form_review._equal on all other types. (3) form_review._report attachments (src/core/src/zava_forward/core/form_review.py:409-420) carry "id" and "version" without an "attachment_id" key and are built from draft["history"], while P01-T01 refers to non-"Empty" fields (form_review uses row["evidence"] is not None, never state "Empty") and requires evidence["attachment_id"] to match the attachment entry without specifying that review_pack stamps a deterministic attachment_id (such as f"{id}:v{version}") onto each detached pack attachment and falls back to None if a tampered field row cites a source absent from history. (4) src/core/README.md lines 668 and 692-693 state "Approved rules, calculations and reviewed packs still do not exist"; P02-T01 should reconcile those lines so README.md remains internally consistent.
* Impact: Blank-string corrections can fail AC-3/P01-T02 by producing Fail instead of Unknown, unapproved rule sets with null approver metadata can raise ValueError instead of Not evaluated, rules can target human-only authority fields, pack["attachments"] can omit attachment_id or raise KeyError on tampered draft rows, and src/core/README.md can contradict itself.
* Smallest useful change: Clarify P01-T01 and P02-T01 so that: (a) "Value lacks reviewer confirmation." is added (deduplicated against report["issues"]) only when an Accepted/Corrected row fails confirmation provenance (_reviewer_confirmed, decision-to-state match, registered nonblank reviewer, or intact dict evidence with source/locator matching last["new"]["evidence"]), leaving blank strings Unknown and wrong-type values as "Wrong schema value type."; (b) _check_rules enforces exact key sets, rejects HUMAN_ONLY targets/addends and duplicate sum rules per field with ValueError, accepts nullable/blank approver and evidence_ref in _check_rules for _approval_gaps to report Not evaluated, and uses Decimal(str(...)) equality on number fields for equals/one_of; (c) review_pack collects evidence from rows with row["evidence"] is not None, stamps deterministic attachment_id = f"{att['id']}:v{att['version']}" on each detached attachment entry, and links evidence["attachment_id"] via lookup (None if tampered/absent from history); and (d) P02-T01 updates src/core/README.md lines 668 and 692-693 alongside adding the form_validation section.
