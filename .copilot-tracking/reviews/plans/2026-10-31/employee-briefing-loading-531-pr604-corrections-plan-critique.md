### PC-001 [Medium]: Rejected-push recovery can publish content not covered by the recorded validation

* Related IDs: AC3-AC5; P01-T02/P01-T03; P02-T01/P02-T02.
* Evidence: .copilot-tracking/details/2026-10-31/employee-briefing-loading-531-pr604-corrections-phase-details.md,
  P02-T01 orders git pull --no-rebase after rejection and permits conflict
  resolution. P02-T02 then permits another evidence/accounting commit and push.
  The dependency statement in the correction plan binds publication to the
  earlier Review but supplies no content-change invalidation rule for either
  later path.
* Concern: A rejected-push merge or manual conflict resolution can change
  repaired destinations, historical text or API inputs after successful
  validation and Review. Matching remote/local HEAD after pushing establishes
  delivery identity, not that the delivered correction is still the assessed
  content. A later accounting commit also changes the publication SHA and needs
  an explicit relationship to the fixing commit and recorded validation.
* Impact: AC3/AC4 can be reported against an earlier candidate while AC5 delivers
  different content, or thread replies can name a commit whose repairs were
  changed by the recovery merge.
* Smallest useful change: Add a recovery checkpoint after pull/merge and before
  retrying push: inspect the resulting diff and conflicts, rerun exact 53-link,
  CLI, historical-preservation and whitespace checks, and rerun existing API
  tooling/tests when their inputs changed. Record the new candidate SHA and
  whether the single Review's assessed correction remains content-equivalent.
  Restrict post-disposition accounting commits to outcome metadata and verify
  that repair/validation inputs are unchanged before the further push. If
  substantive unreviewed changes invalidate the one Review, stop and record
  the blocker rather than silently using stale approval or launching a second
  Review under this bounded authorization.
* Action owner: Planning parent for P02 detail correction; publication executor
  for the recovery checkpoint.
* Exact resolving evidence: Revised P02-T01/P02-T02 specifies the checkpoint and
  invalidation handling. Execution evidence later identifies pre/post-recovery
  SHAs, conflict/diff inspection, exact semantic/preservation results, affected
  API reruns where necessary, Review applicability and the final verified
  remote SHA. Accounting-only changes are distinguished from repair changes.
* Decision route: Direct planner correction. Authorized pull/non-force push and
  the single critique/Review budget remain unchanged; no full local gate or
  divergent user decision is requested.
