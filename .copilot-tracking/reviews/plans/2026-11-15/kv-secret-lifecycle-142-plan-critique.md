### PC-001 [High]: Post-switchover rotation verification leaves authenticated Entra token-exchange proof optional and under-specifies stage-level retirement gating

* Related IDs: `FR-2`, `P01`, `P01-T01`, `P03-T01`, `P04-T01`; research `C3`, `C6`
* Evidence: .copilot-tracking/plans/2026-11-15/kv-secret-lifecycle-142-plan.md (`FR-2`), .copilot-tracking/details/2026-11-15/kv-secret-lifecycle-142-phase-details.md (`P01-T01`), `infra/modules/containerapps.bicep:290-322`, `infra/scripts/secret_lifecycle.py:98`
* Concern: In `infra/modules/containerapps.bicep`, `/healthz` and `/sign-in` are in `apiAuth` `excludedPaths`, anonymous `/api/me` returns `401` without contacting Entra ID, and `GET /sign-in` -> `/.auth/login/aad` issues a `302` authorize redirect using only `clientId`. Container Apps EasyAuth presents `entra-client-secret` (`clientSecretSettingName`) only during the OAuth2 authorization-code callback or token refresh that establishes an authenticated session (`200` on `/api/me` or `/app` after fresh sign-in). However, `FR-2` specifies `browser /sign-in == 302 and/or authenticated probe 200` and `P01-T01` specifies `and authenticatedApiStatus == 200 (when provided)`, while also not stating explicitly that `safeToRetirePriorCredential` must remain `False` during `stage == "dual_secret_overlap"` and `stage == "post_retire"`.
* Impact: If `authenticatedApiStatus` is omitted at `post_switchover` (or if an operator runs `rotation-verify` at `dual_secret_overlap` and sees `safeToRetirePriorCredential=True`), `verify_staged_entra_rotation` can authorize deleting `priorKeyId` even when the newly stored Key Vault secret value does not match Entra ID or has not been switched over -- causing an immediate sign-in outage and weakening step 4 of existing `rotation_plan` (`infra/scripts/secret_lifecycle.py:98`).
* Smallest useful change: Revise `FR-2`, `P01-T01`, and `P03-T01` so that (1) when `browserMode=True` (default), `post_switchover` and `post_retire` require `authenticatedApiStatus == 200` from a post-switchover newly authenticated session / callback probe in addition to `healthzStatus == 200`, `anonymousApiStatus == 401`, and `signInRedirectStatus == 302` (`authenticatedApiStatus` may be omitted only in `dual_secret_overlap` pre-switchover snapshots), (2) `safeToRetirePriorCredential` is `True` if and only if `stage == "post_switchover"` and `ok is True` (`False` in `dual_secret_overlap`, `rollback`, and `post_retire`), and (3) `post_retire` requires either historical `priorCredential` `[startDateTime, endDateTime]` metadata proving `>= min_overlap_minutes` overlap before `retiredAt` or a matching `post_switchover` receipt digest rather than an unverified scalar integer alone, with negative unit coverage in `P03-T01`.
* Action owner: planner
* Exact resolving evidence: Updated `FR-2` in .copilot-tracking/plans/2026-11-15/kv-secret-lifecycle-142-plan.md and updated `P01-T01` and `P03-T01` in .copilot-tracking/details/2026-11-15/kv-secret-lifecycle-142-phase-details.md mandating post-switchover `authenticatedApiStatus == 200`, `stage == "post_switchover"` gating on `safeToRetirePriorCredential`, and verifiable pre-retirement overlap evidence.
* Decision route: direct planner correction (no divergent user decision needed).

### PC-002 [High]: Data-plane access audit leaves symbolic-to-OID principal mapping optional and omits normalization for OID-less Key Vault notification logs and `401`/`403` thresholds

* Related IDs: `FR-3`, `P01-T01`, `P02-T01`, `P03-T01`, `P03-T02`, `P04-T01`; research `C1`, `C12`
* Evidence: .copilot-tracking/plans/2026-11-15/kv-secret-lifecycle-142-plan.md (`FR-3`), .copilot-tracking/details/2026-11-15/kv-secret-lifecycle-142-phase-details.md (`P01-T01`, `P02-T01`, `P03-T01`), `infra/role-assignments.json:16-42`, `infra/modules/keyvault.bicep:81-112`
* Concern: `infra/role-assignments.json` contains symbolic identity keys (`api`, `token-maintenance`, `resident-demo`, `agents`, `orchestrator`, `import`) with zero Entra Object IDs, whereas `az role assignment list` and `AzureDiagnostics` (`identity_claim_oid_g`) contain only GUIDs. `P02-T01` makes `--expected-principals PATH` optional on `access-audit` without defining fail-closed behavior when omitted or partial: inferring expected callers from live `assignments` (`roles.json`) would allow an unauthorized Azure RBAC assignment to self-whitelist its own data-plane calls, while omitting `agents`/`orchestrator`/`import` OIDs prevents `forbidden_workload_caller` detection. Additionally, `keyvault.bicep` sends `allLogs` to Log Analytics (`C1`), which includes system Event Grid rows (`SecretNearExpiryEventGridNotification`, `SecretExpiredEventGridNotification` in `keyvault.bicep:81`) that carry no caller OID, and `FR-3` says `401`/`403` bursts while `P03-T01` says `401`/`403` events (whereas Key Vault's OAuth bearer challenge routinely emits single unauthenticated `401` preflights and `keyvault.bicep:108` alerts at `GreaterThan 4`).
* Impact: Without explicit fail-closed OID-mapping rules, `access-audit` will either trust rogue Azure RBAC grants or misclassify legitimate/system `AzureDiagnostics` rows, and unit tests in `P03-T01` will conflict with `FR-3` on `401` vs `403` handling.
* Smallest useful change: Update `FR-3`, `P01-T01`, `P02-T01`, and `P03-T01` so that (1) `default_expected_caller_policy` never auto-trusts OIDs from live `assignments`; any RBAC assignment or data-plane caller OID absent from `principal_map` is flagged fail-closed (`unexpected_caller` / `unmapped_rbac_principal`), and `principal_map` validates distinct non-empty GUIDs when supplied (`--expected-principals` required for zero-anomaly sign-off or explicitly documented as fail-closed when omitted), (2) platform lifecycle/notification operations (`SecretNearExpiryEventGridNotification`, `SecretExpiredEventGridNotification`) without caller OIDs are counted as system notifications rather than `unexpected_caller`, whereas data-plane secret operations (`SecretGet`, `SecretSet`, `SecretDelete`, `SecretPurge`, `SecretList`, etc.) with missing OID bucket under `<anonymous>`, and (3) `denied_access_activity` triggers deterministically on any `403` response or when `401` count meets `denied_401_threshold` (default `5`, matching `keyvault.bicep` `threshold: 4`, configurable for unit tests).
* Action owner: planner
* Exact resolving evidence: Updated `FR-3` in .copilot-tracking/plans/2026-11-15/kv-secret-lifecycle-142-plan.md and updated `P01-T01`, `P02-T01`, and `P03-T01` in .copilot-tracking/details/2026-11-15/kv-secret-lifecycle-142-phase-details.md defining fail-closed `principal_map` resolution, platform-notification vs anonymous-caller normalization, and exact `401`/`403` anomaly thresholds.
* Decision route: direct planner correction.

### PC-003 [Medium]: Zero-secret guard (`FR-1`) contradicts `verify_access_review_ledger` non-raising semantics and risks false positives on ARM `{"value": [...]}` envelopes and 32/64-hex digests

* Related IDs: `FR-1`, `FR-4`, `P01-T01`, `P02-T01`, `P03-T01`; research `C7`, `C8`, `C10`
* Evidence: .copilot-tracking/plans/2026-11-15/kv-secret-lifecycle-142-plan.md (`FR-1`), .copilot-tracking/details/2026-11-15/kv-secret-lifecycle-142-phase-details.md (`P01-T01`, `P02-T01`), `src/core/src/zava_forward/core/diagnostic_logging.py:31-36`, `infra/scripts/setup-entra.py:1530`
* Concern: Three concrete edge cases in `assert_no_secret_material` conflict across the plan:
  1. `FR-1` states that lifecycle rotation and access-review functions reject raw secret keys or credential-bearing strings by raising `SecretExposureError`, whereas `P01-T01` says `verify_access_review_ledger` walks entries without raising on invalid data while calling `assert_no_secret_material`, and `P02-T01` specifies only exit codes `0`/`1` (not `2`) for `ledger-verify`.
  2. Standard Azure REST / Graph JSON responses (`az rest` for role assignments, revisions, secrets, `passwordCredentials`) wrap arrays in a top-level `{"value": [...]}` list envelope, whereas `"value"` holding a string/scalar or nested inside a secret/credential item is secret material.
  3. Research `C10` cites `diagnostic_logging.SENSITIVE`, whose `\b[0-9a-f]{32,}\b` and `[A-Za-z0-9+/]{40,}={0,2}` patterns match valid 32-hex Key Vault secret version IDs, `entra-<32hex>-<12hex>` staged secret names (`setup-entra.py:1530`), 64-hex SHA-256 `prevHash`/`entryHash`/`evidenceDigest`/HMAC `signature` values, and ARM resource IDs.
* Impact: Reusing `diagnostic_logging.SENSITIVE` or rejecting top-level list envelopes will reject valid metadata fixtures and signed ledgers, while inconsistent `SecretExposureError` handling in `verify_access_review_ledger` will break either `FR-1` exception assertions or `ledger-verify` CLI error handling.
* Smallest useful change: Clarify `P01-T01` and `P02-T01` so that (1) `assert_no_secret_material` raises `SecretExposureError` consistently across all domain functions including `verify_access_review_ledger` (while non-secret schema, hash, signature, and schedule failures in `verify_access_review_ledger` return `intact=False` without raising, and CLI `ledger-verify` catches `SecretExposureError` to exit `2`), (2) CLI/input normalization unwraps top-level ARM `{"value": [...]}` list envelopes only when `"value"` is a `list` of metadata mappings while `assert_no_secret_material` rejects `"value"` anywhere else (including empty or non-list values), and (3) `assert_no_secret_material` uses targeted credential regexes (`?sig=`, `&sig=`, `?sv=`, `Bearer `, `Basic `, `eyJ[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]+`, `sk-`, `SharedAccessSignature`, `AccountKey=`) rather than generic 32+-hex or 40+-base64 path matchers.
* Action owner: planner
* Exact resolving evidence: Updated `P01-T01` and `P02-T01` in .copilot-tracking/details/2026-11-15/kv-secret-lifecycle-142-phase-details.md specifying `SecretExposureError` propagation in `verify_access_review_ledger` / `ledger-verify` (exit `2`), dedicated non-colliding credential patterns, and ARM `{"value": [...]}` list-envelope handling.
* Decision route: direct planner correction.

### PC-004 [Medium]: Signed review ledger lacks cross-entry vault-scope continuity, 1-to-1 audit/decision digest binding, and symlink/repo-outside key-file rules

* Related IDs: `FR-4`, `NFR-1`, `P01-T01`, `P02-T01`, `P03-T01`, `P03-T02`; research `C7`, `C8`, `C11`
* Evidence: .copilot-tracking/details/2026-11-15/kv-secret-lifecycle-142-phase-details.md (`P01-T01`, `P02-T01`), `infra/scripts/private-cutover-proof.py:218-226`, `src/core/src/zava_forward/core/ledger.py:20-35`
* Concern: First, `P01-T01` specifies `prevHash`, `entryHash`, `signature`, `reviewedAt`, and `nextReviewDue` for signed review records, but does not explicitly bind `vaultName` (and verify identical `vaultName` across chained entries), embed `auditDigest` / `windowStart` / `windowEnd`, or require deterministic 1-to-1 matching between `audit_report` RBAC assignment keys + `anomalyId`s and `decisions` (so extra or dropped rows cannot slip past a naive count or subset check). Second, `P02-T01` checks `(st_mode & 0o077) == 0` on `--key-file` and `--keys-file`, but unlike `infra/scripts/private-cutover-proof.py:218-226`, does not reject symlinks or key files stored inside the Git repository tree, nor does it specify the exact file format of `--keys-file` for multi-quarter key lookup.
* Impact: Without vault continuity and 1-to-1 keyed decision matching, records from a disposable dev vault could be chained onto an environment ledger or omit an anomaly/assignment row; without symlink/repo-path guards and a fixed `--keys-file` schema, operators risk placing signing keys inside the worktree and CLI tests risk key-format mismatches.
* Smallest useful change: Specify in `P01-T01` and `P02-T01` that (1) signed ledger entries record `vaultName`, `windowStart`, `windowEnd`, and `auditDigest`, match `decisions` 1-for-1 by deterministic assignment ID (`principalId`, `role`, `scope`) and `anomalyId`, and `verify_access_review_ledger` rejects cross-entry `vaultName` drift, and (2) CLI `--key-file` / `--keys-file` loaders reject symlinks and paths inside the repository root (`REPO`), and define `--keys-file` as an owner-only (`0600`) JSON mapping `{"<key_id>": "<key-string>"}` (UTF-8 or `hex:`/`base64:` >= 32 decoded bytes, scanned so keys are never echoed).
* Action owner: planner
* Exact resolving evidence: Updated `P01-T01` and `P02-T01` in .copilot-tracking/details/2026-11-15/kv-secret-lifecycle-142-phase-details.md defining `vaultName` continuity, `auditDigest` and 1-to-1 keyed decision matching, non-symlink repo-outside key-file checks, and the `--keys-file` JSON map schema.
* Decision route: direct planner correction.

## Strengths and Residual Risk

* Strong architectural boundary: Placing pure zero-dependency verification and cryptographic ledger logic in `src/core/src/zava_forward/core/secret_lifecycle.py` while keeping CLI/file I/O in `infra/scripts/secret_lifecycle.py` respects `src/core/tests/test_dependency_rule.py` (`C17`) and automatically subjects core invariants to `src-core` CI (`ruff` + `mypy --strict`, `C16`).

* Accepted residual risk: Offline deterministic tests prove rotation state-machine invariants, rollback gating, caller anomaly detection, and cryptographic ledger integrity, while live operator execution against the deployed `ama` resource group and Entra tenant remains an explicitly labeled operational follow-up owned by `@jmservera`.
