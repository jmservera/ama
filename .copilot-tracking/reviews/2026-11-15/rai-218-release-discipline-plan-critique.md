## Verdict

* Verdict: Revise
* Rationale: The candidate plan accurately captures all 15 authoritative requirement IDs, preserves existing offline `constructed-fixture` workflows, and cleanly separates `rai_exercise_acceptance` from `real_ai_delivery_gate`. However, five concrete implementation hazards in the phase details would cause silent audit loss, SQLite self-deadlock, existing regression breakage, or local `unittest`/`mypy` failures if executed verbatim: `SqlStore.audit()` buffering without commit when called inside `with store.lock:` (`PC-001`), nested `BEGIN IMMEDIATE` SQLite self-deadlock and missing `not self.sql` / `?assessment=...` branches in readiness endpoints (`PC-002`), a non-existent `monitoring_coverage` helper name plus `"legacy:*"` prefix and pre-`OQ-017` check ordering in `assistant_release.record()` / `assistants.record_release()` (`PC-003`), cross-package `src/api/tests` imports during standalone `src/core` unit-test runs (`PC-004`), and `mypy` `strict = true` `[no-untyped-call]` errors against untyped migrated `core` modules without modifying `pyproject.toml` (`PC-005`). Every finding is a direct planner correction requiring zero user input.

### PC-001 [Critical]: `SqlStore.audit()` called inside `with store.lock:` buffers to `self.local.pending` without committing, dropping `rai_live_activation_rejected` audits on SQL stores

* Related IDs: AC 1, `FR-PLAN-01`, `NFR-PLAN-01`, `OQ-017`, `C5`, `C6`, `P01`, `P01-T01`, `P01-T02`, `P03-T01`
* Evidence: .copilot-tracking/details/2026-11-15/rai-218-release-discipline-phase-details.md (`P01-T01`), src/core/src/zava_forward/core/sqlstore.py (lines 114-160, 1398-1416), src/core/src/zava_forward/core/store.py (lines 183-187)
* Concern: `P01-T01` specifies that `emit_live_activation_rejection_audit(store, ...)` writes `store.audit(actor_id, "rai_live_activation_rejected", "-", ...)` "under `store.lock` when available". On JSON `Store` (`src/core/src/zava_forward/core/store.py` lines 183-187), `store.audit()` mutates `self.last_hash` and appends directly to `audit.jsonl`, so acquiring `store.lock` is right. On `SqlStore` (`src/core/src/zava_forward/core/sqlstore.py` lines 114-160 and 1398-1416), however, `self.lock` is `_SyncLock`: whenever `self.lock.depth > 0` (that is, inside `with store.lock:`), `SqlStore.audit()` appends `item` to `self.local.pending` and returns immediately without writing to the SQLite `audit` table. `self.local.pending` is only flushed by `store.save()`. When live activation is rejected and raises `LiveActivationApprovalError` without calling `store.save()`, the rejection audit entry is absent from `sql_store.audit_entries()` and remains stranded in thread-local `self.local.pending` until an unrelated later `save()` on the same worker thread. Only when `self.lock.depth == 0` does `SqlStore.audit()` invoke `self._audit_immediate(item)` (`BEGIN IMMEDIATE` ... `_append_audit` ... `COMMIT` under `self.dblock`).
* Impact: Rejected live activation attempts against `SqlStore` (including `POST /api/assistants/releases` and `SqlStore.activate_ai_task_live`) fail to persist `rai_live_activation_rejected` to the SQL audit ledger, violating AC 1 and `NFR-PLAN-01` and polluting thread-local pending audit state.
* Smallest useful change: Specify in `P01-T01` that `rai_control_plane`'s audit helper (`emit_live_activation_rejection_audit` and `activate_live_task`'s `rai_live_activation_recorded` emission when no `store.save()` follows) commits immediately on SQL-backed stores: if `hasattr(store, "_audit_immediate")`, invoke `store._audit_immediate({"ts": store.now(), "user": actor_id, "action": action, "case_id": "-", "detail": detail})` directly (which acquires `store.dblock` and commits to the `audit` table regardless of `store.lock.depth` without touching `self.local.pending`), and otherwise acquire `with store.lock:` before calling `store.audit(...)` on file-backed JSON `Store` / stub stores. Add an explicit SQL-backed assertion in `P03-T01` verifying `sql_store.audit_entries()` contains `rai_live_activation_rejected` and `sql_store.verify_audit()` returns `True` immediately after a rejected live activation.
* Action owner: planning parent (`rpi-plan`)
* Exact resolving evidence: Revised `P01-T01` and `P03-T01` in .copilot-tracking/details/2026-11-15/rai-218-release-discipline-phase-details.md specifying `_audit_immediate` SQL persistence vs `with store.lock:` JSON `Store` persistence and immediate `sql_store.audit_entries()` + `sql_store.verify_audit()` test verification.
* Decision route: Direct planner correction (`planner-direct`)

### PC-002 [High]: Nested `BEGIN IMMEDIATE` SQLite self-deadlock, missing `read_only()` guard, and omitted `not self.sql` / `?assessment=...` paths in readiness endpoints

* Related IDs: AC 3, `FR-PLAN-03`, `NFR-PLAN-02`, `C4`, `C8`, `C12`, `P01`, `P01-T01`, `P01-T02`, `P02-T01`
* Evidence: .copilot-tracking/details/2026-11-15/rai-218-release-discipline-phase-details.md (`P01-T01`, `P01-T02`, `P02-T01`), src/core/src/zava_forward/core/assistants.py (lines 1218-1235, 1534-1628), src/core/src/zava_forward/core/assistant_release.py (lines 28-39, 322-358), src/core/src/zava_forward/core/governance.py (lines 772-792), src/core/src/zava_forward/core/sqlstore.py (lines 251-255), src/api/src/zava_forward/api/server.py (lines 560-571, 700-721)
* Concern: Four concrete interactions affect `exercise_acceptance_report()` wiring across `Assistants.registry()`, `GovernanceMixin.governance_view()`, and `/api/governance`: (1) `Assistants.transaction()` (`src/core/src/zava_forward/core/assistants.py` lines 1219-1225) opens a fresh SQLite connection via `self.store.assistant_connection()` and executes `BEGIN IMMEDIATE`. `Assistants.registry(user)` builds its SQL response inside `with self.transaction() as db:` (`assistants.py` lines 1547-1628). If `Assistants.registry(user)` calls `exercise_acceptance_report(..., assistants_service=self)` before exiting `with self.transaction() as db:`, and `exercise_acceptance_report` opens a second `assistants_service.transaction()` (or writes via a second connection), SQLite blocks on `BEGIN IMMEDIATE` on the same thread for `busy_timeout = 5000` ms and raises `sqlite3.OperationalError: database is locked`, causing `GET /api/assistants` to return HTTP 503 (`server.py` lines 715-720). (2) `assistant_release.assessment(db, ...)` executes `UPDATE` invalidations unless wrapped in `with assistant_release.read_only():` (`assistant_release.py` lines 28-39, 336-352), so status endpoints inspecting SQL release state without `read_only()` would mutate SQLite during `GET` requests. (3) `Assistants.registry(user)` has an early `if not self.sql: return dict(...)` branch (`assistants.py` lines 1537-1546) used on JSON `Store`; omitting `**exercise_acceptance_report(...)` from that branch omits `rai_exercise_acceptance` and `real_ai_delivery_gate` on JSON-backed `/api/assistants` responses. (4) In `src/api/src/zava_forward/api/server.py` lines 562-570, `/api/governance` invokes `s.governance_view(u)` at line 562 and invokes `s.governance_view(u, assessment)` again at line 570 when `?assessment=...` is passed; both call sites (or a single post-query call) must forward `assistants_service=app.assistants`, and `GovernanceMixin.governance_view` (`governance.py` lines 772-792) should compute `exercise_acceptance_report` outside `with self.lock:` after `_need_manager` succeeds so `store.lock` is not held across SQLite reads.
* Impact: Causes HTTP 503 `database is locked` self-deadlocks on SQL-backed `GET /api/assistants`, unintended SQL mutations on status reads, and missing or inconsistent readiness sections on JSON-store `/api/assistants` and `/api/governance?assessment=...`.
* Smallest useful change: Update `P01-T01`, `P01-T02`, and `P02-T01` so that: (a) `exercise_acceptance_report(store, user=None, assistants_service=None, db=None)` inspects SQL release rows strictly read-only under `with assistant_release.read_only():` using either a caller-supplied `db` cursor/connection or a read-only `store.assistant_connection()` query (never opening a nested `BEGIN IMMEDIATE` `assistants_service.transaction()`); (b) `Assistants.registry(user)` attaches `**exercise_acceptance_report(...)` on both the `not self.sql` return and the SQL return (computing after exiting `with self.transaction() as db:` or passing `db=db`); (c) `GovernanceMixin.governance_view` merges `**exercise_acceptance_report(...)` after `_need_manager` outside `with self.lock:`; and (d) `server.py` forwards `assistants_service=app.assistants` across both `/api/governance` paths (default and `?assessment=...`).
* Action owner: planning parent (`rpi-plan`)
* Exact resolving evidence: Revised `P01-T01`, `P01-T02`, and `P02-T01` in .copilot-tracking/details/2026-11-15/rai-218-release-discipline-phase-details.md specifying read-only non-nested SQL inspection (`assistant_release.read_only()`), coverage of both `not self.sql` and SQL returns in `Assistants.registry()`, post-lock merging in `governance_view`, and forwarding `assistants_service` on both `/api/governance` branches.
* Decision route: Direct planner correction (`planner-direct`)

### PC-005 [Medium]: New `src/core` modules run under `mypy` `strict = true` (`disallow_untyped_calls = true`) without `pyproject.toml` overrides when calling untyped migrated `core` modules

* Related IDs: `NFR-PLAN-02`, `P01`, `P01-T01`, `P03`, `P03-T01`, `P03-T02`
* Evidence: .copilot-tracking/details/2026-11-15/rai-218-release-discipline-phase-details.md (`P01`, `P01-T01`, `P03`, `P03-T01`, `P03-T02`), src/core/pyproject.toml (lines 38-66, 150-175), src/api/pyproject.toml (lines 75-92)
* Concern: In `src/core/pyproject.toml`, `[tool.mypy]` sets `strict = true` (`disallow_untyped_calls = true`, `disallow_untyped_defs = true`) across `files = ["src", "tests"]`. Migrated modules `zava_forward.core.ai_registry`, `assistant_release`, `assistants`, `store`, `sqlstore`, `dataset`, and `release_support` have `ignore_errors = true` without `follow_imports = "skip"` (`src/core/pyproject.toml` lines 55-65), and their functions (`ai_registry.get`, `Store`, `SqlStore`, `Assistants`, `release_support.install`, `dataset.build`) are unannotated. Because `src/core/pyproject.toml` is rightly kept out of scope (avoiding dependency-manifest edits under the repository validation-tier rules), calling any of those unannotated functions directly inside new typed modules `rai_control_plane.py` or `test_rai_control_plane_218.py` fails `(cd src/core && python3 -m mypy)` with `[no-untyped-call]`. Similarly, `src/api/tests/test_rai_release_readiness_api_218.py` is checked under `src/api/pyproject.toml` `strict = true` and requires explicit `-> None` and parameter annotations on every test and helper method.
* Impact: Causes immediate `(cd src/core && python3 -m mypy)` `[no-untyped-call]` or `[no-untyped-def]` failures in `P01` and `P03` or tempts an implementer to modify `pyproject.toml` outside the owned file boundary.
* Smallest useful change: Add an explicit typing note in `P01-T01` and `P03-T01` instructing the implementer not to edit `src/core/pyproject.toml` or `src/api/pyproject.toml`, to annotate all functions and test methods completely (`-> None`, typed dicts/dataclasses), and in `rai_control_plane.py` and `test_rai_control_plane_218.py` to bind untyped migrated `core` modules (`ai_registry`, `assistant_release`, `assistants`, `store`, `sqlstore`, `dataset`, `release_support`) through `Any`-typed module aliases or `Protocol` interfaces so `(cd src/core && python3 -m mypy)` and `(cd src/api && PYTHONPATH=../core/src:../agents/src python3 -m mypy)` pass under `strict = true` with zero manifest edits.
* Action owner: planning parent (`rpi-plan`)
* Exact resolving evidence: Revised `P01-T01` and `P03-T01` in .copilot-tracking/details/2026-11-15/rai-218-release-discipline-phase-details.md recording the `Any`-alias / `Protocol` boundary for untyped migrated `core` modules and `strict = true` annotations without `pyproject.toml` modifications.
* Decision route: Direct planner correction (`planner-direct`)
