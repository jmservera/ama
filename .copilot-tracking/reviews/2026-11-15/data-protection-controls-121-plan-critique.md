### PC-001 [High]: Store-backed RightsRequestLedger loses data across SqlStore reopen and sync without SqlStore.DOCS registration and lock-scoped access

* Related IDs: Objective 4, FR-4, NFR-2, P01, P01-T03, P02-T01, P03-T02; research C1, C14
* Evidence: src/core/src/zava_forward/core/sqlstore.py:911, src/core/src/zava_forward/core/sqlstore.py:1236, src/core/src/zava_forward/core/sqlstore.py:1393, src/core/src/zava_forward/core/sqlstore.py:1404-1435, src/core/src/zava_forward/core/sqlstore.py:1449-1456, src/core/src/zava_forward/core/store.py:322-327, src/core/src/zava_forward/core/aftercare_store.py:48-84, .copilot-tracking/details/2026-11-15/data-protection-controls-121-phase-details.md
* Concern: `P01-T03` persists store-backed rights requests via `store.data.setdefault("rights_requests", [])` + `store.save()` + `store.audit(...)` while restricting `P01` edits exclusively to `data_protection.py`. Whereas JSON `Store.save()` writes all of `self.data`, `SqlStore` (and `MssqlStore`) persists top-level `self.data[key]` documents to the existing `meta` table only when `key` appears in `SqlStore.DOCS` (`sqlstore.py:1393`). Because `"rights_requests"` is absent from `SqlStore.DOCS` (and `SqlStore.MERGE_PRESERVED_DOCS` at `sqlstore.py:911`), any `SqlStore`-backed `RightsRequestLedger` silently discards all recorded rights requests on store reopen, and `SqlStore._proc_sync()` (`sqlstore.py:1404-1410`) pops or replaces `self.data[key]` on `with store.lock:` entry, detaching any list reference cached in `__init__`. Furthermore, `SqlStore` commits `meta` documents and queued `audit` entries atomically in one transaction only when `store.audit(...)` runs before `store.save()` inside `with store.lock:` (`sqlstore.py:1236`), whereas JSON `Store` runs `store.save()` before `store.audit(...)` (`store.py:322-327`), and `store.audit` detail strings must omit raw `subject_key` values so personal identifiers never enter the append-only audit ledger. Also `P01-T03` does not pin that stored rows populate `"id"` alongside `"request_id"` (needed by legacy `rights_status` row consumers) or that module-level `record_rights_request`, `log_rights_action`, and `answer_rights_request` accept a `RightsRequestLedger`, `Store`/`SqlStore`, or file path directly.
* Impact: Store-backed rights requests fail durability on Zava Forward's SQLite/Azure SQL store (`SqlStore`), risk silent in-memory detachment on `_sync()`, and risk non-atomic SQL audit commits or personal-identifier leakage into `audit`.
* Smallest useful change: Add `src/core/src/zava_forward/core/sqlstore.py` to `P01` / `P01-T03` targets solely to add `"rights_requests"` to `SqlStore.DOCS` and `SqlStore.MERGE_PRESERVED_DOCS` (reusing the existing `meta` table with zero new SQL DDL, matching `aftercare_store.py`), include `sqlstore.py` in `P03` `ruff check`, specify in `P01-T03` that `RightsRequestLedger` always reads/writes `store.data["rights_requests"]` dynamically inside `with store.lock:` without caching the list in `__init__`, orders `audit` before `save` when `hasattr(store, "db")` (and `save` before `audit` otherwise), omits raw `subject_key` from `store.audit` detail strings, stores `"id"` (and `"request_id"`) on every request dict, accepts `RightsRequestLedger | Store | str | os.PathLike[str]` in `record_rights_request` / `log_rights_action` / `answer_rights_request`, and tests reopen persistence on both `Store` and `SqlStore` (imported dynamically as `Any` under `mypy --strict`) in `P02-T01`.
* Action owner: planning parent
* Exact resolving evidence: Updated `P01`, `P01-T03`, `P02-T01`, and `P03` in .copilot-tracking/plans/2026-11-15/data-protection-controls-121-plan.md and .copilot-tracking/details/2026-11-15/data-protection-controls-121-phase-details.md incorporating `SqlStore.DOCS` / `MERGE_PRESERVED_DOCS`, lock-scoped read/write, atomic `audit`/`save` ordering, `subject_key`-free audit details, and `SqlStore` reopen unit testing.
* Decision route: planner-direct

### PC-002 [High]: Task-necessity and field/length/special-category gates in model_dispatch and validate_task_payload leave concrete bypasses when user_permission_granted=True

* Related IDs: Objective 2, FR-2, NFR-1, P01-T02, P02-T01; research C2, C15
* Evidence: src/core/src/zava_forward/core/data_protection.py:109-141, src/core/src/zava_forward/core/data_protection.py:384-404, src/core/src/zava_forward/core/data_protection.py:561-583, src/core/src/zava_forward/core/regulatory_privacy.py:213-227, src/core/src/zava_forward/core/regulatory_privacy.py:253-257, .copilot-tracking/details/2026-11-15/data-protection-controls-121-phase-details.md
* Concern: Caller Objective 2 requires enforcing in both `validate_task_payload` and `model_dispatch` that `user_permission_granted=True` alone never establishes task necessity or bypasses field/length/special-category/derivative checks, but `P01-T02` leaves four gaps: (1) `model_dispatch` has no optional `payload: Mapping[str, Any] | None = None` parameter, so `model_dispatch` cannot enforce field, type, length, or special-category checks on a supplied payload when `user_permission_granted=True`; (2) in `model_dispatch` (`data_protection.py:394-400`), `c.kind == "constructed"` returns `permitted=True` before any `task` check unless `P01-T02` explicitly places unknown-`task` and optional `payload` checks ahead of the `constructed` shortcut; (3) in `validate_task_payload`, `P01-T02` denies only when `payload` (excluding `"user_permission_granted"`) is non-empty and `kept` is empty, so an empty `{}` or `{"user_permission_granted": True}` payload returns `permitted=True` with `fields={}` (zero necessary task inputs); and (4) `validate_task_payload` (`data_protection.py:570`) evaluates `isinstance(value, kind) and len(value) <= limit`, which raises `TypeError` on `int` values and accepts `bool` for `int` (`isinstance(True, int)` is `True`), `"read_document"` is allowed via a hardcoded set union in `model_dispatch` without a `TASKS` manifest entry, and `SPECIAL_FIELDS` omits several UK GDPR Art. 9/10 field names already guarded in sibling `regulatory_privacy.SPECIAL_CATEGORY_FIELDS` (`adjustment`, `medical`, `biometric`, `genetic`, `sexual_orientation`, `trade_union`, `criminal`, `hardship`).
* Impact: Undeclared tasks on constructed fixtures, empty `{}` payloads with `user_permission_granted=True`, disallowed payloads passed to `model_dispatch`, or integer bounds in expanded `TASKS` manifests can bypass necessity validation or fail at runtime with `TypeError`.
* Smallest useful change: Revise `P01-T02` and `P02-T01` so that (1) `validate_task_payload` returns `permitted=False` whenever `not kept` (including `{}` and `{"user_permission_granted": True}`), validates `int` bounds with `type(value) is int and 0 <= value <= limit` and `str` bounds with `isinstance(value, str) and len(value) <= limit`, aligns `SPECIAL_FIELDS` with `regulatory_privacy.SPECIAL_CATEGORY_FIELDS` (retaining all 7 existing members), and includes `"read_document"` in `TASKS` alongside the 7 required whole-system tasks; and (2) `model_dispatch` accepts optional `payload: Mapping[str, Any] | None = None`, validates `task in TASKS` before the `c.kind == "constructed"` return, and when `payload is not None` runs `validate_task_payload` and denies dispatch (`permitted=False`) if `not checked["permitted"]` or any field appears in `rejected`, `dropped`, or `special_category_dropped`, regardless of `user_permission_granted=True`.
* Action owner: planning parent
* Exact resolving evidence: Updated `P01-T02` and `P02-T01` in .copilot-tracking/plans/2026-11-15/data-protection-controls-121-plan.md and .copilot-tracking/details/2026-11-15/data-protection-controls-121-phase-details.md specifying pre-`constructed` task validation, optional `payload` enforcement in `model_dispatch`, `not kept` denial and `int`/`bool`-safe checking in `validate_task_payload`, `"read_document"` manifest coverage in `TASKS`, and corresponding unit test cases.
* Decision route: planner-direct

### PC-003 [Medium]: Intact-attachment dispatch specification permits OR-fallback bypasses on invalid inputs, leaves policy flags conditional, and omits hold-wrapper forwarding

* Related IDs: Objective 3, FR-3, NFR-2, P01-T02, P02-T01; research C2, C3, C4, C15
* Evidence: src/core/src/zava_forward/core/data_protection.py:145, src/core/src/zava_forward/core/data_protection.py:172, src/core/src/zava_forward/core/data_protection.py:259, src/core/src/zava_forward/core/data_protection.py:405-558, .copilot-tracking/details/2026-11-15/data-protection-controls-121-phase-details.md
* Concern: Three attachment-gate edge cases in `P01-T02` weaken fail-closed behavior or contract consistency: (1) `P01-T02` says when `derivative != "reviewed_redacted"`, permit if `necessity_exception` validates OR `scoped_necessity_ref` validates; if a caller passes `derivative == "synthetic_safe"` (`CONSTRUCTED_DERIVATIVE`), an invalid/expired/case-mismatched `necessity_exception`, or `derivative == "reviewed_redacted"` with an invalid/automated reviewer pair while also passing `scoped_necessity_ref`, an `OR` fallback could rescue an invalid call instead of failing closed, and `SYNTH-` checks must be case-insensitive (`.upper().startswith("SYNTH-")`, matching `data_protection.py:259`); (2) `P01-T02` includes `user_permission_establishes_necessity=False` and `storage_approves_ai_dispatch=False` only "where applicable", risking `KeyError` on early-return branches (such as missing `DP_RAW_DOCUMENT_*_REF` env vars, unknown class, or non-model-bound class); and (3) `P01-T02` names `dispatch_hold` and `document_model_hold` as targets without specifying that they accept and forward the new optional keyword arguments (`user_permission_granted`, `storage_permission_granted`, `redaction_reviewer_id`, `redaction_review_id`, `scoped_necessity_ref`, plus `task` on `document_model_hold` defaulting to `"read_document"`).
* Impact: Contradictory or partially invalid attachment dispatch calls or lowercase `"synth-"` tokens could fail open, callers inspecting `storage_approves_ai_dispatch` on unconfigured-env denials could hit `KeyError`, and hold wrappers could not forward reviewer/scoped-necessity metadata.
* Smallest useful change: Specify in `P01-T02` that (1) `derivative == CONSTRUCTED_DERIVATIVE`, any invalid `reviewed_redacted` reviewer/review pair, or any non-`None` invalid `necessity_exception` fails closed immediately (`permitted=False`, `manual_path=MANUAL_PATH`) with no fallback to `scoped_necessity_ref`, and all `SYNTH-` checks use `.upper().startswith("SYNTH-")`; (2) every return dict from `model_dispatch` and `dispatch_attachment_to_model` unconditionally includes `user_permission_establishes_necessity=False` and `storage_approves_ai_dispatch=False` (treating `storage_permission_granted`, `upload_permitted`, and `download_permitted` alike as never approving AI dispatch); and (3) `dispatch_hold` and `document_model_hold` accept and forward those optional keyword arguments while preserving legacy 3-argument `read_document` behavior when omitted.
* Action owner: planning parent
* Exact resolving evidence: Updated `P01-T02` and `P02-T01` in .copilot-tracking/details/2026-11-15/data-protection-controls-121-phase-details.md documenting strict fail-closed precedence, case-insensitive `SYNTH-` matching, unconditional boolean policy keys across all dispatch return branches, and keyword forwarding in `dispatch_hold` and `document_model_hold`.
* Decision route: planner-direct
