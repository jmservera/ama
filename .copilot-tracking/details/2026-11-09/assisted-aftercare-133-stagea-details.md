## Service contract (`aftercare_intake.py`)

* `AftercareService(store: StateStore, *, homes=None, cohort=None, scenarios=None, now=None)`. `StateStore` has `read() -> str | None` and `update(mutator)`, an atomic read-modify-write: the mutator receives the current text and returns `(new_text, result)`; an exception leaves the stored text unchanged. `FileStateStore(path)` takes an exclusive lock file for the whole update and writes a temp file then `os.replace`. The service caches nothing, so stale instances cannot overwrite receipts (critique PC-01). The later shared store must provide the same atomic `update` under its own lock. A corrupt or invalid document raises `StateInvalid` and is never overwritten; a failed write raises `PersistenceError` with nothing changed.
* State document `zf-aftercare-intake/1`: `version`, `register` (`to_state()`), `receipts` by concern id (with the raw original statement and representative basis, because core strips them: PC-03), `requests` (request id to fingerprint and concern id), `actions` (time, actor name and role, action, concern id). Restore validates the whole document (PC-06): core `from_state`, every concern has exactly one receipt that equals its record (home, kind, raised by, channel, recorded by, owner, stripped statement and basis), fingerprints are recomputed from receipt originals, request ids point to existing concerns, types and counts are checked. Failure raises `StateInvalid`.
* Roles: record = `controls.RESIDENT_ROLES`; view, act, add context = `controls.RESIDENT_VIEW_ROLES`; assign owner, record closure = `workflows.MANAGER_ROLES`. Anything else, including a contractor, is `PermissionError`. No evaluator role is created.
* Owner: only a manager may name an owner at intake (PC-04), via `owner_role`, one of the view roles, stored as `"<role> (synthetic scenario owner)"`. Any other case, including `owner_role` sent by a non-manager (refused with a plain error), is stored as `"Unknown (no owner named)"` and the receipt says Unknown. Owner actions need the actor's role to equal the owner role and an owner that is not Unknown. `assign_owner` is manager-only and only from Unknown, and appends a history event.
* Intake values: `request_id` (8 to 64 of `A-Za-z0-9_-`), `raised_by`, `representative_basis`, `home_ref`, `kind`, `statement`, `channel` (core non-digital channels), `next_update` (ISO date, not before the received date), optional `owner_role`. The route is always `staff_recorded`; `recorded_by` is the acting staff name. All field errors are returned together, plain language. Every persisted free-text field (statement, basis, outcome evidence, remedy evidence) is refused with a synthetic-only message when `chat_privacy.redact` flags it, and is length capped (PC-02). This is a best-effort guard, not proof that no personal data is present; the synthetic-only notice, a home id from the stated synthetic set and the open DPO decision remain the controls. A home outside a stated synthetic set is refused.
* Receipt: `receipt_id`, `concern_id`, `received_at`, `recorded_by`, `channel`, `raised_by`, `representative_basis`, `home_ref`, `kind`, original `statement` verbatim, `owner` label and status, `next_update`, `investigation`, `what_happens_next`, `protection`, `accessible_route`, `synthetic_notice`. Replay of the same request id and payload returns the stored receipt with `replayed` true; the same id with different values is a conflict.
* Staff concern display joins owner, investigation, outcome, remedy, next update, overdue flag against the service date, closures for the home with a fixed note that closure changes nothing, sensor context labelled context only, and history.
* Joined view (PC-05): the handed-over cohort is the `cohort` parameter, defaulting to the scenario homes and labelled a synthetic handover cohort. Scenarios map by row `home_id`. Per cohort home: `baseline`, `early`, `late` means and deltas from `retrofit_comparison`, shown only when its status is SUFFICIENT and otherwise Unknown with no partial means; concerns, unresolved count and closures; `totals` with denominators; core `evaluator_view(cohort, baseline_homes)` embedded as `register_summary`, where baseline homes are those with a SUFFICIENT comparison; fixed Unknowns; neutral notice. A cohort home with no scenario has comparison Unknown. A concern is listed whatever the sensor comparison says, and concerns outside the cohort are counted, not hidden.
* `handle`: `GET /api/aftercare/form`, `POST /api/aftercare/concerns`, `GET /api/aftercare/concerns`, `GET /api/aftercare/concerns/{id}`, `POST .../investigation`, `.../outcome`, `.../remedy`, `.../owner`, `.../sensor-context`, `POST /api/aftercare/closures`, `GET /api/aftercare/evaluator`. Statuses 200, 201, 400 with `errors`, 403, 404, 405, 409, 503. Every payload has a plain `error` when not successful. Pack endpoints are not exposed.

## Tests (`test_aftercare_intake.py`)

Added from critique: concurrent submissions through two service instances on one file store keep every receipt; whitespace-preserving original after restart; manager-only initial owner (both routes); free-text redaction on evidence fields; restore corruption cases never overwrite; missing and out-of-scope cohort homes.

Role gate (allowed, contractor, application administrator, unknown); record happy path and receipt content; verbatim statement and channel provenance; representative basis required; all errors at once; unknown home; personal-detail refusal; idempotent replay and conflict; persistence round trip through a new service on the same file; failed save leaves nothing; corrupt state refused and not overwritten; Unknown owner cannot act; wrong role cannot act; owner can investigate, record outcome and remedy; closure does not change remedy and concern stays unresolved; normal sensor context never dismisses; joined view denominators and Unknowns with an insufficient comparison; templated text free of banned phrases; handle routing and status mapping; household view omits sensor context.
