\begin{abstract}
Each feature changes the starting point for the next. In agentic software
development, that starting point includes code, tests and the instructions
guiding later work. This paper examines how faults and corrective rules
accumulate in that inherited state. Maintenance literature and agent
benchmarks distinguish conversational errors from repository-carried failures.
A practitioner-led demonstrator supplies a motivating case: agent-assisted
research, business and product requirements, architecture decisions,
Design Thinking critique and disposable prototypes informed epics and user
stories. Despite preparation intended to improve delivery speed and quality,
extended autonomous work left the replacement unusable for the participant
and prompted renewed feedback and refactoring. Five candidate mechanisms
organise this transition: specification inflation, proxy capture, learning
evaporation, process-gate inflation and feedback starvation. Migration and
deployment dependencies remain central to the observed failure.
A prospective protocol specifies 495 trajectories across three selected
models and five arms: feature-only delivery, scheduled consolidation,
read-only review, matched-resource delivery and visible regression repair.
The outcomes are final behavioural coverage, retained-contract loss,
an unforeseen change request and resource cost. The design targets a
ten-percentage-point coverage gain under an explicit variance assumption;
consolidation combines structural work, additional tests and a revised
handover. Source freeze, prospective registration, affordability and collection
authorization remain gates. The study asks whether consolidation improves
the system inherited by later feature work.
\end{abstract}

\section{Introduction}\label{sec:intro}

On 1~August 2012, Knight Capital's automated router sent more than four
million orders while attempting to fill 212 customer orders. The firm lost
more than USD~460 million. The SEC traced the incident to a defective
function left in the router after a 2005 change, an incorrect deployment for
a new trading programme, and inadequate controls. The new deployment
activated old code that was no longer meant to run~\cite{sec2013knight}.
The failure crossed a feature boundary and a seven-year interval: the
relevant starting point was the accumulated system, not just the latest patch.

Less spectacular versions of the same maintenance problem are familiar.
Cunningham's 1992 account of WyCash described a financial product continually
adapted to market demands. Its mature code was repeatedly revised and
rewritten; the technical-debt metaphor explained why shipping a
first-time implementation required later rewriting as understanding
improved~\cite{cunningham1992wycash}.
Some debt is visible as duplication or awkward dependencies. Some remains
hidden in assumptions about inputs, deployment and earlier behaviour until
another change depends on it. Counting completed changes reveals neither.

Agentic development makes this distinction newly pressing. PhotoCraft, an
early-alpha reimplementation of Photoshop, reports 631 of 631 menu items
live, but explicitly defines that count as dispatch rather than behaviour.
Its own dated assessment estimates about 76\% feature breadth and 45\%
readiness for real work~\cite{photocraft2026}. A command can be reachable
without the surrounding workflow being dependable. At the repository level,
SWE-Maintain finds that agents solve fewer later tasks when starting from
their own earlier changes than from the developers' changes, even though
each task starts in a fresh session~\cite{pan2026swemaintain}.
The next session can forget the conversation and still inherit its mistakes.

The engineering response has a long history: isolation and explicit contracts
limit dependencies; tests and continuous integration expose regressions;
small releases shorten feedback; refactoring preserves room for later
change~\cite{parnas1994aging,beck2002tdd,beck2004xp,fowler2007stamina}.
Recent discussions by Beck, Martin and Fowler revisit these concerns for
agent-assisted work~\cite{beck2026prodacity,martin2026productengineers,fowler2025thoughts}. Beck's
distinction between producing code and learning through working software
sharpens the research question~\cite{beck2026prodacity,orosz2025beck}:
what does a feature leave behind for the next one?

The question arose in an architectural demonstrator developed by one
practitioner with multiple agents. Research documents, business and product
requirements and architecture decisions were built through sustained
conversation, challenge and owner decisions. Design Thinking methods,
including what-if scenarios, persona analysis and journey mapping, helped
question the proposed solution; disposable pilots and prototypes exposed
workflow problems before a usable MVP emerged. A backlog agent then converted
that accumulated context into epics and user stories for a delivery coordinator.
The intended advantage was faster implementation of better-understood
features, supported by explicit acceptance criteria and review.

Extended autonomous sessions nevertheless left the replacement unusable for
the participant. Renewed product-use feedback redirected implementation and
refactoring. This sequence motivates investigating how preparation and local
completion checks translate into the behaviour inherited by later work.
The repository, pull requests, append-only log and versioned coordinator
instructions retain the evolving delivery record~\cite{servera2026ama};
the source package pins the evidence used here. The repository may be
temporarily unavailable during the experiment embargo, after which the
approved history and context are intended for release.
The author's earlier
experience with Aithena, a book-search project with PDF ingestion and
a browser interface discussed separately in the supplement, and the PhotoCraft
inspection selected after the motivating-case analysis have separate provenance in
the ancillary \nolinkurl{anc/supplementary-context.md}.

The working hypothesis is that feature-driven delivery can carry unresolved
errors and avoidable change burden forward unless it includes cumulative
verification and consolidation. Two kinds of state matter: the software
being changed, and the instructions used to change it. Adding a corrective
rule after every failure can leave prompts, skills and handover notes with
their own maintenance burden. A fresh agent inherits both kinds of state.
Section~\ref{sec:background} distinguishes these pathways; the case then
examines how they interact with completion proxies, review capacity and
product-use feedback.

Here \emph{feature-driven decay} describes loss of retained behaviour or
increasing change burden across feature steps. Whether feature-driven decay
occurs remains a question for the prospective study.

Three questions guide the investigation:

\begin{itemize}[leftmargin=*]
\item \textbf{RQ1.} Through which retained state can errors and change
burden carry from one feature to the next, and what does existing evidence
show about those pathways?
\item \textbf{RQ2.} How does an exploratory delivery record illuminate that problem,
and which candidate mechanisms and rival explanations does the gap between
completion signals and usable replacement behaviour suggest?
\item \textbf{RQ3.} Does scheduled agent-led consolidation after each feature
improve retained behaviour and future changeability, and at what cost?
\end{itemize}

\noindent The report makes three linked contributions:

\begin{enumerate}[leftmargin=*]
\item A focused synthesis distinguishing conversational self-conditioning,
repository-carried faults and instruction maintenance, with a replot of
published paired-history data (Section~\ref{sec:background}).
\item An exploratory account of the transition from agent-assisted discovery
and challenged requirements to coordinated feature delivery and corrective
product feedback. Five candidate mechanisms and within-case contrasts connect
the interruption of usability to competing explanations
(Sections~\ref{sec:method}--\ref{sec:mechanisms}).
\item A consolidation harness and a prospectively sized five-arm protocol to
estimate retained behaviour, future changeability and resource cost. It follows the
registered-report example of Lulla et~al.~\cite{lulla2026protocol} and HVE
Core's Minimum Viable Experiment method
(Sections~\ref{sec:harness} and~\ref{sec:experiment}).
\end{enumerate}

The case concerns a migration and a configuration designed by the author, including
delegated delivery and merge decisions. The case suggests hypotheses whose
causal relationships remain to be tested. The planned pilot estimates a
multi-component, extra-resource package comparison; it does not isolate
refactoring or validate the five
case mechanisms individually. Registration and launch checks precede
collection. The case's validity and the pilot's
identification limits are consolidated in Sections~\ref{sec:threats}
and~\ref{sec:protocollimits}.

\section{Case and method}\label{sec:method}

\subsection{Setting}

The motivating project was an architectural training exercise developed by
one practitioner acting as architect, developer and product owner.
Its synthetic, multi-role service workflow combined documentary evidence,
approvals, identity, data and external-service dependencies. The exercise
required research, requirements, architecture, a delivery plan and a working
demonstrator. These interdependencies made preservation of a complete user
journey consequential even in a non-production system. No operational
service or real resident data is evaluated here.

Agents performed most research synthesis, drafting and coding, with the
practitioner steering scope and decisions. Several weeks of discovery and
requirements work preceded roughly a week of interactive MVP development
and a ten-day autonomous delivery window. The project continued afterward;
its current state and detailed chronology belong to the versioned repository
record~\cite{servera2026ama}. An automated repository scorer supplied an
additional completion signal. Internal assessment wording is not reproduced.

\subsection{Workflow and tools}

GitHub Copilot and HVE Core supported a sequence of connected activities:

\begin{itemize}[leftmargin=*]
\item Research agents assembled a knowledge base of source snapshots,
maintained syntheses, an index, owner-curated memory and an append-only log.
\item The Design Thinking coach and stakeholder-role agents challenged
assumptions through what-if scenarios, persona analysis and journey mapping.
Their critiques separated bounded AI tasks from deterministic controls and
accountable human decisions. Role-agent answers were hypotheses for the
exercise; direct stakeholder research remained a separate requirement.
\item BRD and PRD builders, quality review and the ADR assistant turned
successive discussions and owner decisions into revised requirements and
architecture records. These documents changed as understanding developed.
\item Disposable pilots and prototypes tested candidate workflows. Their
critiques and participant feedback informed a deployed MVP that the author
used intermittently and refined through short feedback loops.
\item A backlog agent converted the accumulated context into epics, features
and user stories, with acceptance criteria, dependencies and indications of
existing MVP coverage. Some stories also exposed scope needing subsequent
requirements reconciliation.
\item A custom coordinator then dispatched implementation and review work
against that backlog (Section~\ref{sec:coordinator}).
\end{itemize}

The intended benefit was accelerated planning and better-grounded feature
delivery. Neither a human-only comparator nor a measured speed or quality
gain was available. The retained documents and conversations matter because
they shaped what workers were asked to build and reviewers were asked to
accept.

\subsection{The coordinator}\label{sec:coordinator}

The coordinator ran through Copilot CLI on a VM. It selected dependency-ready
issues and launched parallel worker sessions in isolated git worktrees.
Each worker received an issue and HVE Core's research, plan, implement and
review (RPI) workflow. The coordinator checked the resulting pull request,
updated the project board and, under owner delegation, merged changes.
Interactive and CLI model configurations changed during the project;
recorded selectors and recalled interface labels are distinguished in the
source package. The delivery record is consequently an evolving workflow.
% TODO(author): recover historical CLI versions, reviewer models and actual session/provider build identifiers where retained records expose them; distinguish records from author recollection.

Early worker sessions implemented directly, prompting the author to make
the full RPI sequence and committed tracking artefacts mandatory. Further
instructions required evidence-backed acceptance ticks, scheduled monitoring
and increasingly comprehensive local gates. Human decisions, approvals,
credentials and unresolved review findings could still block work. At the
same transition, an accepted architecture decision prioritised migration
to a new source layout and froze feature work in the MVP. Coordination,
migration and procedural requirements therefore changed together.

\subsection{Data and analysis}

This exploratory single-case study follows the transition from interactive
discovery and MVP use to backlog-mediated autonomous delivery. The author
selected the case after encountering the unusable replacement and acts as
participant-observer. Case-study guidance and the ACM SIGSOFT Empirical
Standards inform the account~\cite{runeson2009guidelines,sigsoft2021standards}.

The original analysis pins repository commit \texttt{29c6b51}; a separately
pinned follow-up uses \texttt{9b74ac8d}. Sources include the knowledge-base
log and index, requirements, architecture decisions, coordinator definition,
issues, pull requests and retained RPI records. The author's review adds
process clarification and an export of project issue states, retained as
\nolinkurl{anc/project-insights-2026-11-01.csv}. Source dates, historical
counts and extraction rules remain in the ancillary records. The main
account uses them to reconstruct the sequence and handoffs.

Analysis combined descriptive measures, reference tracing of recorded
lessons and AI-assisted interpretation of selected episodes. It did not
include systematic entry-by-entry coding. Early log entries were
reconstructed from history; later entries are contemporaneous project
accounts. Specification review was selective. Participant recollection,
committed source and execution evidence remain distinct, including in the

External repositories and literature were selected for relevance to
inherited faults, instruction maintenance and outcome verification.
They supply contextual comparisons and a focused narrative synthesis.
The published-evidence figures reproduce reported values with source
locators; the external applications and original studies were not rerun.
The ancillary observation record preserves its purposive issue sample,
exclusions and retrieval boundaries. These sources are analysed separately
from the motivating project.

\subsection{Constructs and evidential boundaries}\label{sec:constructs}

Here an \emph{agent} is a configured model--tool--instruction loop that
selects and executes actions, not the model alone or an independently
accountable person. A \emph{skill} is a reusable procedural resource describing
when and how to act and verify the outcome, distinct from an execution
history or a model-weight update. This procedural distinction follows
Jiang et~al.~\cite[Sec.~1]{jiang2026skills}; the pilot's handover note is
retained context, not a separately manipulated skill treatment.

\emph{Working behaviour} means completing an intended task through the
running system, including the identity, data and service dependencies needed
for that task. A healthy endpoint or a passing repository test alone does not
establish it. \emph{Decay} denotes loss of previously working behaviour or
increasing difficulty of understanding and changing a system. The case
records lost usability during replacement; any decline in intrinsic code
quality remains unmeasured. Deployment drift could produce the same observation.
\emph{Adaptability} is operationalised prospectively as success and cost on
the fixed-budget, unforeseen change request, not as a universal measure of
maintainability. \emph{Consolidation} means scheduled structural work intended
to preserve observable behaviour, with tests checking that intention; passing
finite tests cannot prove semantic equivalence.

Five measurement categories remain separate. PRs, lines and words describe
\emph{production volume}; checks, reviews and receipts describe
\emph{validation activity}; observed user tasks describe \emph{system
behaviour}; code metrics and the change request probe \emph{internal quality
and changeability}; and corrective help requested or supplied describes
\emph{intervention}. The original observations cover the first three.
A later post-hoc comparison adds structural proxies, not a controlled
changeability task or systematically coded intervention dataset. Neither volume nor validation
activity is used as a direct estimate of decay.

\subsection{From discovery to epics and user stories}

Preparation involved sustained steering rather than a single specification
prompt. Role-agent challenges questioned the requested end-to-end agents;
what-if scenarios tested alternative inputs and responsibilities. Persona
and journey work exposed handoffs, missing information and approval boundaries.
The resulting BRDs, PRDs and ADRs were critiqued and revised through further
conversation. These activities changed the proposed solution before and
during implementation.

Disposable prototypes then made some assumptions tangible. Participant
critique and an agent-assisted simplicity review produced requirements for
clear ownership, a visible next action, understandable blockers and manual
paths that remained usable without AI. Short feedback cycles reshaped an
MVP around those lessons. The author reports using it intermittently,
including sign-in, synthetic data and model-backed assistant paths.

The backlog manager drew on this accumulated context to generate the work
hierarchy, acceptance criteria and dependencies. Existing-coverage labels
distinguished proposed work from functionality already present in the MVP.
The supplied project export records a batch expansion around this handoff,
followed by movement into completed states. It provides a trace of work
organisation; accepted user journeys require their own evidence.
Requirements reconciliation continued afterward, including for scope first
surfaced in backlog stories. Thus preparation and delivery overlapped, and
the issue hierarchy remained an evolving interpretation of the design.

\subsection{Local completion and the usable workflow}

Autonomous delivery changed the feedback path. The coordinator selected
issues and workers satisfied local implementation and review obligations.
At the same time, a source-layout migration replaced the used MVP. The
replacement passed bounded engineering checks, including health, restart
and unauthenticated-request rejection, but lacked identity, staff and model
prerequisites needed for the participant's complete workflow. Restoring a
public entry point left sign-in dependencies unresolved.

The author continued supplying approvals and resolving technical blockers.
What diminished was the ability to exercise realistic work in the
replacement and use that experience to steer the next change. Missing
prerequisites became further issues, each with research, planning, review
and correction work. Scope additions and validation costs also changed
delivery conditions. These observations locate a concrete interruption of
usable behaviour within a broader process of accumulating obligations.
The automated score and failed journey still need release-and-scope linkage
before their disagreement can be assessed as a matched comparison.

\subsection{Renewed feedback and follow-up}\label{sec:currentstatus}

The participant requested a usable increment, prioritised feedback-first
work and asked the coordinator to pause, exercise the accumulated
functionality and refactor. The participant's account places this renewed
feedback at the turning point in making the replacement useful. Subsequent
source history records implementation refinement and recurring stabilization
checkpoints. The retained checkpoint review qualifies its local engineering
evidence and leaves live acceptance separate.

This follow-up matters because the project was steered through interaction:
the backlog and the worker instructions did not settle the product outcome
once and for all. A dated, release-linked journey is still needed to measure
time to restored usability. The original observation window and the later
repository snapshots remain distinct. The repository supplies the evolving
history; the ancillary records preserve the exact observations used here,
including changing issue totals, document volume, lexical counts and static
source metrics. Those records support reconstruction while the prospective
experiment supplies a separate test of retained behaviour and changeability.

They occupy different points in the delivery process (Table~\ref{tab:theory}).
Specification growth increases the obligations and interactions that later
work must preserve. Learning evaporation concerns the path by which a
relevant lesson reaches the next session. Proxy capture concerns what selects
and approves work; process-gate inflation and feedback starvation concern
the capacity to detect and correct cumulative problems. None needs to be
called error propagation to explain how an inherited fault can survive.

Before the participant's checkpoint request, the loop had no scheduled
cumulative consolidation step.
Its large restructuring, the source-layout migration, was planned as backlog
items; local refactoring could still occur within individual issues.
The experiment separates retained-contract loss, structural fidelity
diagnostics and later adaptation. Formal fault-lineage
annotation would address the stronger question of whether an earlier fault
generates distinct later failures; it is deferred rather than added to the
pilot's workload.

\subsection{Case validity and rival explanations}\label{sec:threats}

The five categories are not independent causes identified by these data.
The same missing identity and staff bindings can indicate deferred migration
work, incomplete deployment acceptance or a lost lesson. Discriminating them
requires the deployment comparison and actual session-input trace identified
in Table~\ref{tab:audittrail}, not another count of documents or citations.
Similarly, a growing read path does not demonstrate context overflow, and an
expensive gate is not necessarily a disproportionate gate. Per-change gate
time, avoided defects and human effort were not measured.

The source-layout migration, owner-selected priorities and delegated merging
changed alongside coordination. Scope additions, budget constraints, model/tool
changes and deployment conditions also differ between periods. These are
direct rivals to an autonomy-only account. The
\hyperref[sec:supplement]{supplementary rival-explanation register} retains the full
register, separating recorded circumstances from plausible but untested
alternatives. Bird et~al.'s study of co-installed applications on Windows
machines supplies a methodological analogy for checking environmental
influences on reliability~\cite{bird2014extrinsic}. It neither tests
AI-agent configuration nor diagnoses this case's sign-in failure.

Construct validity is limited by whitespace counts, lexical indicators and
selectively reviewed records. Appropriate caution can raise boundary-phrase density;
missing references do not prove missing knowledge. As coordinator designer,
participant and analyst, the author selected the episodes and may favour a coherent
retrospective explanation. AI synthesis is not an independent observer.
Public records support recomputation but not independent corroboration of
every statement. The single practitioner-designed exercise and purposively selected
external examples do not establish prevalence or general causal effects.
The proposed experiment has separate identification limits in
Section~\ref{sec:protocollimits}.

\section{Consolidation hypothesis and harness}\label{sec:harness}

The observed operational failure and the prospective hypothesis are distinct.
Missing deployment identity and staff bindings are concrete obstacles to
sign-in; structural code consolidation would not necessarily restore either.
Recovery of that journey requires configuration and end-to-end verification.
Consolidation is worth testing for a different reason: repeated feature work
may make later changes harder, even when deployment dependencies are correct.
The experiment probes that possibility through retained tests and CR1; it
does not claim that consolidation would have prevented this episode.

The idea is already practised. OpenAI describes replacing weekly manual
clean-ups with recurring background agents that open small refactoring pull
requests, alongside a documentation-gardening agent~\cite{openai2026harness}.
Anthropic asks each session to leave a clean state and update a progress
file~\cite{anthropic2025harness}. Neither account reports a controlled
comparison of feature-only delivery with consolidation between feature steps.
Darwin's continuous optimisation is a further precedent for automated
improvement, but its performance evaluations do not isolate that intervention
or test an unforeseen change request~\cite{pavlenko2026factory}
(Section~\ref{sec:factory}). RefactorBench already evaluates refactoring
agents~\cite{gautam2025refactorbench}; the narrower hypothesis concerns retained
behaviour and later adaptation during repeated feature additions.

AutoSaddler's preprint abstract already treats harness improvement as
offline learning from execution traces, combining failure diagnosis,
structured patches and validation-based update
selection~\cite{microsoft2026autosaddler}. Agent-led reflective correction is
therefore not the novelty claimed here. The proposed intervention instead
consolidates the retained repository between feature steps and measures
retained contracts and a withheld change request.

The proposed consolidation harness tests a bounded part of reflective
correction. The distinction is what persists afterward. Self-Refine revises
an output and Reflexion retains lessons for later trials
~\cite{madaan2023selfrefine,shinn2023reflexion}; the present intervention
instead consolidates the software and its handover between different
feature requests. CRITIC's tool feedback is another precedent
~\cite{gou2024critic}, but it does not authorize feeding the held-out
evaluation into this experiment. Whether the retained changes help an
unforeseen request remains the empirical question. The harness schedules
each pause; the agent is not authorised to reject features or redirect
the product.
After every feature the loop stops, and an agent:
\begin{enumerate}[leftmargin=*]
\item runs the tests and a metrics script that lists complexity hotspots,
duplicated blocks and lint warnings;
\item reviews the last feature's diff and the hotspots against a short
checklist (duplication, long or complex functions, unclear names, dead code,
rules from one feature leaking into another, tests that check implementation
rather than behaviour);
\item refactors in small, behaviour-preserving steps, each applied through
\texttt{test \&\& commit || revert}~\cite{beck2018tcr}, so that every change
either keeps all tests green or disappears;
\item may add tests that pin current behaviour, but may not change or delete
the example tests that define the features;
\item rewrites a design note of at most 300 words that says where each rule
lives and what debt remains, replacing the previous one rather than
appending to it;
\item stops when a quality budget is met or its time budget runs out.
\end{enumerate}
Only then may the next feature start. The supplement reproduces the
historical v4 prompt; the current researcher kit defines the amended
prompt. The intervention combines refactoring, additional tests and a
design-oriented note; it is not a pure refactoring treatment.

The hypothesis draws on Beck's alternation of features and
futures~\cite{beck2026prodacity,beck2025devslow} and \emph{Tidy
First?}~\cite{beck2023tidy}. It is not free, and may not work. Agent
refactorings can be incomplete or incorrect~\cite{gautam2025refactorbench};
human studies also caution against equating a refactoring label with a
quality gain. Kim et~al. report developers' refactoring challenges and
benefits~\cite{kim2014refactoring}; Bavota et~al. find that observed
refactorings do not consistently target or remove code
smells~\cite{bavota2015quality}. These findings motivate checking outcomes
rather than assuming improvement. Test-commit-or-revert
protects only behaviour represented by its tests, not every intended
contract~\cite{ma2026building}. Section~\ref{sec:experiment} specifies how
the package will be evaluated.

\section{Discussion}\label{sec:discussion}

\subsection{Projected cost of omitting consolidation}\label{sec:costprojection}

The experiment measures costs over ten features and one final change. It
does not yet estimate the price of maintaining a larger system without
refactoring. Figure~\ref{fig:refactoringeconomics} and
Table~\ref{tab:costscenario} therefore give an explanatory sensitivity
scenario, not results, an empirical forecast or an addition to the frozen
analysis. The economic hypothesis is that early investment can reduce the
implementation and repair burden inherited by later features. It can fail:
refactoring may consume credits without reducing that burden or may damage
behaviour. Cost must always be read beside coverage, retention and adaptation.

Let $N\geq1$ be an integer number of feature cycles, $k$ the assumed average consolidation
investment in AI credits per cycle, and $\delta\cdot(t-1)$ the assumed excess
feature-implementation cost in A relative to B at cycle $t$, excluding
B's consolidation session. Shared baseline implementation costs cancel.
Under the explicit simplifying assumptions of constant $k$, a linearly
growing relative premium $\delta\geq0$, and comparable delivered behaviour,
the cumulative net difference is
\begin{equation}
\Delta C(N)=C_A(N)-C_B(N)
=\sum_{t=1}^{N}\bigl[\delta(t-1)-k\bigr]
=\delta\frac{N(N-1)}{2}-kN.
\label{eq:costprojection}
\end{equation}
The first term is the assumed gross avoidable burden of omitting
consolidation; the second is the investment to avoid it. A positive
difference means A costs more under these assumptions, not measured savings.
For $k>0$ and $\delta>0$, the first cycle count with $\Delta C(N)\geq0$ is
$N_{\mathrm{BE}}=\lceil1+2k/\delta\rceil$; when $\delta=0$, the investment never pays back in
this credit-only model. Real trajectories need not follow a linear premium,
and B can retain debt too: $\delta$ is a relative gap, not A's absolute
debt or a claim that B is debt-free.

\begin{figure}[!htbp]
\centering
\includegraphics[width=\linewidth]{fig-refactoring-economics.png}
\caption{Assumed cost-of-inaction mechanism and break-even sensitivity, not
pilot results or an empirical projection. A linearly increasing relative
implementation premium accumulates across feature boundaries; recurring
consolidation has an explicit cost. Payback depends on $k/\delta$: a ratio of 5 breaks even at 11 cycles
and a ratio of 100 at 201; $\delta=0$ gives no payback for $k>0$.
Parameters are invented for transparent sensitivity,
not fitted to study data. No dollar conversion or human-work estimate is
implied.}\label{fig:refactoringeconomics}
\end{figure}

The study can report actual B consolidation consumption and all-attempt
CR1 cost by model. Calibration can anchor $k$ once billed spend exists.
Because feature budgets are capped, harder work can instead reduce coverage:
$\delta$ is an uncapped, quality-matched counterfactual, not a directly
identified endpoint of this design. Even the enlarged replication over
ten features does not identify a stable long-run $\delta$ or justify extrapolation
to 40 features. A future forecast would require longer replicated sequences,
matched delivered quality, measured residual repair work and independently
checked billing. Human review, operational failures, opportunity costs and
currency prices are not measured by this kit and cannot be monetized from
its credits or code-size proxies. Thus the current projected cost of
inaction is conditional and unestimated, not a claimed business saving.
For comparison, assumed $k=100$ and $\delta=1$ yield break-even at 201
cycles, not eleven. No observed consolidation spend supports a preferred
$k$ yet.

\subsection{What worked}

Agents contributed useful challenge and rapid iteration. The research phase
assembled a corpus and analysis in days; a human-only
duration was not measured. The role agents' challenge
killed a bad idea, five end-to-end agents, before any code was written. The
agents refused to invent approvals, figures or company facts, and recorded
the limits of their evidence. The MVP was built and reshaped in a day. These
episodes included targeted human challenge and feedback; they are not a
controlled comparison with human-only teams or proof that all short loops
succeed.

\subsection{Human judgement and reflective work}

The participant supplied several kinds of reflective
work: choosing what not to build, recognising the unusable replacement and
deciding which earlier lessons mattered. Naur's theory-building account
helps describe that retained understanding~\cite{naur1985theory}.
Beck's distinction between visible output and understanding supplies another
framing~\cite{beck2026mathematicians}. These judgements were supplied by the author
during the case. Whether agents could make comparable judgements remains
open. The narrower
experimental question is whether bounded post-feature correction preserves
behaviour and later changeability.

Human sign-off also need not establish who formed a judgment. In Anthropic's
randomised study, 61 analysts were recruited and 50 used the agent. Those
50 analysts matched their agent's
randomly assigned preference on 86\% of four analytical choices
\cite[Study design; Results]{herdagdelen2026judgment}. The preferences were
deliberately strengthened in one farming-analysis task with one model; the
rate concerns a different task and setting from coding
\cite[Our study's limitations]{herdagdelen2026judgment}.
This challenges an assumption that retaining approval alone preserves
independent judgment, not the case's reported decisions. The article proposes
asking experts for their view first or making the best case for each option
\cite[What this means]{herdagdelen2026judgment}. Separately, recording alternatives
and a human's reasons before accepting an agent's recommendation is the
present author's proposed safeguard, not a remedy evaluated in that study.

\subsection{Can another agent restore futures?}

Beck's alternation suggests preserving the options consumed by feature
execution~\cite{beck2026prodacity,beck2025devslow}. Darwin, AutoSaddler and
SkillOpt already provide precedents for agent-guided correction; reflection
itself is not the proposed novelty. Ng's reflection framework also argues
for evaluating and revising work rather than treating first-pass generation
as the finished product~\cite{ng2024reflection}. Improvement here means
a measured advantage in retained behaviour or later adaptation, not merely
writing a lesson, changing a prompt or calling the process self-improving.
The experiment does not train model weights; the evolving repository and
handover are the states under test. An exposed model name is not a guarantee
against provider-side changes.

The memory presentation's proposed ``dreaming'' pass is a useful contrast:
it curates prior transcripts into persistent context
~\cite{beamnxw2026memorytalk}, whereas this study changes retained code,
tests and the handover. Memory updates can carry an incorrect lesson forward
just as code updates can retain a defect. A self-improvement label therefore
cannot replace the retention and adaptation measures. The study asks what
remains after a fixed repository-consolidation step, with CR1 as one
future-change probe. It does not test choosing when to interrupt delivery,
changing product goals or restoring a deployment. Those questions, and
matched human/agent steering, belong to the separate research agenda in the
ancillary supplement.

\subsection{Implications for practice}\label{sec:feedbackfirst}

The case motivates protecting a usable increment, bounding the delivery horizon
and keeping lessons retrievable or executable. The ancillary supplement
retains the proposed practice checklist and framework-builder suggestions.
For future product integrations, routine intermediate tracking files should
stay out of the squash-merged product diff once durable findings and original
review evidence have been preserved. This is a proposed practice, motivated
by the large intermediate evidence trails retained in this case.
It is not permission to wipe an active or historical tracking tree:
selection must be finite, archive-backed and restore-verified, with adverse
reviews retained. Proportionality never overrides mandatory safety, privacy,
approval or publication gates, and compact context views must retain their
source evidence.
The pilot does not test that practice package, an optimal human-intervention
cadence or the preservation of expertise. Those remain separate questions.

\section{Conclusion}\label{sec:conclusion}

The unit of progress in cumulative development is the system left for the
next change. Knight Capital shows how a new deployment can activate an old
fault. WyCash makes consolidation part of continued growth. Agent research
adds a direct cross-feature test: in SWE-Maintain, earlier changes affect
later tasks even when conversation history is discarded. Its clean-history
results make preserving behaviour a more precise target than treating all
agent-written code as structurally deficient.

The instructions governing development need maintenance too. Repository
studies show repeated additions and revisions, alongside pruning; controlled
context-file comparisons show that more guidance can increase work without
improving task resolution. Code, tests and instructions are all inherited
state, but they require different measures of correctness and burden.

The motivating case traces a fuller process: agent-assisted research and
challenge shaped requirements, prototypes and a hierarchical backlog;
autonomous issue delivery then failed to preserve the participant's usable
workflow. Renewed feedback, refinement and refactoring redirected subsequent
work. The five candidate mechanisms frame possible links among accumulated
obligations, lost lessons, completion proxies and insufficient product-use
feedback. Migration and deployment dependencies remain central to that
particular failure. The versioned repository retains the evolving record
and the distinction between local engineering evidence and accepted journeys
(Section~\ref{sec:currentstatus}).

The prospective five-arm study asks what scheduled consolidation leaves
for later work. It separates final behavioural coverage from retained-contract
loss, probes an unforeseen change and reports the resources consumed.
Secondary metrics provide descriptive evidence; testing the proposed mechanisms
would require further work.
A new freeze, prospective OSF recording and collection gates precede the
planned runs. The cost-of-inaction scenario makes the break-even
assumptions explicit.
What matters is whether the agents' combined work preserves the behaviour and
options needed by subsequent features.
