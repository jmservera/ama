\begin{abstract}
I spent weeks refining requirements with agents before asking a coordinator
to develop the product. After 47 completed issues in five days, checks
were passing, but I could not sign in.
What does each feature leave for the next one?
We tested three models across five arms with 21 runs per cell, each building
ten Python features before a withheld change request, with hidden tests
after each step.
Earlier behaviour was largely preserved: one of 315 runs ended with an
open regression, and workflow replay found no witnessed losses in 626
evaluable packets, each representing one run at one endpoint.
Consolidation removed complexity hotspots, but its coverage gain over longer
sessions was 1.19 percentage points (conditional 95\% interval [0.10, 2.22]);
the controls left only a 3.04-point ceiling against the pre-specified
ten-point target.
The main failures concerned missing ranking features and permission
boundaries; read-only review completed the extension in 16/21 Gemini runs
versus 8/21 with consolidation, which used 1.84--2.25 times the delivery
credits of feature-only work in fully billed subsets.
Rollback and immutable accepted tests plausibly helped prevent decay while
also obstructing a later feature, but no arm tested their absence.
Unregistered amendments, uncertain run independence, incomplete billing and
judging, and two unknown extension outcomes limit this single-task study.
Structural cleanup improved the measured code properties without
demonstrating cheaper adaptation.
\end{abstract}

\noindent\textbf{Keywords:} agentic software engineering; coding agents;
spec-driven development; software evolution; technical debt; refactoring;
feedback loops; human-AI interaction; exploratory case study; experiment protocol.

\section{Introduction}\label{sec:intro}

I was developing a product from a supplied housing-retrofit use case:
helping staff coordinate energy-efficiency work on residents' homes.
\footnote{``I'' identifies Servera Bondroit's participant account; ``we''
identifies the authors' experiment, analysis and paper.}
I used the HyperVelocity methodology to move an early prototype towards
production readiness while leaving out some non-essential production
requirements, expecting to keep the behaviour that already worked.
Short exchanges with agents had produced a prototype and a Minimum Viable
Experiment (MVE) in a few hours, including working sign-in. I used those
results to refine the business and product requirements documents (BRD and
PRD), then gave a coordinator and parallel workers a formal backlog to
implement autonomously. My account records 47 completed issues out of more
than 180 in the first 5 days. I could inspect completed issues and passing
checks, but when I opened the replacement to provide feedback, I could not
sign in to the new application.

The immediate problem was a blocked deployment and sign-in workflow,
but it raised a question about the accumulated system:
when a change passes its local checks, what evidence shows that the next
change inherits working software?

Inherited faults predate coding agents: the Knight Capital incident
combined old router code with an incomplete deployment and inadequate
controls~\cite{sec2013knight}, illustrating why local feature checks can
miss the state a deployment inherits.

Established engineering practice has a long answer to inherited faults:
define which behaviour a change must preserve, test it, and keep the
running increment available for feedback, allowing refactoring to change
the implementation while those contracts continue to hold
~\cite{parnas1994aging,beck2002tdd,beck2004xp,fowler2007stamina}.
Anthropic's long-running-agent example makes this concrete: before adding
a feature to a chat application, the next session starts the server,
opens a new chat, sends a message and checks for a response
~\cite[Getting up to speed]{anthropic2025harness}. That check asks whether the previous session left a usable application for the next change, a concern revisited by Beck and Fowler~\cite{beck2026prodacity,fowler2025thoughts}. Beck's distinction between producing code and learning through working
software sharpens the research question~\cite{beck2026prodacity}:
what does a feature leave behind for the next one?

Before asking the coordinator to implement the backlog, I had spent weeks
working through the requirements with the agents and recording our decisions.
Research agents maintained the evidence base, and in one what-if exercise, I asked whether phone photos with
GPS metadata would make an assessment agent more useful; the resulting
proposal still required checked provenance and a professional decision.
Persona and journey work examined who would take over a case when information or approval was missing.
Disposable pilots and prototypes exposed workflow problems before a usable minimum viable product (MVP)
emerged, and a backlog agent
translated the resulting requirements and architecture decisions into epics
and user stories.
I expected the agents to build the product faster and make fewer mistakes
because we had already questioned and revised the requirements.

My attempts to use the new application changed what I asked the coordinator
to do next: provide a running website, fix the missing workflow and refactor.
The case analysis follows those requests to see where preparation and local
completion checks failed to preserve the workflow I needed.
The public repository, pull requests, append-only log and versioned
coordinator instructions document that evolving record~\cite{servera2026ama};
the source package pins the evidence used here.
My earlier experience on another book-search project (Aithena, with PDF
ingestion and a browser interface, discussed in the supplement) and the
external PhotoCraft inspection selected after the motivating-case analysis
are documented as contextual comparisons in the Supplement.

The initial conjecture was that feature-driven delivery carries
unresolved errors and avoidable change burden forward, and that cumulative
verification and consolidation can reduce that burden. We distinguish
the software being changed from the instructions used to change it; in this case, my
instructions grew to require the full research, plan, implement and review
(RPI) sequence, committed evidence
and recurring checks (Section~\ref{sec:coordinator}). Section~\ref{sec:background} separates these
pathways; the case then examines how they interact with completion proxies,
review capacity and product-use feedback.

Stable behaviour would count against the conjecture under the tested conditions, while a single regression would provide little evidence of progressive decay. Here
\emph{feature-driven decay} means a measurable loss of previously passing
behaviour or a rising cost and failure burden across sequential changes.
The experiment asks agents to build the same small Python
package, called S1, through ten features and then complete a withheld
change request (CR1). The arms compare feature-only work (A), consolidation (B), read-only review (C), longer feature sessions (D) and visible-specification repair (E). A \emph{contract} is a required behaviour checked by a fixed hidden test, and the analysis distinguishes the \emph{decay premise} from
the \emph{consolidation remedy} through three predictions and a check of
whether consolidation actually changed the code.

\paragraph{P1 (Short-horizon decay premise).}
Without a dedicated
post-feature pause (Arms~A and~D), sequential delivery across ten features
induces progressive behavioural loss by the final feature checkpoint
($P_{10}$): previously passing contracts still fail, failures accumulate
across cycles, or replayed workflows lose earlier capabilities.

\paragraph{P2 (Primary coverage gain threshold).}
Scheduled consolidation (Arm~B) exceeds the matched-allowance longer-session control
(Arm~D) in equal-model-weight final hidden-test coverage at $P_{10}$ by at
least the pre-specified minimum useful effect of $\Delta_*=10$ percentage
points (Section~\ref{sec:protocollimits}).

\paragraph{P3 (Change-request adaptability and short-horizon payback).}
Consolidation (Arm~B) raises held-out CR1 success and reduces CR1 or net
credit expenditure relative to feature-only delivery (Arm~A), read-only
review (Arm~C) and longer sessions (Arm~D).

\paragraph{Manipulation check (Structural treatment fidelity).}
Consolidation reduces functions above cyclomatic complexity 10, duplication
and lint density towards its stopping targets, checking whether
the intervention changed structure before the behavioural
results are interpreted.

The results changed our interpretation: most acquired behaviour survived,
while structural cleanup produced a coverage gain below the practical
benchmark (Table~\ref{tab:predictionverdicts}), directing attention towards
missing features and failures exposed by a new requirement.

Only $\Delta_*=10$ percentage points was fixed in the pre-collection
planning calculation. The public execution manifest left its formal hypothesis
array empty, so the operational criteria in P1 and P3 structure the
post-collection evaluation and do not amount to a preregistered
confirmatory test.

Three questions guide the investigation:

\begin{itemize}[leftmargin=*]
\item \textbf{RQ1.} How can the code and instructions left by one feature
carry errors or make the next feature harder to implement, and what does
existing evidence show about that problem?
\item \textbf{RQ2.} What could explain the gap between completed issues and
an application I could use in the motivating case, and which competing
explanations does the delivery record support?
\item \textbf{RQ3.} Does scheduled agent-led consolidation after each feature
improve retained behaviour and future changeability, and at what cost?
\end{itemize}



The primary comparison measures consolidation, added tests and a handover
note against a control with matching time and nominal-credit ceilings;
the secondary feature-only comparison adds resources as well as
consolidation. The experiment neither isolates refactoring nor tests the
five case mechanisms individually; Section~\ref{sec:threats} consolidates
the limits of both studies.
Table~\ref{tab:source-register} and Data availability identify the source
register, public repositories and supporting records.

\section{Case and method}\label{sec:method}

\subsection{Setting}

For this architectural training exercise, I acted as architect, developer and product owner on a supplied housing-association retrofit use case; the application used synthetic cases to connect documentary evidence
and approvals with staff and resident actions. A staff member
needed to sign in, open an assigned case and record a resident decision
without replacing the staff decision to release work. An assistant could prepare a draft, but nothing was sent automatically; the exercise
required research, requirements, architecture, a delivery plan and a working
version of the product. No operational
service or real resident data is evaluated here.

Agents performed most research synthesis, drafting and coding while I steered scope and decisions, through several weeks of discovery and requirements work followed by roughly a week of interactive MVP development and a ten-day autonomous delivery window. The project continued afterward, with a versioned repository chronology~\cite{servera2026ama} and an automated scorer reporting implementation completeness
(Section~\ref{sec:audittrail}).

\subsection{Workflow and tools}

GitHub Copilot and HVE Core first helped me learn what to build.
Research agents assembled source snapshots and maintained syntheses
in a knowledge base with an index, owner-curated memory and an append-only
log; the Supplement's case evidence index gives their locators.
The Design Thinking coach and stakeholder-role agents then challenged
assumptions by asking what would happen under different conditions, examining
users' responsibilities and walking through their tasks.
For example, a photo's GPS metadata could support the location of a survey,
but did not establish whether the evidence was sufficient for a retrofit
assessment. The proposed assessor would check the evidence bundle and retain professional approval.
Role-agent answers stayed hypotheses for the
exercise; direct stakeholder research was still needed.

As understanding changed, BRD and PRD builders, quality review and the
architecture decision record (ADR)
assistant helped turn conversations and owner decisions into revised
requirements and architecture records. Disposable pilots and prototypes made candidate workflows tangible, and critiques together with my product-use feedback informed a deployed MVP that I used intermittently and refined
through short feedback loops. Its landing view was
\textquotedblleft{}My cases today\textquotedblright{};
case cards showed status and the next action, and a call log and manual
paths let work continue without a model response. These features are
recorded in the historical log and prototype review identified in the
case evidence index; my intermittent MVP use is a participant account.

The handoff to autonomous delivery changed how that understanding reached implementation: a backlog agent converted the accumulated context into
epics, features and user stories, including acceptance criteria, dependencies
and indications of existing MVP coverage. Some stories exposed scope that still needed requirements reconciliation.
A custom coordinator dispatched
implementation and review against this evolving backlog
(Section~\ref{sec:coordinator}).

I expected this preparation to shorten planning because each feature's
purpose and constraints had already been discussed. The documents and
conversations show what workers were asked to build and reviewers were asked to accept, without measuring a speed or quality gain: I did not
compare the work with a human-only team or another planning approach.

\subsection{The coordinator}\label{sec:coordinator}

The coordinator ran through Copilot CLI on a VM, selecting dependency-ready
issues and launching parallel worker sessions in isolated git worktrees,
so workers could change their own copies without editing the same files.
Each worker received an issue and HVE Core's research, plan, implement and review (RPI) workflow, and the coordinator checked the resulting pull request,
updated the project board and, under owner delegation, merged changes.
Interactive and CLI model configurations changed during the project;
recorded selectors and recalled interface labels are distinguished in the
source package. The delivery workflow kept changing, and the recovered history records my steering decisions and prescribed model
selectors; the Supplement distinguishes those instructions from verified
historical execution.

Early worker sessions implemented directly, prompting me to make
the full RPI sequence and committed tracking artefacts mandatory; further
instructions required evidence-backed acceptance ticks, scheduled monitoring
and increasingly extensive local gates. I instructed workers to use the new
source layout and migrate the prerequisites first
(the supplementary coordinator audit, turn 66).
Human decisions, approvals, credentials and unresolved review findings could still block work.
An accepted architecture decision prioritised migration to a new source layout and froze feature work in the MVP\@. Coordination changed alongside migration and procedural requirements,
and the recovered history also contains repeated scheduled prompts, so a
message stored in the user field cannot automatically count as a human
intervention. Supplement Section~\ref{app:deferredmeasures} records the
selection rule and explains why the human-intervention and
intervention-demand rates (HIR and IDR) were not estimated.

\subsection{Data and analysis}

This exploratory single-case study follows the transition from interactive
discovery and MVP use to delivery through issues dispatched by a coordinator. I selected the case after encountering the unusable replacement and acted as participant-observer, using case-study guidance and the ACM SIGSOFT Empirical Standards~\cite{runeson2009guidelines,sigsoft2021standards}.

We examined versioned requirements, architecture decisions, coordinator
instructions, issues, pull requests and selected research/plan/review
records, using distinct snapshots for the original case and later follow-up.
My supplied issue-state export and recollections help reconstruct the
handoff, while committed sources show what was recorded at the time.

We traced descriptive measures and selected episodes with AI assistance,
using a focused narrative literature synthesis and purposively selected
external repositories for context rather than rerunning their applications.
Section~\ref{sec:threats} explains the selection and corroboration limits;
the Supplement preserves extraction rules and source-specific qualifications.

\subsection{What the study measures}\label{sec:constructs}

Here an \emph{agent} combines a model, tools and instructions in a loop that
selects and executes actions. In the case, I kept scope decisions,
approval and delegated merge authority (Section~\ref{sec:coordinator});
the human authors retain responsibility for this study.
A \emph{skill} is a reusable set of procedures describing when and how to
act and check the outcome, distinct from a session history and without updating model weights, a distinction that follows
Jiang et~al.~\cite[Sec.~1]{jiang2026skills}. The pilot uses a handover
note as context; it does not vary skill use as its own treatment.

\emph{Working behaviour} means completing an intended task through the
running system, including the identity, data and service dependencies needed
for that task. In this case, rejecting an unauthenticated request did not
show that an authorised staff member could sign in and open a case.
\emph{Decay} denotes loss of previously working behaviour or
increasing difficulty of understanding and changing a system. The case
records lost usability during replacement; any decline in intrinsic code
quality was not measured. Deployment drift is another explanation (Section~\ref{sec:threats}).
\emph{Adaptability} was defined in the prospective design as success and cost
on the unforeseen change request under a fixed budget, measuring one aspect of maintainability.
Here, \emph{consolidation} means scheduled structural work intended
to preserve observable behaviour, with tests checking that intention.
The later CR1 view-write failures exposed behaviour that the earlier
workflow panel did not check (Section~\ref{sec:resultsjudging}).

We distinguish five measurement categories: PRs, lines and words describe
\emph{production volume}; checks, reviews and receipts describe
\emph{validation activity}; observed user tasks describe \emph{system
behaviour}; code metrics and the change request probe \emph{internal quality
and changeability}; and corrective help requested or supplied describes
\emph{intervention}. The original observations cover the first three categories, and a later post-hoc comparison adds code metrics as indirect measures of structure,
but no controlled changeability task or systematically coded intervention
dataset.

\section{Consolidation hypothesis and procedure}\label{sec:harness}

Restoring the case's missing identity and staff bindings required
configuration and end-to-end verification. Consolidation addresses a
different concern from the same experience: even with a correct
deployment, repeated feature work may leave a repository that is harder to
extend. The experiment narrowed the question to that inherited state by testing preserved behaviour and a withheld change request, and it
did not treat code cleanup as a remedy for the case's configuration failure.

Practitioners already structure multi-session agent handoffs around clean
repository states: Anthropic prompts each coding session to leave merge-ready
code and update a progress file~\cite{anthropic2025harness}, an account of
practice without a comparison of feature-only delivery against
consolidation between feature steps.
Darwin's continuous optimisation is a further precedent for automated
improvement, but its performance evaluations do not isolate that intervention
or test an unforeseen change request~\cite{pavlenko2026factory}
(Section~\ref{sec:factory}). RefactorBench already evaluates refactoring
agents~\cite{gautam2025refactorbench}; the narrower hypothesis concerns preserved
behaviour and later adaptation during repeated feature additions.

The consolidation procedure tests one bounded form of reflective
correction, and it changes what persists in the repository. Self-Refine revises
an output and Reflexion retains lessons for later trials
~\cite{madaan2023selfrefine,shinn2023reflexion}; the present intervention
consolidates the software and its handover between different
feature requests. CRITIC's tool feedback is another precedent
~\cite{gou2024critic}. The held-out evaluation remained separate from that
feedback, and the study tests whether the accepted changes help with an
unforeseen request. The schedule sets each pause, and the agent cannot reject
features or redirect the product; after each feature, delivery pauses for
a bounded consolidation session.
The agent runs the tests and examines structural diagnostics, then reviews
the latest diff for duplication, complexity, unclear names, dead code,
misplaced responsibilities and tests coupled to implementation details.
It attempts small refactorings through
\texttt{test \&\& commit || revert}, so a change survives
only while the tests remain green. It may add tests of current behaviour,
but the defining example tests stay protected.

To prepare the next session, the agent replaces a design note of at most 300 words instead of appending to it, recording where rules reside and what debt is outstanding.
Once the quality targets are reached or the time budget expires, the pause
ends and the next feature begins. Supplement Section~\ref{app:activeprompts}
gives the inspected B/C templates and source bindings alongside the historical
prompt, keeping their different scopes explicit. The intervention combines
refactoring, additional tests and a design-oriented note, so the study
cannot isolate refactoring alone.

The hypothesis draws on Beck's alternation of features and
futures~\cite{beck2026prodacity,beck2025devslow} and \emph{Tidy
First?}~\cite{beck2023tidy}. The procedure costs time, and its benefit remains
an empirical question. Agent
refactorings can be incomplete or incorrect~\cite{gautam2025refactorbench},
and human studies caution against equating a refactoring label with a
quality gain. Kim et~al.\ report developers' refactoring challenges and
benefits~\cite{kim2014refactoring}; Bavota et~al.\ find that observed
refactorings do not consistently target or remove code
smells~\cite{bavota2015quality}. These findings argue for checking outcomes instead of assuming improvement, because test-commit-or-revert
protects behaviour only to the extent that the tests cover it
~\cite{ma2026building}. Section~\ref{sec:experiment} specifies how
the procedure was evaluated and reports the results.

\section{Discussion}\label{sec:discussion}

\subsection{Observed costs and possible payback}\label{sec:costprojection}

Consolidation improved structure at 1.84--2.25 times feature-only delivery
credits in fully billed subsets; its 1.19-point coverage advantage
over longer sessions faced a 3.04-point ceiling against the original
practical target. Matching resource ceilings did not match spending,
and the extra delivery cost brought no consistent reduction in CR1 cost.
Some consolidation runs delivered more complete software, so cost
comparisons must consider that difference rather than treating cheap
failure as efficiency.

The assumed payback model in Supplement Section~\ref{app:economics} asks whether lower costs on enough later features could recover the cleanup investment, but we did not fit its cost-growth parameter $\delta$ to these
data: capped budgets allow harder work to produce less complete features
without increasing spending. Testing long-term payback needs longer
sequences, resolved billing and comparable delivered behaviour.

\subsection{What worked}

For the product described in Section~\ref{sec:method}, the agents were useful
before coding began: they helped me question what to build. Research agents
gathered and analysed source material, and role-based agents challenged
the proposed design. An evidence-assessment task still
needed surveyor judgement; a resident-contact task still needed consent
and a manual route. The prototypes made those boundaries visible in a
case card and resident-decision record. I built and reshaped the MVP
through targeted exchanges and feedback.
These observations come from my use of the tools; we did not measure a
human-only duration or run a controlled comparison of feedback cadences.
The Supplement documents the discovery, prototype and backlog handoffs.

\subsection{Human judgement and reflective work}

I supplied several kinds of reflective work: choosing what not to build,
recognising the unusable replacement and deciding which earlier lessons
mattered. Naur's theory-building account
describes the understanding I carried forward~\cite{naur1985theory}, and
Beck similarly separates producing code from learning through working
software~\cite{beck2026prodacity}. These case-specific judgements
raise the question of whether agents could make comparable ones.
The experiment asks something narrower: whether bounded post-feature
correction preserves behaviour and later changeability.

An approval record alone cannot establish that a person evaluated the
alternatives independently. In Anthropic's
randomised study, 61 analysts were recruited and 50 used the agent. Those
50 analysts matched their agent's
randomly assigned preference on 86\% of four analytical choices
~\cite[Study design; Results]{herdagdelen2026judgment}. The preferences were
deliberately strengthened in one farming-analysis task with one model; the
rate concerns a different task and setting from coding
~\cite[Our study's limitations]{herdagdelen2026judgment}.
The study did not assess the decisions reported in this case. Its authors suggest
asking experts for their view first or making the best case for each option
~\cite[What this means]{herdagdelen2026judgment}. I propose a separate step:
record the alternatives and a person's reasons before accepting an agent's
recommendation. This study did not test that procedure.

\subsection{Protection can also constrain the next feature}

Every arm rolled back unsuccessful increments and protected immutable
accepted tests, a harness that plausibly explains why the expected decay
did not appear. The same protection obstructed GPT~6.1 Sol's ninth feature:
an earlier test fixed the allowed view methods, so adding ranking broke a
test the agent could not edit. This is a hypothesis about the harness,
not an estimated treatment effect, because no arm ran without those rules.

The case and experiment also suggest a shared problem at interfaces that
local checks did not exercise. In my application, rejecting unauthorised
requests did not verify identity and internal-staff binding for an
authorised user; in CR1, refusing an established write method did not
verify refusal of newly introduced view methods. We interpret this
gap between local completion and usable behaviour as ``everything but the
software'', without treating the coding experiment as a reproduction of
the deployment failure. Gemini's 16/21 review successes versus 8/21 under
consolidation illustrate the distinction between structural hygiene and
extension-safe permissions, although we did not trace the responsible review
actions.

\subsection{What this study teaches a future experiment}\label{sec:futureexperiment}

We expected decay, but the agents largely preserved what they had
implemented, changing the next study's question from whether cleanup prevents
inevitable loss to when it improves acquisition or adaptation enough to
justify its cost. A longer, coupled brownfield task could test that
trade-off, distinguishing rejected edits from accepted failures and
allowing stable retention as an outcome.

Several change requests on isolated branches would probe adaptation without
altering the continuing development history, and component comparisons could
distinguish refactoring from review, new tests and handover notes.
Discovery was disabled here; comparing full RPI with feature-only delivery
would answer another question. Supplement Section~\ref{app:futuredesign}
preserves the numerical candidates and reporting requirements for a
prospectively registered study, deferred until its design and resources
are approved. We plan no additional experimental or judge batch for this paper.

\subsection{Implications for practice}\label{sec:feedbackfirst}

The report recommends \emph{adjust} before adopting unconditional consolidation and proposes a triggered hybrid of cleanup, review and specification-bound repair (Supplement Section~\ref{app:practicecandidate}), but we have not tested that combination,
so its proposed efficacy cannot justify replacing an existing review
workflow.

For my application, the useful checkpoint would have been signing in and
opening an assigned case with both identity bindings checked together.
Carrying that prerequisite into later briefs or executable checks is a
proposed response to the case, subject to the existing safety and approval
boundaries; any context compaction must preserve adverse evidence and use
archive-backed, restore-verified selection.

\subsection{Threats to validity}\label{sec:threats}

The case is a retrospective participant-observer account of a project whose
success interested me: I designed the coordinator and selected the episodes.
We analysed selected records without exhaustive coding or independent
corroboration of every observation. The failed deployed task still lacks a
matched release-linked trace. Migration, scope, model/tool changes,
configuration and owner priorities changed with coordination; document
counts cannot identify their effects or measure context overload,
per-change gate burden or lost knowledge~\cite{devanbu2016belief}.

The experiment covers one synthetic Python suite, ten features and one
fixed change request under rollback and protected-test rules, so it
does not estimate the five case mechanisms or unrestricted development.
Consolidation combines refactoring, added tests and a handover note;
matching resource ceilings leaves spending and session structure
unequal. Near-ceiling controls prevented the planned useful coverage gain;
post-treatment prerequisite groups and fully billed subsets describe
different delivered functionality rather than quality-matched effects.

The executed design includes unregistered amendments and sixteen source
versions, without a complete chronology of outcomes inspected when
amendments were chosen. Shared scheduling and provider conditions could
violate the within-cell independence assumed by the reported intervals,
which are exploratory and unadjusted for multiplicity; exposed model names
cannot guarantee fixed provider builds~\cite{chen2023drift}. Operationally
distinct execution and analysis do not provide independent scientific
review, and the unassisted-run attestation cannot exclude unrecorded
out-of-band intervention.

Two GPT CR1 outcomes are unknown, and 55 billing holds leave all-allocation
cost and payback unresolved. Judging used the earlier 313-run snapshot,
leaving four packets unavailable; scenario abstentions and an incomplete,
AI-assisted human spot-check limit rating interpretation. Packet
anonymisation did not remove historical anchoring or judge/development
family overlap (Section~\ref{sec:postrunjudging}), and the workflow panel
missed permission checks that the hidden suite exercised.
Inline suppressions could also affect lint counts because the evaluator
did not independently count them. Human effort, opportunity cost,
provider-active time and currency prices were not measured.

\FloatBarrier
\section{Conclusion}\label{sec:conclusion}

Across the ten-feature S1 task, previously acquired behaviour was largely
preserved. None of the 126 feature-only or longer-session runs had an open
regression at the final checkpoint ($P_{10}$); only one trajectory across
all arms did, and workflow replay found no witnessed losses across 626
evaluable packets. Rollback and immutable accepted tests plausibly helped
protect earlier behaviour while also constraining ranking, but their effect
was not tested against an unprotected arm.

Consolidation (B) removed complexity hotspots at all 63 endpoints, but its
primary coverage advantage over longer feature-only sessions (D) was
1.19 percentage points (conditional 95\% interval [0.10, 2.22]), below the
ten-point minimum useful threshold. Even perfect consolidation endpoints
could exceed the observed longer-session results by only 3.04 points,
exposing a ceiling in the task and measurement design.
GPT~6.1 Sol supplied most of the observed gain by
completing priority ranking. Sonnet~5.5 and Gemini~4 Argon showed small B--D gains whose
intervals spanned zero. Read-only review (C) achieved 16/21 Gemini CR1
successes versus 8/21 with consolidation.
Consolidation used 1.84--2.25 times feature-only delivery credits in
fully billed subsets without consistently lowering CR1 cost.

The motivating case concerns a different scale and failure: a migration
interrupted a usable workflow after extensive agent-assisted preparation.
Its candidate explanations informed a narrower experiment whose missing features and permission failures redirect attention towards acquisition and adaptation as well as retention; subject to the consolidated threats
in Section~\ref{sec:threats}, the evidence supports structural improvement
at additional delivery cost, without demonstrated short-horizon payback.
A later study needs longer, coupled work and several adaptation probes
under its own approved protocol and resources.

\section{Source and digest register}\label{app:source-register}

Record links such as \sourceref{R17} identify the version used for a claim.
Git commit IDs identify revisions, tree IDs directory contents and blob IDs
individual Git objects. SHA-256 digests identify retained file bytes or an
image. Matching an identifier verifies content identity. Claim support and
independent validation require their own evidence. Unless another repository is named, records refer to
\nolinkurl{jmservera/ama-thought-mve}. Historical and final records remain
separate even when they concern the same file.
