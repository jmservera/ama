\begin{abstract}
Software that only accumulates features decays; this has been known since
the 1970s. I propose that coding agents may accelerate this decay through
compounding errors and output that exceeds human review capacity. This
exploratory case study examines that proposition in
one well-documented case and specifies an experiment to test a remedy. Over
six weeks I used agents, centred on Microsoft's open-source HyperVelocity
Engineering (HVE Core) framework, to research a fictional social-housing
retrofit programme, write requirements and deploy an MVP, then handed a
backlog of 192 issues to a coordinator of my own design that ran parallel
research--plan--implement--review loops and merged its own pull requests. In
ten days, 183 pull requests were merged and the project log grew by about
37,000 words, yet I no longer had a system I could use, while an LLM-scored
rubric rated implementation completeness five out of five. I propose five
mechanisms consistent with the gap: specification inflation, proxy capture, learning
evaporation, process-gate inflation and feedback starvation. As a remedy I
propose a consolidation harness that, after every feature, stops the agent to
review its work, refactor under test-commit-or-revert and rewrite a one-page
design note before the next feature starts. I specify a controlled
experiment, designed with HVE Core's Minimum Viable Experiment method, that
compares the harness with feature-only delivery on cumulative correctness,
internal quality, changeability and cost. The developer's scarce
contribution, I argue, is shifting from producing code to designing the loops
that keep software working.
\end{abstract}

\noindent\textbf{Keywords:} agentic software engineering; coding agents;
spec-driven development; software evolution; technical debt; refactoring;
feedback loops; human--AI interaction; exploratory case study; experiment protocol.

\section{Introduction}\label{sec:intro}

On 15~October 2026 I started an agent coordinator against a backlog of more
than 180 GitHub issues and let it run. Each issue went into its own git
worktree, where an agent session ran a full research, plan, implement and
review loop, passed a local validation gate and published a pull request. The
coordinator assessed each candidate, merged it when every gate was green,
rebased the remaining branches and started the next wave of work. Ten days
later, 183 pull requests had been merged. I could not sign in to a running
version of the system I was building.

That gap, between an extraordinary volume of activity and the absence of
anything I could touch, try and learn from, is the subject of this report. It
is the wall that several of the most experienced practitioners in our field
have been describing. Kent Beck compares coding agents to genies that grant
wishes literally, warns that plausible code is not working code, and has
written about the existential crisis that follows when the visible part of a
craft can be produced by a machine~\cite{orosz2025beck,beck2026prodacity,beck2026mathematicians,beck2023ninety}.
Robert C.\ Martin argues that agents will out-code us, so our discipline must
move into constraints that machines enforce~\cite{martin2026outcodes,martin2026productengineers}.
Andrew Murphy reminds engineering leaders that the speed of writing code was
never the bottleneck~\cite{murphy2026speed}. I knew these warnings and
followed many of them. I hit the wall anyway, and the way I hit it is
instructive.

My working theory is simple. Software that only accumulates features, without
deliberate consolidation, decays: it becomes more complex, more fragile and
slower to change. That has been documented for
decades~\cite{lehman1980laws,parnas1994aging,eick2001decay,cunningham1992wycash}.
I propose that agentic development may run the same decay faster, through two
possible accelerants. The first is
compounding error. Each step builds on the agent's previous output, including
its misreadings of intent and complexity nobody asked for; Beck's genie grants
the wish as stated, not as meant~\cite{orosz2025beck}, and every literal wish
becomes the context for the next. The second is volume. Agents produce more
code and documentation than people have the time or patience to review and
test, so the decay goes unseen until something breaks. If the theory holds,
the remedy is the one Beck describes: stop adding features blindly, and after
each feature stop, review, refactor and improve before adding the
next~\cite{beck2026prodacity,beck2025devslow,beck2023tidy}.

The case is unusually well documented. The repository is public, every change
went through a pull request, an append-only log recorded what the agents did
and why, and the coordinator's own instructions are versioned with the
code~\cite{servera2026ama}. This makes it possible to go beyond anecdote and
ask four questions:

\begin{itemize}[leftmargin=*]
\item \textbf{RQ1.} What did a long-running, autonomous, spec-driven delivery
loop produce, and what did it fail to produce?
\item \textbf{RQ2.} Which proposed mechanisms fit the gap between activity and
usable outcome, and do they fit the working theory?
\item \textbf{RQ3.} Can a harness that consolidates after every feature slow
the decay, and at what cost? This report specifies the experiment that will
answer it.
\item \textbf{RQ4.} What does all this imply for the developer's role?
\end{itemize}

\noindent The report makes five contributions:

\begin{enumerate}[leftmargin=*]
\item A documented case of one architect working with agents for six weeks,
from desk research to a deployed MVP and then a ten-day autonomous delivery
loop, with quantitative evidence from the repository, its issue tracker and
its log (Sections~\ref{sec:method} and~\ref{sec:what}).
\item Five proposed mechanisms consistent with the loop's activity without usable
software, each grounded in the case, mapped onto the working theory, linked to
prior work and paired with an early-warning signal
(Section~\ref{sec:mechanisms}).
\item A feedback-first operating model for agentic delivery, made of
invariants, checkpoints, proportional gates and measures that an architect can
apply on the next working day (Section~\ref{sec:feedbackfirst}).
\item A consolidation harness and a controlled experiment protocol to test
an intervention that is practised but untested in the controlled comparisons
I found~\cite{openai2026harness,anthropic2025harness}. The protocol follows
the registered-report example of Lulla et~al.~\cite{lulla2026protocol}
and HVE Core's Minimum Viable Experiment method, with hypotheses
and decision rules to reconcile with the tagged protocol before registration
and fresh confirmatory runs (Sections~\ref{sec:harness}
and~\ref{sec:experiment}).
\item A reading of the developer's existential crisis grounded in what, in
this case, remained the human's job (Section~\ref{sec:discussion}).
\end{enumerate}

This is not an evaluation of the tools I used. The framework at the centre of
the case keeps a human between its phases by default; the failures described
here occurred in a configuration I designed that delegated delivery and merge
decisions (Section~\ref{sec:hve}). I still handled approvals and technical
blockers, but no longer learned from using the replacement product. I cannot
isolate that change from the others.

\section{Background}\label{sec:background}

\subsection{Software that only grows}\label{sec:decay}

That software decays when it only accumulates features is one of the oldest
observations in our field. Lehman's laws of software evolution hold that a
program in real-world use must keep changing, and that its complexity grows as
it evolves unless work is done to maintain or reduce it~\cite{lehman1980laws};
a later formulation adds that its quality will appear to decline unless it is
rigorously maintained and adapted~\cite{lehman1997metrics}. Parnas called the
result software aging, and blamed in part the changes made by people who do
not understand the original design~\cite{parnas1994aging}. Eick and colleagues
found mixed but, on the whole, persuasive evidence of code decay in fifteen
years of change data from a large telephone-switching
system~\cite{eick2001decay}. Cunningham's technical-debt metaphor framed the
cost of not consolidating as interest paid on every later
change~\cite{cunningham1992wycash}, and Fowler's design stamina hypothesis
holds that without attention to design, adding features eventually becomes
slower than it would have been with it~\cite{fowler2007stamina}. Studies have
since put numbers on the interest: across 39 proprietary code bases,
low-quality code had fifteen times more defects and took 124\% longer to
develop than high-quality code~\cite{tornhill2022codered}, and developers in a
longitudinal study lost about 23\% of their working time to technical
debt~\cite{besker2018cripples}.

The evidence has limits. Lehman's laws are conditional: they predict decay
only when no counter-work is done. Increasing complexity and declining quality
are among the least empirically supported of the laws, and some open-source
systems, Linux among them, have grown without the predicted
decay~\cite{herraiz2013laws}. Several of the studies above are correlational.
The common lesson is narrower and sturdier: quality is not preserved by
default. It is the product of work that feature delivery tends to crowd out.

\subsection{Why agents might accelerate the decay}\label{sec:empirical}

Two properties of current agents could speed that decay up. The first is
compounding error. When language models execute long tasks they condition on
their own earlier mistakes, so errors become more likely as tasks
lengthen~\cite{sinha2025illusion}; in multi-turn, underspecified conversations
their performance drops by 39\% on average, largely because they commit to
early, wrong assumptions and then build on them~\cite{laban2025lost}. Coding
benchmarks show the same pattern at the scale of a code base. In
SlopCodeBench, where agents repeatedly extend their own solutions, structural
erosion rises in 77\% of trajectories, agent code is 2.3 times more verbose and
twice as eroded as comparable open-source code, and explicit quality
instructions improve the starting point without changing the rate of
degradation~\cite{orlanski2026slopcodebench}. In SWE-CI, which replays months
of real repository history, regressions increased with iterations for most of
the models tested~\cite{chen2026sweci}. All 20 models scored below human
oracle code on the Maintainability Index, although 15 of 20 scored better on
Pylint; most had a zero-regression rate below 0.25. Code could look clean on
the surface while scoring worse on structure. Heander et~al. found a related
caution in agentic review: better CodeHealth was associated with lower token
cost, but batch fixing left median CodeHealth unchanged~\cite{heander2026codehealth}.
Given only a requirements document and
an empty repository, agents lose global coherence~\cite{ding2025nl2repo}, and
some ``pass'' tests by modifying them~\cite{zhong2026impossiblebench}. Field
data point the same way. Open-source projects that adopted an AI coding tool
saw a short-lived jump in velocity but persistent increases of about 30\% in
static-analysis warnings and 41\% in code complexity, which in turn slowed
later development~\cite{he2025cursor}; repository-scale analyses report
copy-pasted code rising and moved, that is refactored, code falling as AI
assistance spread~\cite{gitclear2025}; and DORA associated a 25\% increase in
AI adoption with better documentation and code quality but lower delivery
stability ($-7.2$\%) in 2024, with stability still lower in its 2025 report,
which describes AI as an amplifier of existing strengths and dysfunctions and
recommends working in small batches and a user-centric
focus~\cite{dora2024,harvey2024dora,dora2025,dora2025blog}.

The evidence is not one-sided. A preregistered randomised trial found no
significant difference in how easily developers evolved code that others had
written with or without AI assistance~\cite{borg2025echoes}. A study of chained
maintenance tasks found that the downstream cost of agent edits comes mainly
from inherited test failures and disappears when the earlier tests pass,
which points to regressions rather than complexity as the channel of
compounding~\cite{pan2026swemaintain}. And the best-known controlled
productivity result, experienced developers 19\% slower with early-2025 tools
while believing they had been 20\% faster~\cite{becker2025metr}, has since been
qualified by its authors, who think developers are probably faster
now~\cite{metr2026uplift}. Its durable lesson is the gap between perceived and
measured progress.

The second property is volume. Human review works best on small changes in
short sessions: industrial guidance is to review no more than a few hundred
lines at a time~\cite{cohen2006review}, the median change at Google is about
two dozen lines~\cite{sadowski2018google}, and understanding the change, more
than finding defects, is the main challenge of modern code
review~\cite{bacchelli2013review}. Agents break those conditions. Among repeat
reviewers of agent-authored pull requests, approval rates rose while inline
comments fell, a pattern its authors call habituation~\cite{yu2026habituation}.
Multi-agent systems add failure modes of their own, in system design,
inter-agent misalignment and verification~\cite{cemri2025multiagent}; agent
builders advise sharing full context rather than splitting it across agents
that each see a fragment~\cite{yan2025multiagents}; and models use long
contexts unevenly and less reliably as they grow~\cite{liu2024lost,hong2025contextrot}.
By contrast, tests that clarify intent help both the model and the person
judging its output~\cite{fakhoury2024ticoder}.

\subsection{The practitioner conversation}\label{sec:practitioners}

The closest practitioner argument is Waseem et~al.'s account of internally
developed MVPs and industry reports~\cite{waseem2025vibe}. They describe the
same trade-off: rapid generation can accumulate debt through architectural
inconsistency, security vulnerabilities and maintenance overhead. Their
account includes descriptive security-scan counts but does not estimate a
controlled effect of consolidation. I do not claim that argument as new.
I add a public case trace, proposed mechanisms with early-warning signals,
and a falsifiable experiment protocol.

Kent Beck has been the most persistent chronicler of this shift. In 2023 he
wrote that the value of most of his skills had dropped to zero while the
leverage of the rest had multiplied~\cite{beck2023ninety}. His 2025 experiment
in \emph{augmented coding}, building a B+~tree library with an agent under
strict test-driven development, separated it from vibe coding by whether the
programmer still cares about the code, its complexity, the tests and their
coverage. He named the warning signs he watched for: loops, functionality
nobody asked for, and tests disabled or manipulated so that they
pass~\cite{beck2025augmented}. He describes agents as genies that grant wishes
literally rather than as intended, and that will delete tests and declare
themselves finished~\cite{orosz2025beck}. In his Prodacity~2026 talk he argued
that fully agentic work without feedback goes off the rails, that the best
software comes from maximising learning with software as a side effect, that
every feature burns options that must be restored by alternating features
with consolidation, and that one-shot spec-driven development is ``waterfall
wearing a new coat''~\cite{beck2026prodacity,beck2025devslow}. In a September
2026 essay addressed to mathematicians facing AI systems that prove theorems,
he separates a discipline's visible output from the less visible work of
understanding, simplifying and building abstractions, and places lasting human
value in the latter~\cite{beck2026mathematicians}.

Robert C.\ Martin, who in 2024 dismissed doom-laden predictions about AI
while treating language models as useful tools~\cite{martin2024weprogrammers},
now argues that agents will out-code humans by a wide margin. Programmers
should therefore use that leverage to
enforce test coverage, mutation testing and complexity limits through
deterministic, executable standards, writing tests first and knowing their
customers~\cite{martin2026outcodes,martin2026productengineers}. Erich Gamma,
discussing the open-sourcing of AI features in Visual Studio Code, made a
related point about evaluation: once a language model is part of a test,
``your test is, by definition, flaky'', so his team built stochastic
simulation tests instead~\cite{gamma2025syntax}. Andrew Murphy applies the
Theory of Constraints~\cite{goldratt1984goal}: accelerating a non-bottleneck
fills review queues and inflates work in progress, so that ``you are producing
more code and shipping less software''~\cite{murphy2026speed}. He has also
described engineers' grief at the loss of their craft~\cite{murphy2026fivestages}.

Voices from inside the HVE community and from Microsoft's product groups say
similar things. Mike Lanzetta, who writes about hypervelocity engineering,
advises early-career engineers to work in small chunks, test first and limit
the complexity of files and functions, and says that experienced developers
``should expect to spend more time in Pull Request reviews, not
less''~\cite{lanzetta2025growing}. After pushing roughly 60,000 lines of code
in a two-week sprint with a crew of specialised agents, he described
re-explaining architectural constraints to agents that had drifted from the
original intent, observed that in a high-throughput environment ``quality
drift creeps in fast'', and responded with a mandatory done gate and
sprint-boundary retrospectives whose findings block the next sprint until they
are resolved~\cite{lanzetta2026orchestra}. Charles Lamanna reports that
agentic coding moved his organisation's bottleneck from writing code to
deciding what matters and knowing whether what was built is good. Rather than
spending the surplus on more features, his teams shipped about as many as
before with more depth, reliability, performance and security, and one
product's support tickets fell by double-digit percentages year over year
while usage grew. Counting inputs such as lines of code, he writes, ``is easy
and tells you almost nothing''~\cite{lamanna2026changing}.

Spec-driven development (SDD) is the most direct attempt to tame agents with
structure. GitHub's Spec Kit proposes a specify, plan, tasks and implement
flow in which the developer's role is to verify, not merely to
steer~\cite{delimarsky2025speckit}. Birgitta B\"ockeler's review of SDD tools
distinguishes spec-first, spec-anchored and spec-as-source approaches,
reports one tool turning a small bug into four user stories with sixteen
acceptance criteria, observes that agents both ignored and over-followed
instructions, and concludes: ``I'd rather review code than all these markdown
files''~\cite{boeckeler2025sdd}. A study of SDD in practice reports more
reliable agent behaviour but higher planning and review costs, and
specifications that decay~\cite{agarwal2026sdd}. Other voices frame the same
tension: \emph{vibe coding} for throwaway projects~\cite{karpathy2025vibe};
\emph{vibe engineering}, in which experienced engineers stay
accountable~\cite{willison2025vibeeng}; the observation that AI gets a project
most of the way while the rest needs engineering
judgement~\cite{osmani2024seventy}; software engineering joining the
non-deterministic engineering disciplines~\cite{fowler2025thoughts}; and the
advice to hold back on complacency with AI-generated
code~\cite{thoughtworks2025complacency}.

\subsection{Older theory}\label{sec:theory}

None of this is new in kind. Peter Naur argued that programming is primarily
the building of a theory, held by the programmers, of how the program solves
its problem, and that documentation cannot fully carry that theory. In his
example, a second team equipped with full documentation still made changes
that destroyed the power and simplicity of the original
design~\cite{naur1985theory}. Brooks located the essential difficulty of
software in specifying, designing and testing the conceptual construct rather
than in representing it~\cite{brooks1987silver}. Royce, often cited as the
origin of the waterfall model, called the purely sequential approach risky
because testing at the end is the first time behaviour is experienced rather
than analysed~\cite{royce1970}. Gall observed that complex systems that work
evolve from simple systems that worked~\cite{gall1975}. Extreme Programming
built its practices around short feedback loops and small
releases~\cite{beck2004xp,beck2002tdd}; Cockburn's walking skeleton and Hunt
and Thomas's tracer bullets both start with a thin end-to-end
implementation~\cite{cockburn2004crystal,hunt1999pragmatic}; and the Agile
Manifesto values ``working software over comprehensive
documentation''~\cite{agile2001manifesto}. Beck's \emph{Tidy First?} treats
design as small, reversible structural changes made before behaviour
changes~\cite{beck2023tidy}.

From human factors, Bainbridge's ironies of automation explain why automating
the routine parts of a task leaves operators with the hardest parts,
monitoring and intervention, while eroding the skills those parts
need~\cite{bainbridge1983ironies}. Recent work applies this to generative AI:
users shift from producing to evaluating, workflows are restructured
unhelpfully, and automation makes easy tasks easier and hard tasks
harder~\cite{simkute2024ironies}. Working with generative AI makes
metacognitive demands similar to delegating to a
team~\cite{tankelevitch2024metacognitive}; higher confidence in AI is
associated with less critical thinking~\cite{lee2025critical}; and AI that
challenges rather than obeys has been proposed as a
counterweight~\cite{sarkar2024challenge}. Finally, Goodhart's law, in
Strathern's formulation, warns that a measure used as a target
``ceases to be a good measure''~\cite{goodhart1975,strathern1997improving}.

\subsection{HyperVelocity Engineering (HVE Core)}\label{sec:hve}

HVE Core is an open-source framework from Microsoft that describes itself as
an opinionated agentic software development lifecycle built on GitHub
Copilot, guided by the principle ``AI carries the rules, humans keep the
judgment''~\cite{hvecore}. Its central workflow is Research, Plan, Implement
and Review (RPI): research when evidence is missing, a plan with a default
critique, implementation, review and follow-up. Each phase writes dated
artefacts under a \texttt{.copilot-tracking} folder, so that context travels
through files rather than chat history, and the framework treats these
artefacts as git-ignored working memory by default. Its RPI agent runs in a
manual mode by default; a fully automatic mode must be confirmed explicitly
and still stops for blockers, required human review, and destructive or
externally visible actions. The framework describes itself as a lifecycle
wrapper rather than a dispatcher of autonomous worker agents. Around RPI it
offers product-side agents: a Design Thinking coach, builders for business
and product requirements documents (BRD and PRD), a Socratic assistant for
architecture decision records (ADRs) and a backlog manager for GitHub, Azure
DevOps and Jira. The project warns that it evolves quickly and is best treated
as a source of patterns~\cite{hvecore}.
Its experimental collection includes an Experiment Designer agent that
coaches a team through a Minimum Viable Experiment: falsifiable hypotheses
with success thresholds set before any run, vetting against red flags, a
minimal design, and an evaluation of the outcome against the precommitted
criteria~\cite{hvecore}. Section~\ref{sec:experiment} uses it.
I used the HVE Core plugin snapshot \texttt{plugins-v3.3.106} throughout the
case. Its snapshot commit is
\texttt{2df5013e29ebfd2ce61bcd0cf021d8c8186482eb}, generated from source commit
\texttt{e9af018fe5ffbfbc72321a8bca21fb987359af08}. Historical use is my account;
the snapshot identifiers do not establish an installation date.

\section{Case and method}\label{sec:method}

\subsection{Setting}

The case is my capstone for Microsoft's \emph{Azure Master Architect} (AMA)
programme. Its name is public in the Microsoft Employee Learning
badge listing.\footnote{\url{https://www.credly.com/org/microsoft-employee-learning/badge/azure-master-architect}}
That public listing does not authorise publication of internal assessment
material or this paper.

The brief, Case Study~48, describes Zava North Homes, a fictional
not-for-profit housing association that manages about 60,000 homes in the
North of England. It must improve the energy efficiency of its stock while
meeting statutory response times for hazards such as damp and mould, and it
coordinates retrofit assessment, grants, procurement, resident consent and
quality assurance in spreadsheets. The brief asks for a research-backed
proposal, business requirements, an agent architecture, a delivery plan, a
working demonstrator and an executive presentation. The programme's rubric
has twenty criteria; the top descriptor for implementation completeness is
``all required capabilities working end to end''.

I worked alone, as architect and product owner, from 11~September to
24~October 2026. Agents did almost all of the research synthesis, writing and
coding. The repository also contains an automated scorer: a GitHub agentic
workflow that asks a language model to score each pull request against the
rubric and records the result~\cite{servera2026ama}.

\subsection{Workflow and tools}

For interactive development I used GitHub Copilot in VS Code, mainly
Opus~5.5 during the first two weeks and then GPT-6.1 Sol through the case
cut-off. These are the model labels I recall using, not verified provider
build identifiers or an exact switch date.

\begin{itemize}[leftmargin=*]
\item \textbf{Research.} Sixteen official legislation, regulator, policy,
standards and funding documents were downloaded, converted to Markdown and
organised, with agent-written sector and company research, into a knowledge
base: an index, immutable sources, maintained syntheses, an
owner-curated memory file and an append-only log of every change.
\item \textbf{Challenge.} Eight agents role-playing the case organisation's
stakeholders (asset management, programme delivery, finance, procurement,
data, building safety, neighbourhood housing and resident engagement) and HVE
Core's Design Thinking coach challenged each idea. Their first verdict was
that none of the five end-to-end agents requested in the brief should be
built as such.
\item \textbf{Requirements and decisions.} HVE Core's BRD and PRD builders, a
BRD quality reviewer and the ADR assistant produced and revised the
requirements and six architecture decision records.
\item \textbf{Prototypes and MVP.} Several prototypes were built, reviewed by
the role agents and kept as evidence. An MVP followed and was deployed to
Azure.
\item \textbf{Backlog.} HVE Core's backlog manager turned the requirements and
decisions into GitHub issues with epics, features, acceptance criteria and
dependencies, labelled by how much of each item already existed in the MVP.
\item \textbf{Coordinator.} On 15~October I added a coordinator agent of my
own design to deliver the backlog (Section~\ref{sec:coordinator}).
\end{itemize}

\subsection{The coordinator}\label{sec:coordinator}

The coordinator ran through Copilot CLI on a VM. It selected waves of issues
whose dependencies were merged and launched parallel worker CLI sessions
through \texttt{tmux}, each in an isolated git worktree with HVE Core's RPI
agent and one issue as its brief. I used Sonnet~5.5 for the workers, including
before the explicit pin. At the pinned repository commit the worker selector
is \texttt{claude-sonnet-5.5}; PR \#420 introduced that requirement on
21~October. The earlier use is my recollection; the committed selector
independently records the later configuration.
The coordinator used Auto selection with the Intelligence setting. I observed
it tending to select GPT-6.1 Sol, but this was not a guaranteed model pin or
proof of every session's actual model or provider build.

Within its first day I added four rules, each in response to an observed
problem. First, it could merge its own pull requests through a gate it
verified itself, because repository auto-merge was unavailable. Second, the
full research, plan, implement and review loop became mandatory for every
issue, and the presence of the loop's \texttt{.copilot-tracking} artefacts in
the pull request became a merge condition, because the first waves of sessions
had implemented directly without them. Third, it updated the project board and
ticked only the acceptance criteria that reviewed evidence proved. Fourth, it
monitored sessions on a schedule instead of blocking. Later rules required a
complete local validation gate before every push, including
documentation-only changes, covering five source projects, infrastructure
templates, a disposable SQL Server, browser accessibility checks, migrations,
four container images, vulnerability scans and a software bill of materials,
to be rerun after every correction or rebase. An issue stopped only on a
\emph{human blocker}: an owner decision, a named approval, a missing
credential, or a review finding still open after two correction cycles. On the
same day an accepted ADR made migrating the working MVP into a new source
layout the first priority and barred new feature code from the MVP.

\subsection{Data and analysis}

\section{Five mechanisms}\label{sec:mechanisms}

I propose five mechanisms consistent with how a loop that merged a pull
request every eighty minutes or so left its owner with nothing to use.
Table~\ref{tab:mechanisms} summarises them.

Read against the working theory of Section~\ref{sec:intro}, they fall into
groups (Table~\ref{tab:theory}). The base rate is feature accumulation
without consolidation: until 24~October the loop had no step that paused
feature work to review and refactor what had been built, and its one large
restructuring, the migration to a new source layout, was planned up front as
backlog items rather than done continuously. Specification inflation, proxy
capture and learning evaporation are forms of the first accelerant,
compounding error: each misreading, or literal reading, of intent became the
context, the criteria or the evidence for the next step. Process-gate
inflation and feedback starvation may reflect the second, unreviewable
volume: gates and caveats coexisted with the absence of a person using the product.

\subsection{Specification inflation}\label{sec:m1}

\emph{The specification grew faster than any system could absorb it or any
person could validate it.} By 22~October the BRD had reached version~0.19 and
about 37,900 words, with requirement identifiers up to FR-052 and AC-103; the
PRD had reached version~0.18 and about 33,900 words, with identifiers up to
FR-061 and AC-110. The backlog inherited that scale and grew to 192 issues.
Cross-cutting concerns were appended to existing issues rather than sequenced
as their own work: a responsible-AI section on 15~October and an
AI-consumption section on 22~October. Issue \#126, on pilot release gates,
ended with seventeen acceptance criteria in three sections. Even my request
for the smallest runnable preview arrived with thirteen.

This expansion began before the autonomous backlog loop, including after my
prototype and MVP feedback. The requirements agents sought fully specified
BRDs and PRDs, named approvers and resolved ownership before building. I
pushed for explicit demonstrator assumptions and imperfect increments that
could produce feedback. Smaller, iterative requirements documents are a
plausible alternative, not an intervention tested in this case.

This is B\"ockeler's small bug that became sixteen acceptance
criteria~\cite{boeckeler2025sdd}, at the scale of a programme. It is also what
Royce and Gall warned about: a large system specified up front and tested at
the end~\cite{royce1970,gall1975}. Brooks explains why more text does not
help: the essential difficulty lies in the conceptual construct, and writing
it down in more places does not reduce it~\cite{brooks1987silver}. The
benchmark evidence points the same way: agents given only a requirements
document lose global coherence~\cite{ding2025nl2repo}. Beck's metaphor fits:
every feature, and every acceptance criterion, burns
options~\cite{beck2026prodacity,beck2025devslow}. The early-warning signal is
the ratio of specification growth to behaviour a human has validated in the
same period. Here the denominator was close to zero.

\subsection{Proxy capture}\label{sec:m2}

\emph{In this case, artefacts made into gates appeared to displace outcomes.}
I interpret three patterns this way.

Merged pull requests are a weak proxy for delivered value. Murphy-Hill et~al.
report roughly 24\% more merges among adopters in Microsoft's rollout, while
explicitly distinguishing merges from value~\cite{murphyhill2026agents}.
Peralta et~al. studied 9,799 human-reviewed agent pull requests; in their
manually inspected samples, only 35.7\% of rejections reflected clear agent
failures and 15.4\% of merges required explicit reviewer
involvement~\cite{peralta2026merged}. AIDev shows the scale of this measurement
problem: 932,791 agent-authored pull requests from five agents across 116,211
repositories, not a count of delivered outcomes~\cite{li2026aidev}.

\emph{Process.} When the first waves of sessions skipped the research and
planning phases, I made the presence of their artefacts a merge condition.
From then on every pull request carried research, plan, change and review
records; the artefacts were guaranteed, the thinking they were meant to
evidence was not. Pull request \#445 changed two lines of behaviour and added
a 78-line evidence record that reports its own artefact completion as 100\%.
HVE Core treats these files as git-ignored working memory; my gate turned them
into the deliverable.

In the first-parent integration view, tracking-artefact additions were
10.27 times product-source additions during the loop, compared with 29.28
before it (\texttt{anc/repo\_history\_metrics.out.txt}). This supports concern
about artefact volume, not a claim that the ratio rose when autonomy began.
Churn alone does not establish code decay.

\emph{Evaluation.} The rubric scorer, a language model reading the repository,
rated implementation completeness at five out of five, ``all required
capabilities working end to end'', citing a README and a check script, at a
time when I could not sign in to the system. Gamma's remark about tests
applies to judges too: put a model in the evaluation and the evaluation
becomes stochastic~\cite{gamma2025syntax}, and a judge that reads the
repository is scoring the text that agents are best at producing.

\emph{Honesty.} I had instructed the agents never to fabricate approvals or
overstate evidence. They complied: hedged statements of unmet acceptance more
than tripled in density, and the knowledge-base index filled with them.
Issue \#349 records that a browser redirect ``is not successful sign-in''.
The agents were right, and still nobody could sign in. Honest boundary
statements became the output.

Goodhart and Strathern predict the first two
levels~\cite{goodhart1975,strathern1997improving}; Beck observed agents
deleting tests to finish~\cite{orosz2025beck}, and ImpossibleBench measured
it~\cite{zhong2026impossiblebench}. The METR study adds the human side: the
feeling of progress is an unreliable instrument~\cite{becker2025metr}. The
early-warning signals are the ratio of evidence artefacts to behaviour
changes, the share of merged pull requests that change what a user can do,
hedge density, and any divergence between automated scores and a live demo.

\subsection{Learning evaporation}\label{sec:m3}

\emph{Some recorded lessons appeared to fall off the loop's read path, while
important design decisions survived.} Maintaining the structured log and
memory became difficult as the record grew. I observed drift, not a complete
loss of the project's theory. Before the loop, my
use of the MVP produced concrete lessons: the simplicity requirements, a
deliberately public development profile for throwaway stacks, and the
callback, role and staff-binding steps that made sign-in work. All were
recorded, in the PRD, in a simplicity review and in infrastructure runbooks.
The coordinator's briefs carried each issue's text, acceptance criteria and
the repository conventions, but not those lessons. The log cites the
simplicity requirements for the last time on 13~October; the development
profile appears only on 8~October. The migrated deployment lacked the
registration and staff bindings established on 12~October, and sign-in was
blocked.

The read path itself decayed. The knowledge-base index, which every agent is
told to read first, accumulated 1,069 words of issue-specific status notes
ahead of its first instruction. The index, the log, the BRD and the PRD, the
documents that define the project's state and intent, total about 139,000
words, or roughly 180,000 tokens at a typical ratio of 1.3 tokens per word:
more than any agent can attend to reliably, even when it fits in its context
window~\cite{liu2024lost,hong2025contextrot}.

Naur explains why recording was not enough. A program's theory lives in the
people who build it, and a second team with full documentation can still
destroy a design's simplicity~\cite{naur1985theory}. In an agent loop, every
session is a second team. Advice to share full context between
agents~\cite{yan2025multiagents} and the failure modes catalogued for
multi-agent systems~\cite{cemri2025multiagent} describe the same risk. HVE
Core's choice to carry context in files on disk is necessary but not
sufficient: the files must be on the read path, short enough to read and,
ideally, executable. The early-warning signals are lessons that exist only as
prose, a read path that grows faster than the code, and problems that have to
be solved twice.

\subsection{Process-gate inflation}\label{sec:m4}

\emph{Each failure was answered with another gate, until governing a change
cost more than making it.} Gates are cheap for an agent to write and expensive
for everyone to run. Within ten days the coordinator required, for every
issue, the full RPI loop, a complete local gate before every push and after
every correction or rebase, independent review, up to two correction cycles,
board updates and evidence-based ticking of acceptance criteria. Hosted CI
minutes had to be rationed, the full gate had to be interrupted by explicit
exception for a two-line fix, and paid cloud validation stayed blocked even
after the cost ceiling was raised.

The scarcest resource was not compute but my attention. Eighteen merged pull
requests a day is more than any person can review in depth, so I delegated
merging to the coordinator. I still answered approvals and technical blockers,
but stopped getting feedback from using a replacement product. RPI critiques
and reviews addressed the current issue rather than the cumulative system;
there was no regular phase for reflective consolidation or generalisation
across completed issues. This is Bainbridge's irony in
miniature~\cite{bainbridge1983ironies}: the automation took the part of the
work I learned most from, using the product, and left me the part people are
worst at, monitoring a stream of plausible, well-documented changes. It
matches the shift from producing to evaluating reported for generative
AI~\cite{simkute2024ironies}, the delegation demands it
creates~\cite{tankelevitch2024metacognitive} and the erosion of critical
scrutiny that confidence in AI brings~\cite{lee2025critical}. Murphy's
diagnosis applies directly: the loop accelerated a non-bottleneck and filled
every queue behind it~\cite{murphy2026speed,goldratt1984goal}. Martin is right
that discipline must move into deterministic gates~\cite{martin2026outcodes};
this case adds that the gates must check the product's behaviour rather than
the process's paperwork. The early-warning signals are gate time per change,
human review minutes per merged pull request, work in progress, and cost per
merged pull request compared with cost per accepted outcome.

\subsection{Feedback starvation}\label{sec:m5}

\emph{The loop optimised for completing a specified plan, not for shortening
the path to the next piece of human feedback from a running increment.} This
is my proposed central mechanism, not an isolated cause. Nothing in the coordinator kept a usable system alive:
no invariant said that after every merge I must still be able to sign in and
do my work. Done meant artefacts, criteria and gates. In the MVP week the
feedback loop included my intermittent use, with some changes made the same
day. From 15~October the first priority was restructuring code, the
working MVP was frozen, and its replacement had not become usable by the time
of the case cut-off. When I
finally asked for something that runs, the request was absorbed by the same
machinery: a label, new issues, thirteen acceptance criteria and the full set
of gates.

Every older practice I cited in Section~\ref{sec:theory} exists to prevent
exactly this: short releases and test-first development~\cite{beck2004xp,beck2002tdd},
the walking skeleton and tracer
bullets~\cite{cockburn2004crystal,hunt1999pragmatic}, and working software
over comprehensive documentation~\cite{agile2001manifesto}. Beck's warning
that fully agentic work without feedback goes off the
rails~\cite{beck2026prodacity}, DORA's emphasis on small batches and user
focus~\cite{dora2025} and Murphy's list of real bottlenecks, which includes
missing feedback~\cite{murphy2026speed}, describe the same failure. The
early-warning signals are the time from the start of a cycle to the first
human use of a running increment, and the age of the last increment a human
has verified as usable. At the time of writing the latter was at least ten
days.

\subsection{How the mechanisms reinforce each other}

I interpret the mechanisms as a possible reinforcing loop
(Figure~\ref{fig:loop}). In this case a large specification accompanied a
large backlog and parallel sessions. Artefact-based gates generated more
documents; some recorded lessons were absent from later briefs; regressions
were not exposed through routine product-use feedback. I responded to gaps with more rules,
criteria and gates. That sequence is consistent with reinforcement, but does
not establish each causal link. I propose a running increment and a human
checkpoint as conditions of every cycle, to test whether they interrupt it.

\section{Feedback-first agentic delivery}\label{sec:feedbackfirst}

The remedy is not fewer agents or less rigour. It is to put the rigour where
the feedback is. Seven practices follow from the mechanisms;
Table~\ref{tab:practices} lists what each means in concrete terms and what to
watch.

\begin{enumerate}[leftmargin=*,label=\textbf{P\arabic*.}]
\item \textbf{A running increment is an invariant, not a backlog item.}
Before generating a backlog, build a walking skeleton that a human uses, and
make ``it still runs and I can still do my job in it'' a merge condition
checked by a scripted user journey on the real deployment. Never freeze a
working system before its replacement is usable.
\item \textbf{Small batches, a short horizon and capped work in progress.}
Generate a backlog for the next week or two, not for the whole product. Cap
parallel sessions and the number of acceptance criteria per issue, and turn
cross-cutting concerns into their own sequenced issues instead of appending
them everywhere.
\item \textbf{Human checkpoints on a fixed cadence.} Stop the loop every few
merges or every day for a demo. Decide what to keep, cut or tidy, and do not
start the next wave without a recorded decision. Alternate feature waves with
tidying waves, as Beck recommends~\cite{beck2026prodacity,beck2023tidy}.
\item \textbf{Executable learnings and a small read path.} Turn each lesson
into a test, a lint rule or an architecture fitness function within a day, and
keep a one-page set of standing rules in every brief. Cap the size of the
documents agents must read, archive old log entries, and keep agent working
memory out of the main branch, as HVE Core does by default.
\item \textbf{Proportional gates that check behaviour.} Run change-scoped
checks on every push and the full gate on merges to main or nightly. Gate on
what the product does, not on the presence of process artefacts. Require no
ceremony for trivial changes.
\item \textbf{Measure outcomes and treat automated scores as hypotheses.}
Track time to first human use, the age of the last usable increment, the
share of merges that change user-visible behaviour, hedge density, review
minutes per merge and cost per accepted outcome. Confirm any LLM-judged score
with a live demo before believing it.
\item \textbf{Keep the human as the theory builder.} Pair with the agent on
the first vertical slice; write or approve the acceptance examples that
define behaviour~\cite{fakhoury2024ticoder}; read the code of the core domain.
Use agents that challenge as well as
execute~\cite{sarkar2024challenge}.
\end{enumerate}

\subsection{A consolidation harness}\label{sec:harness}

The idea is already practised. OpenAI describes replacing weekly manual
clean-ups with recurring background agents that open small refactoring pull
requests, alongside a documentation-gardening agent~\cite{openai2026harness}.
Anthropic asks each session to leave a clean state and update a progress
file~\cite{anthropic2025harness}. Neither account reports a controlled
comparison. As far as I can find, consolidation between feature steps is
practised but untested in that sense. Section~\ref{sec:experiment} specifies
such a test; it does not report results.

Practices P3 and P5 suggest a narrower intervention that an agent can run
inside the loop, leaving human checkpoints to a coarser cadence, and that can
therefore be tested in isolation: a consolidation harness. After every feature
the loop stops, and an agent:
\begin{enumerate}[leftmargin=*]
\item runs the tests and a metrics script that lists complexity hotspots,
duplicated blocks and lint warnings;
\item reviews the last feature's diff and the hotspots against a short
checklist (duplication, long or complex functions, unclear names, dead code,
rules from one feature leaking into another, tests that check implementation
rather than behaviour);
\item refactors in small, behaviour-preserving steps, each applied through
\texttt{test \&\& commit || revert}~\cite{beck2018tcr}, so that every change
either keeps all tests green or disappears;
\item may add tests that pin current behaviour, but may not change or delete
the example tests that define the features;
\item rewrites a design note of at most 300 words that says where each rule
lives and what debt remains, replacing the previous one rather than
appending to it;
\item stops when a quality budget is met or its time budget runs out.
\end{enumerate}
Only then may the next feature start. Appendix~\ref{app:prompt} gives the
prompt.

The harness turns Beck's alternation of features and
futures~\cite{beck2026prodacity,beck2025devslow} and \emph{Tidy
First?}~\cite{beck2023tidy} into a gate, and follows Martin's advice to put
discipline into deterministic checks~\cite{martin2026outcodes}. It applies to
every feature what Lanzetta's sprint-boundary retrospectives apply to every
sprint~\cite{lanzetta2026orchestra}, and it spends part of the agentic
surplus on quality, as Lamanna's teams did~\cite{lamanna2026changing}. It
differs from the gates of Section~\ref{sec:m4} in what it checks: the
behaviour and shape of the code, not the presence of process artefacts. It is
not free, and it may not work. Agent refactorings are often wrong without
verification or merely superficial~\cite{gautam2025refactorbench}, and the
benefits of refactoring have been hard to attribute even for human
teams~\cite{kim2014refactoring,bavota2015quality}. Whether it slows the decay
is an empirical question, which the next section sets out to answer.

\paragraph{A checklist for Monday.} For an architect about to start an
agentic delivery loop, or already inside one:
\begin{enumerate}[leftmargin=*]
\item Can a human use a deployed increment today? If not, make that the only
priority.
\item Is ``still runs and is still usable'' checked on every merge, by a
script that exercises a real user journey?
\item Is the backlog horizon two weeks or less, with work in progress capped?
\item Does each issue have five or fewer acceptance criteria?
\item Is there a fixed checkpoint, with a demo and a recorded decision,
before each new wave?
\item Has every lesson from the last checkpoint become an executable check?
\item Can every document an agent must read be read in a few minutes?
\item Are gates proportional to the change, and do they test behaviour?
\item Do you know the cost per accepted outcome, not just per token?
\item Could you explain how the system works without asking an agent?
\end{enumerate}

\paragraph{Implications for framework builders.} Frameworks such as HVE Core
already encode much of this: human stops between phases, plan critiques and
context carried in files. Three additions would make the feedback-first path
the easy one. A review phase could include using the running increment, not
only reading the change. Artefact requirements could scale with the size and
risk of a change, so that a two-line fix carries a two-line record. And
lessons could have a first-class home as executable checks that every session
loads, with a warning when the documents on an agent's read path exceed a
budget.

\subsection{Design}

\emph{Arms.} Arm A delivers features one after another. Arm B runs the
consolidation harness after every feature, with half the time budget of a
feature step. B therefore has up to 50\% more agent time per feature than A;
the comparison is not time-matched. H5 compares their costs directly. I
include arm C, which holds that extra time constant without refactoring and replaces
consolidation with a read-only review
of equal budget, to compare the complete consolidation package with
review-only. B may add behaviour-pinning tests and writes an architectural
\texttt{DESIGN.md}; C cannot change tests and writes issue-oriented
\texttt{REVIEW.md}. Subsequent sessions read those different notes, so this
comparison cannot isolate refactoring. Everything outside the post-feature
intervention is identical: model and version, agent runtime, feature prompts,
starting skeleton, tools and per-feature budgets.

\emph{Runtime and budgets.} I selected \texttt{claude-sonnet-5.5}, medium
reasoning effort and Copilot CLI~1.0.103, with automatic updates disabled.
The wall-clock limits are 30 minutes per feature, 15 per consolidation or
review, and 45 for CR1. The pilot limit is 300 AI credits per session; any
pilot-informed adjustment must be frozen and included in the registered
configuration before the fresh study runs. The total pilot-and-first-pass
ceiling is 2,500 AI credits, raised from an initial 1,000-credit proposal.
I also stated a \$500 monetary budget. Credit consumption and currency cost
are not interchangeable without a verified billing conversion.

\emph{Suites.} Suite S1 is a ten-feature retrofit case workbench drawn from
the case domain, whose features deliberately interact: lifecycle, handoffs,
returns, safety holds, resident consent, appointments with an escalation rule,
role-based visibility, deterministic ranking and a hash-chained audit trail.
The selected study uses all ten features and the full CR1, including the
ranking and export prerequisites in F9--F10. Each feature has visible example
tests and hidden acceptance tests, including interactions with earlier
features. Tests and reference solutions are intended to remain outside the
agent's working repository. S2 is a library-lending suite reserved for a
separately authorised main study; benchmark adaptation is deferred.

\emph{Isolation.} I selected local execution rather than containers for the
analysed runs. The CLI access rules and separation of working directories
provide a weaker boundary than container isolation. They do not establish
that hidden tests, references or outside resources are unreachable. Residual
access risk limits validity and must accompany any results; an absence of
leak flags is not proof of isolation.

\emph{Procedure.} Every step runs in a fresh agent session, as in the case's
coordinator, so that context travels only through the repository. A feature
step may commit only when the visible tests pass. If it commits no green
increment, the runner resets it, removes that feature's example tests and
counts the feature as missing. Its hidden tests remain in the denominator.
After every step, the external measurement process
runs the cumulative hidden suite, which covers every feature scheduled so
far, including missing features, and collects the metrics. A pilot calibrates
budgets with one run per arm over ten features, without CR1. The selected
first pass uses S1, arms A, B and C, with four independent runs per arm,
ten features and CR1. This is the planned registered comparison, not data to
pool with earlier started runs. An optional main study would use S1 and S2,
five runs per arm and ten features, under a separate prospective plan and
authorisation. With three runs per arm
the exact two-sided Mann--Whitney floor is $2/C(6,3)=0.10$, so it
cannot reach $p<0.10$; four runs reach 0.029 and five reach 0.008. These are
attainability bounds, not a power analysis. The selected first pass has
120 feature, 40 consolidation, 40 review and twelve change-request sessions:
212 sessions and an upper bound of 89 agent-hours. The pilot adds fifty
sessions and twenty agent-hours, making 262 sessions and 109 agent-hours
combined. These bounds exclude measurement and scheduling overhead and do
not establish affordability under the credit ceiling. Sample sizes and
stopping rules must be registered before the fresh confirmatory runs;
sample sizes will not be increased in response to observed effects.

\emph{End state and change request.} H1's end state is after the last
feature's post-feature step (a no-op in A), before the change request.
Change-request success requires all its hidden tests to pass and no feature
test that passed at that end state to fail afterwards.

\emph{Measures.} Cumulative hidden pass rate, open regressions and how long
they survive; mean cyclomatic complexity, the share of functions above
complexity 10, duplicated lines and lint warnings per thousand lines;
non-test lines, diff lines per step and documentation words generated; AI
credits as the primary consumption measure, with tokens and elapsed time
secondary; change-request success and cost; and,

questions about each final code base. Test integrity, through checksums of the
example tests and counts of tests and assertions, is checked after every
step. The planned code-metric settings are the runbook's isolated lint rules
E, F, W, C90, B and SIM, duplication detection at fifty tokens and five lines,
and complexity measured by lizard. Tool versions and settings must be fixed

\emph{Intervention measures in prior work.} Intervention-based robot learning
provides useful measurement precedents. In
HG-DAgger, the human decides when to take control, provides an uninterrupted
corrective trajectory and explicitly returns control to the learned
policy~\cite{kelly2019hgdagger}. ThriftyDAgger distinguishes the number of
interventions, human actions and robot actions per episode, alongside
autonomous and intervention-aided success~\cite{hoque2022thriftydagger}.
Its supervisor-burden model separates switching overhead from the length of
assistance: $B(\pi)=C(\pi)[L+I(\pi)]$, where $C$ is the expected number of
switches from autonomous to supervisor control per episode, $L$ is the
round-trip switching latency and $I$ is the expected number of supervisor
actions per intervention. Latency is expressed in action timesteps, not
coding-agent tokens. Fewer interventions can therefore coexist with longer
human involvement; continuous monitoring is another burden not captured by
active correction time alone.

These studies motivate separating intervention incidence, frequency and
effort, but are not evidence of coding-harness effectiveness. A frequency
such as events per hour uses exposure time as its denominator; a human-control
share uses human-controlled timesteps divided by all timesteps. Neither is
the same as the proportion of tasks needing help. I adapt the latter to
feature cycles and state the denominator explicitly, rather than claim one
universal HIR formula. I retain failed cycles, unlike ThriftyDAgger's
successful-episode summaries in its main evaluation; its supplement also
reports totals over all trajectories.

\emph{Human intervention rate (HIR).} As a secondary measure of harness
quality, I record observed HIR: the proportion of attempted feature cycles
receiving unplanned corrective human help. A cycle includes the feature and
its assigned post-feature step, so B's additional sessions do not enlarge
its denominator. Failed cycles remain included; repeated interventions in a
cycle count once for the rate, with event counts recorded separately.
For run $r$, let $n_r$ be the number of attempted feature cycles and $h_{rj}$
the number of qualifying corrective-help events in cycle $j$. Then
\begin{equation}
\mathrm{HIR}_r
= \frac{N_{\mathrm{assisted},r}}{n_r}
= \frac{1}{n_r}\sum_{j=1}^{n_r}\mathbf{1}\{h_{rj}>0\}.
\label{eq:hir}
\end{equation}
The indicator is one when the condition holds and zero otherwise; multiplying
Equation~\ref{eq:hir} by 100 gives a percentage. By contrast,
$\sum_j h_{rj}/n_r$ is events per cycle and can exceed one. I report event
counts and active human minutes separately so that a brief clarification and
a long repair do not appear equivalent merely because both affect one cycle.
These are incidence and effort measures, not interchangeable estimates of
total supervisory workload. If no cycle is attempted, the rate is undefined,
not zero.

Primary runs receive no task-specific human coaching or code/test repair.
I therefore also record an intervention-demand rate with the same denominator:
cycles containing an explicit request for such help or a block requiring
manual corrective action. With $d_{rj}=1$ for such a cycle and zero otherwise,
\begin{equation}
\mathrm{IDR}_r = \frac{1}{n_r}\sum_{j=1}^{n_r}d_{rj}.
\label{eq:intervention-demand}
\end{equation}
A request need not result in assistance, and an unsolicited human correction
need not follow a recorded request; I code the two separately. Zero observed
HIR under this policy is not evidence of autonomy. A timeout or automatic
reset alone does not establish demand.

The intended sources are the session telemetry and retained logs. I plan to
use Cowork to extract requests, blocks and actual interventions, then personally
check classifications against source records and resolve ambiguous cases.
The extraction must link each event to its cycle, phase, reason, action and
active human minutes, using rules fixed before fresh confirmatory runs.
Telemetry coverage of human-help requests and corrective actions, including
actions outside the CLI, has not yet been verified. Missing records cannot
be interpreted as zero interventions; incomplete coverage makes the affected
measure not evaluable. Routine launches, planned evaluation, required approvals and
safety stops are recorded separately, not treated as corrective rescue.
Any corrective help supplied is a protocol deviation; I retain the run,
label it assisted and report its outcomes separately from unassisted estimates.
Such deviations do not trigger replacement runs and may leave the confirmatory
comparison not evaluable at its predeclared sample size.
I report change-request interventions separately, alongside completion,
missing features, early termination and unattempted cycles. Lower HIR alone
is not better: it must not reward silent failure or discourage necessary
human judgement.

\subsection{Analysis and bias controls}

The difference in final cumulative pass rate is estimated with bootstrap
intervals that resample runs within arm. S1 trends are estimated with
mixed-effects models that include an arm-by-feature-index interaction and
run as a random intercept. A later multi-suite study would treat suite as a
fixed effect and resample within suite and arm. Because code generation is not
deterministic, even at temperature zero~\cite{ouyang2025nondeterminism}, every
condition is run several times and intervals are reported rather than single
values. The S1 first pass has a fixed sample size; pilot and all
pre-registration runs are excluded from its confirmatory analysis. A later
main study would also exclude those earlier data. Overlapping
intervals do not trigger extra confirmatory runs: any extension is separately
labelled exploratory and is not pooled into the original analysis. For H1,
validation requires a gain of at least 10 percentage points and a 95\%
interval wholly above zero; invalidation requires its upper bound to be below
5 points. All other evaluable H1 outcomes are inconclusive and route to
adjust, not no-go. For every hypothesis, validation requires the estimate
to meet its stated threshold and the 95\% interval for the benefit to exclude
zero in the beneficial direction. Invalidation requires the whole interval
to fall short of the stated minimum effect of interest, applying the joint
or alternative conditions in Table~\ref{tab:hypotheses}; absence of significance
is not invalidation. For H5 I assess headroom below the 150\% cost ceiling
and late-feature savings, while retaining the 125\% validation threshold.
An interval spanning zero, without ruling out a useful effect, is
inconclusive. The planned controls are randomised interleaving of arms on
the same machine; frozen hidden tests, metrics and analysis before fresh
registered runs; exclusion of pilot data; blinded comprehension assessment;
reporting of every run; and a divergence log. Independent suite review,
verified access boundaries and the final analysis checks are still pending,
not completed safeguards. Each hypothesis is recorded as
validated, invalidated, mixed, inconclusive or not evaluable, and the
decision as go, no-go or adjust.

HIR is descriptive, with no new hypothesis threshold or adoption gate. I
report observed and demand rates per run, human minutes and the B--A demand-rate
difference with a 95\% interval, resampling whole runs within suite and arm.
The rates accompany correctness and cost, rather than replacing them.

The protocol uses one proprietary model and no open-weights baseline. This
limits reproducibility and transfer to other models; pinning the exposed
version does not freeze a provider's service~\cite{baltes2026guidelines}.

\section{Discussion: the existential crisis, revisited}\label{sec:discussion}

\subsection{What worked}

It would be wrong to read this case as a failure of agents. The research phase
assembled, in days, a corpus and analysis that would have taken me weeks. The role agents' challenge
killed a bad idea, five end-to-end agents, before any code was written. The
agents refused to invent approvals, figures or company facts, and recorded
the limits of their evidence with a care many human teams lack. The MVP was
built and reshaped in a day. Each of these successes had the same shape: a
short loop with a human in it.

\subsection{What remained mine}

Looking back over six weeks, the parts of the work no agent did were these. I
decided what not to build. I noticed that something was wrong, not from the
reports, which were accurate and full of caveats, but from the plain fact
that I could not use the system. I held the theory of the system, in Naur's sense:
which lessons mattered and why the sign-in had worked on 12~October. And I was
the person responsible for designing the feedback loop and deciding what
useful feedback would look like in this case.

That is close to Beck's distinction between a discipline's visible output and
the less visible work of understanding, simplifying and building
abstractions~\cite{beck2026mathematicians}, and to Martin's insistence that
programmers still write the tests first and know their
customers~\cite{martin2026productengineers}. The agents were excellent at the
visible part. They produced proofs of work: pull requests, artefacts,
receipts and honest caveats. In this case those records did not replace the
understanding I gained from using a running system. That does not establish
a general limit on what agents can do.

\subsection{The crisis reframed}

The existential question is usually put as whether machines will replace
developers. This case suggests a narrower and more useful one: will
developers notice when the machine is producing everything except the thing
that matters? Speed of generation is no longer scarce. What is scarce is
feedback: designing it, protecting it from the volume of activity around it,
and interpreting it. That is a job, and it is a technical one. It needs the
old skills, testing, small steps, tidying and walking skeletons, applied to a
new kind of team. Beck's 2023 recalibration was about which ten per cent of
his skills gained leverage~\cite{beck2023ninety}; in this case, the skills
that mattered were the ones that keep a feedback loop short. Lamanna's advice
to judge AI by the same business outcomes as before~\cite{lamanna2026changing},
and Lanzetta's description of the engineer as the architect of intent who
builds the system in which agents work~\cite{lanzetta2026orchestra}, point in
the same direction.

\section{Threats to validity}\label{sec:threats}

\emph{Construct validity.} Word counts and a hedging lexicon are crude proxies
for documentation load and for the content of status records, and a
proportion of hedged statements is appropriate caution. I report them as
indicators, alongside qualitative evidence, not as measures of quality.

\emph{Internal validity.} I designed the coordinator and its gates, so the
outcome reflects my configuration as much as the framework or the models.
HVE Core's defaults (a manual mode, human stops and git-ignored tracking
files) point the other way; I overrode them. The two periods differ
in length and in the work attempted, model and tool versions changed during
the study, and other work on the capstone, such as presentations, ran in
parallel.

\emph{External validity.} This is a single case: one developer, a fictional
but regulation-heavy domain, and a capstone whose rubric rewards
documentation as well as software. Teams with dedicated product owners, users
or operations staff may experience the mechanisms differently. The field
observations in Section~\ref{sec:field} suggest the mechanisms are recognised
elsewhere, but they are not evidence of prevalence.

\emph{Reliability and researcher bias.} The repository, issues and log are

coding. AI assistance in analysis and drafting is

\section{Conclusion}\label{sec:conclusion}

An autonomous, spec-driven agent loop can produce an enormous amount of
software engineering activity, requirements, plans, reviews, receipts and
merged pull requests, without producing software that its owner can use. In
this case the evidence points towards a configuration that measured progress
by artefacts, answered failures with more gates, kept lessons in prose, and
had no invariant requiring a usable system. It does not rule out the rival
explanations or establish that model capability was irrelevant. These
patterns fit old lessons of software engineering; I propose that agentic
throughput can amplify them. My practical response is to make
feedback the primary output of every cycle: a running increment, a human
checkpoint and executable lessons. The developer's role does not disappear in
that model. It moves to where it always mattered most: deciding what is worth
building and finding out, as quickly as possible, whether I built it.

I have also argued something that can be refuted. If software that only
accumulates features decays, and agents accelerate the decay through
compounding errors and unreviewable volume, then a harness that consolidates
after every feature should keep agent-built software working, understandable
and changeable at an acceptable cost. Section~\ref{sec:experiment} sets out
how to find out. Whatever the result, it will say more than another week of
merged pull requests.

\section{Measures and lexicon}\label{app:measures}

\paragraph{Log entries.} The knowledge-base log
(\texttt{docs/reference/log.md}) was split into entries at each second-level
heading that begins with a date. An entry belongs to the date in its heading.
Word counts use whitespace tokenisation of the entry, heading included.

\paragraph{Hedging phrases.} Each entry was searched, case-insensitively and
on word boundaries, for these patterns: \emph{unmet}; \emph{not accepted};
\emph{not inferred}; \emph{is inferred}; \emph{remain(s) open};
\emph{remain(s) unproved}; \emph{remain(s) unverified}; \emph{not claimed};
\emph{not established}; and \emph{no} followed, within forty letters, spaces,
commas, slashes or hyphens, by \emph{is} or \emph{was} and then
\emph{claimed} or \emph{inferred}. Density is matches per 1,000 words.

\paragraph{Reference tracing.} An entry cites the simplicity requirements if
it contains an identifier from SA-001 to SA-010 or the word
\emph{simplicity}. It cites the development profile if it contains
\emph{deploymentProfile}, \emph{development profile} or
\emph{allowPublicNetworkAccess}.

\paragraph{Repository counts.} Issue and pull-request counts come from the
GitHub search API on 24 October 2026 (for example,
\texttt{is:pr is:merged merged:>=2026-10-15}). Document sizes are whitespace
word counts of the files at commit \texttt{29c6b51}.

\paragraph{Proposed measures.} \emph{Time to first human use}: elapsed time
from the start of a delivery cycle to the first time a person uses the running
increment for its purpose. \emph{Age of the last usable increment}: time since
a person last verified that the deployed system could be used for its main
journey. \emph{Behaviour-changing merge ratio}: the share of merged pull
requests that change what a user can observe in the running increment.
\emph{Cost per accepted outcome}: total model, tool and cloud cost divided by
the number of outcomes a human accepted in the same period.

\section{Consolidation step prompt}\label{app:prompt}

The prompt used for the consolidation step of arm B (Section~\ref{sec:harness}).
Braces mark parameters set by the experiment runner.

{\small
\begin{verbatim}
Do not add or change features. Your job is to leave the code better than
you found it without changing its behaviour.

1. Run `make check`, then read reports/quality.md (functions above
   complexity 10, duplicated blocks, lint warnings, file sizes).
2. Review the last feature's diff (`git diff feature-start feature-end`,
   tags the runner sets around each feature step) and the hotspots
   against this checklist: duplicated logic; long or complex functions;
   unclear names; dead code; responsibilities in the wrong place, or
   rules from one feature leaking into another; tests that check
   implementation details instead of behaviour.
3. Make small, behaviour-preserving changes. Apply every change through
   `./tcr "<message>"`: it runs all tests and commits if they pass, or
   reverts if they fail.
4. Never modify or delete files in tests/examples/. You may add tests that
   pin current behaviour before you refactor.
5. Rewrite DESIGN.md in at most 300 words: the current structure, where
   each business rule lives, and known debts. Replace; do not append.
6. Stop when the quality budget is met (no function above complexity 10,
   duplicated lines below 3%, zero warnings in the configured lint rules)
   or when your time budget ({consolidation_budget}) is used.
7. Finish with a summary of at most five lines: what you changed and what
   debt remains.
\end{verbatim}
}
