\begin{abstract}
After refining requirements and testing prototypes, I used coordinated
coding agents to turn an early prototype into a fuller product.
The new application passed local checks, but I could not sign in.
What does each feature leave
for the next one? A case analysis examines five possible mechanisms alongside
migration and configuration failures.

We tested a standard-library Python task with three models, each completing
21 development runs in every condition: feature-only delivery,
consolidation, read-only review, longer sessions and visible-specification
repair. Each run started with a fresh repository and received ten features
and a withheld change request.
A separate evaluator ran hidden tests in isolated containers after each
step; post-collection replay checked earlier workflows.

All 315 allocated runs finished. Under rollback and protected-test
rules, one ended with a test of earlier behaviour failing; replay found
no losses of previously passing workflows in 626 evaluable checkpoints. Consolidation left no function
above cyclomatic complexity ten at its 63 final checkpoints. Its
hidden-test coverage gain over longer sessions, averaged equally across models, was 1.19 percentage
points (conditional 95\% bootstrap interval [0.10, 2.22]). The longer-session
controls left room for at most 3.04 points of improvement, making the pre-specified ten-point
target unattainable against them. Consolidation used 1.84--2.25 times the
delivery credits of feature-only work in fully billed subsets.

Unregistered amendments, uncertain independence between runs, two unresolved
change-request outcomes, 55 billing holds and judging on an earlier
313-run snapshot limit inference. The main failures were incomplete
features and later permission failures, rather than widespread loss of
earlier behaviour. Structural cleanup did not establish easier or cheaper
adaptation.
\end{abstract}

\noindent\textbf{Keywords:} agentic software engineering; coding agents;
spec-driven development; software evolution; technical debt; refactoring;
feedback loops; human-AI interaction; exploratory case study; experiment protocol.

\section{Introduction}\label{sec:intro}

I was developing a product from a supplied housing-retrofit use case:
helping staff coordinate energy-efficiency work on residents' homes.
I used the HyperVelocity methodology to take an early prototype toward a
product close to production readiness, while leaving out some non-essential
production requirements. I wanted to keep what already worked.
Short exchanges with agents had produced a prototype and a Minimum Viable
Experiment (MVE) in a few hours, including working sign-in. I used those
results to refine the business and product requirements documents (BRD and
PRD), then gave a coordinator and parallel workers a formal backlog to
implement autonomously. My account records 47 completed issues out of more
than 180 in the first 5 days. I could inspect completed issues and passing
checks, but when I opened the replacement to provide feedback, I could not
sign in to the new application.

The immediate problem was a blocked deployment and sign-in
workflow. Yet it raised a question about the accumulated system as a whole:
when a change passes its local checks, what evidence shows that the next
change inherits working software?

Software development had this problem long before coding agents existed, as
public post-mortems and classic maintenance accounts show. On the 1st of
August 2012, for instance, Knight Capital's automated router sent millions
of orders and obtained more than four million executions while processing
212 customer orders, costing the firm more than USD~460 million. The SEC
traced that public incident to a defective function left in the router after
a 2005 change, an incomplete deployment for a new trading programme across
one of eight servers, and inadequate controls; the new deployment activated
old code that was no longer meant to run~\cite{sec2013knight}. The failure
crossed a feature boundary and a seven-year interval, so understanding it
required examining the code and deployment state that the new programme
inherited.

Cunningham's 1992 account of WyCash described a financial product
continually adapted to market demands, where mature code was repeatedly
revised and rewritten; his technical-debt metaphor explained why shipping a
first-time implementation required later rewriting as understanding
improved~\cite{cunningham1992wycash}.

The external PhotoCraft project, an early-alpha reimplementation of
Photoshop, reports 631 of 631 menu items live, while its dated
assessment separately estimates about 76\% feature breadth and 45\%
readiness for real work~\cite{photocraft2026}. SWE-Maintain finds that agents solve
fewer later tasks when starting from their own earlier changes than from
the developers' changes, even though each task starts in a fresh
session~\cite{pan2026swemaintain}.

Established engineering practice has a long answer to inherited faults:
define which behaviour a change must preserve, test it, and keep the
running increment available for feedback. Refactoring can then change
the implementation while those contracts continue to hold
~\cite{parnas1994aging,beck2002tdd,beck2004xp,fowler2007stamina}.
Anthropic's long-running-agent example makes this concrete: before adding
a feature to a chat application, the next session starts the server,
opens a new chat, sends a message and checks for a response
~\cite[Getting up to speed]{anthropic2025harness}. That check asks whether
the previous session left a usable application for the next
change.
Recent discussions by Beck and Fowler revisit these concerns for
agent-assisted work~\cite{beck2026prodacity,fowler2025thoughts}.
Beck's distinction between producing code and learning through working
software sharpens the research question~\cite{beck2026prodacity}:
what does a feature leave behind for the next one?

Before asking the coordinator to implement the backlog, I had spent weeks
working through the requirements with the agents and recording our decisions.
Research agents maintained the
evidence base. In one what-if exercise, I asked whether phone photos with
GPS metadata would make an assessment agent more useful; the resulting
proposal still required checked provenance and a professional decision.
Persona and journey work examined who would take over a case when
information or approval was missing. Disposable pilots and prototypes
exposed workflow problems before a usable minimum viable product (MVP)
emerged, and a backlog agent
translated the resulting requirements and architecture decisions into epics
and user stories.
I expected the agents to build the product faster and make fewer mistakes
because we had already questioned and revised the requirements.

My attempts to use the new application changed what I asked the coordinator
to do next: provide a running website, fix the missing workflow and refactor.
The case analysis follows those requests to see where preparation and local
completion checks failed to preserve the workflow I needed.
The repository, pull requests, append-only log and versioned coordinator
instructions retain that evolving record~\cite{servera2026ama};
the source package pins the evidence used here. The repository may be
temporarily unavailable during the experiment embargo, after which the
approved history and context are intended for release.
My earlier experience on a separate book-search project (Aithena, with PDF
ingestion and a browser interface, discussed in the supplement) and the
external PhotoCraft inspection selected after the motivating-case analysis
have separate provenance in the ancillary
\nolinkurl{anc/supplementary-context.md}.

The initial conjecture was that feature-driven delivery carries
unresolved errors and avoidable change burden forward, and that cumulative
verification and consolidation can reduce that burden. I distinguish
the software being changed from the instructions used to change it. In this case, my
instructions grew to require the full research, plan, implement and review
(RPI) sequence, committed evidence
and recurring checks (Section~\ref{sec:coordinator}). Section~\ref{sec:background} separates these
pathways; the case then examines how they interact with completion proxies,
review capacity and product-use feedback.

Stable behaviour would count against the conjecture under the tested
conditions. A single regression would provide little evidence of progressive
decay. Here
\emph{feature-driven decay} means a measurable loss of previously passing
behaviour or a rising cost and failure burden across sequential changes.
The separate experiment asks agents to build the same small Python
package, called S1, through ten features and then complete a withheld
change request (CR1). It compares feature-only work (A), consolidation (B),
read-only review (C), longer feature sessions (D) and repair against visible
specifications (E). A \emph{contract} is a required behaviour checked by a
fixed hidden test. The analysis separates the \emph{decay premise} from
the \emph{consolidation remedy} through three predictions and a check of
whether consolidation actually changed the code:

\paragraph{P1 (Short-horizon decay premise).}
Without a dedicated
post-feature pause (Arms~A and~D), sequential delivery across ten features
induces progressive behavioural loss by the final feature checkpoint
($P_{10}$): previously passing contracts still fail, failures accumulate
across cycles, or replayed workflows lose earlier capabilities.

\paragraph{P2 (Primary coverage gain threshold).}
Scheduled consolidation (Arm~B) exceeds the matched-allowance longer-session control
(Arm~D) in equal-model-weight final hidden-test coverage at $P_{10}$ by at
least the pre-specified minimum useful effect of $\Delta_*=10$ percentage
points (Section~\ref{sec:protocollimits}).

\paragraph{P3 (Change-request adaptability and short-horizon payback).}
Consolidation (Arm~B) raises held-out CR1 success and reduces CR1 or net
credit expenditure relative to feature-only delivery (Arm~A), read-only
review (Arm~C) and longer sessions (Arm~D).

\paragraph{Manipulation check (Structural treatment fidelity).}
Consolidation reduces functions above cyclomatic complexity 10, duplication
and lint density toward its stopping targets. This check asks whether
the intervention changed structure before the behavioural
results are interpreted.

The results changed my interpretation of the case. Most acquired behaviour
survived, and structural cleanup produced a coverage gain below the practical
benchmark (Table~\ref{tab:predictionverdicts}). The analysis therefore
separates features that were never implemented from regressions and from
failures exposed when a new requirement crossed an existing boundary.

Only $\Delta_*=10$ percentage points was fixed in the pre-collection
planning calculation. The public execution manifest
(\nolinkurl{protocol/pilot-estimation.json}) left its formal hypothesis
array empty, so the operational criteria in P1 and P3 structure the
post-collection evaluation and do not amount to a preregistered
confirmatory test.

Three questions guide the investigation:

\begin{itemize}[leftmargin=*]
\item \textbf{RQ1.} How can the code and instructions left by one feature
carry errors or make the next feature harder to implement, and what does
existing evidence show about that problem?
\item \textbf{RQ2.} What could explain the gap between completed issues and
an application I could use in the motivating case, and which competing
explanations does the delivery record support?
\item \textbf{RQ3.} Does scheduled agent-led consolidation after each feature
improve retained behaviour and future changeability, and at what cost?
\end{itemize}

\noindent The investigation moves from earlier studies to my project and
then to a separate coding experiment:

\begin{enumerate}[leftmargin=*]
\item I review earlier studies of errors carried through conversations,
inherited code and maintained instructions, including published comparisons
of agent-written and developer-written histories (Section~\ref{sec:background}).
\item I trace the move from questioning requirements with agents to
coordinated feature delivery, then my return to trying the product and
requesting fixes. Five possible explanations are examined against episodes
in the delivery record
(Sections~\ref{sec:method}--\ref{sec:mechanisms}).
\item We test scheduled consolidation in a 315-trajectory, five-arm
exploratory study, then replay earlier workflows and have a separate AI
judge rate the execution evidence. The results distinguish implementing a
feature from preserving it and adapting it later. The study also exposed
a task too easy to demonstrate the planned coverage gain and incomplete
billing. Its earlier planning drew on the registered-report example of
Lulla et~al.~\cite{lulla2026protocol} and HVE Core's Minimum Viable Experiment method
(Sections~\ref{sec:harness} and~\ref{sec:experiment}).
\end{enumerate}

The case concerns a migration and a configuration I designed, including
delegated delivery and merge decisions. It suggests hypotheses whose
causal relationships remain to be tested. The primary comparison measures the combined effect of consolidation,
added tests and a handover note against a control with the same time and
nominal-credit limits. The B--A comparison adds resources as well
as consolidation and is secondary. Equal limits need not produce equal spending,
and the design does not isolate refactoring or validate the five case
mechanisms individually. A registered base, which I confirmed, and disclosed
unregistered amendments frame the completed exploratory collection.
All 315 allocated trajectories are complete and owner-attested unassisted;
the execution record preserves interruptions and recoveries. Sections~\ref{sec:threats}
and~\ref{sec:protocollimits} consolidate the case's validity and the pilot's
identification limits.

\section{Case and method}\label{sec:method}

\subsection{Setting}

For this architectural training exercise, I took on the roles of
architect, developer and product owner.
The supplied use case concerned a housing association coordinating retrofit
work. The application used synthetic cases to connect documentary evidence
and approvals with staff and resident actions. A staff member
needed to sign in, open an assigned case and record a resident decision
separately from the staff decision to release work. An assistant could
prepare a draft, but nothing was sent automatically. The exercise
required research, requirements, architecture, a delivery plan and a working
version of the product. No operational
service or real resident data is evaluated here.

Agents performed most research synthesis, drafting and coding; I steered
scope and decisions. Several weeks of discovery and
requirements work preceded roughly a week of interactive MVP development
and a ten-day autonomous delivery window. The project continued afterward;
its current state and detailed chronology belong to the versioned repository
record~\cite{servera2026ama}.
An automated repository scorer also reported implementation completeness
(Section~\ref{sec:audittrail}).

\subsection{Workflow and tools}

GitHub Copilot and HVE Core first helped me learn what to
build. Research agents assembled source snapshots and maintained syntheses
in a knowledge base with an index, owner-curated memory and an append-only
log (\nolinkurl{anc/case-evidence-matrix.json}, author-review discovery
and handoff entries).
The Design Thinking coach and stakeholder-role agents then challenged
assumptions by asking what would happen under different conditions, examining
users' responsibilities and walking through their tasks.
For example, a photo's GPS metadata could support the location of a survey,
but did not establish whether the evidence was sufficient for a retrofit
assessment. The proposed assessor would check the evidence bundle and retain
professional approval. Role-agent answers remained hypotheses for the
exercise; direct stakeholder research was still needed.

As understanding changed, BRD and PRD builders, quality review and the
architecture decision record (ADR)
assistant helped turn conversations and owner decisions into revised
requirements and architecture records. Disposable pilots and prototypes
made candidate workflows tangible. Critiques and my product-use feedback
informed a deployed MVP that I used intermittently and refined
through short feedback loops. Its landing view was
\textquotedblleft{}My cases today\textquotedblright{};
case cards showed status and the next action, while a call log and manual
paths let work continue without a model response. These features are
recorded in the historical log and prototype review identified in the
case evidence index; my intermittent MVP use remains a participant account.

The handoff to autonomous delivery changed how that understanding reached
implementation. A backlog agent converted the accumulated context into
epics, features and user stories, including acceptance criteria, dependencies
and indications of existing MVP coverage. Some stories exposed scope that
still needed requirements reconciliation. A custom coordinator dispatched
implementation and review against this evolving backlog
(Section~\ref{sec:coordinator}).

I expected this preparation to shorten planning because each feature's
purpose and constraints had already been discussed. The documents and
conversations show what workers were asked to build and reviewers were
asked to accept. They cannot establish a speed or quality gain: I did not
compare the work with a human-only team or another planning approach.

\subsection{The coordinator}\label{sec:coordinator}

The coordinator ran through Copilot CLI on a VM\@. It selected dependency-ready
issues and launched parallel worker sessions in isolated git worktrees,
so workers could change their own copies without editing the same files.
Each worker received an issue and HVE Core's research, plan, implement and
review (RPI) workflow. The coordinator checked the resulting pull request,
updated the project board and, under owner delegation, merged changes.
Interactive and CLI model configurations changed during the project;
recorded selectors and recalled interface labels are distinguished in the
source package. The delivery record therefore describes a workflow that kept changing.
Read-only recovery of the original coordinator history corroborates my
requests for RPI tracking, tmux workers and recurring checks, followed by
migration, budget and functional-checkpoint decisions. Later committed
instructions selected \texttt{claude-sonnet-5.5} for worker launches while
leaving the coordinator on Automatic. Actual historical CLI versions,
reviewer models and backend builds remain unavailable in the inspected
records. The evidence index distinguishes prescribed selectors, stored
instructions and assistant-reported outcomes.

Early worker sessions implemented directly, prompting me to make
the full RPI sequence and committed tracking artefacts mandatory. Further
instructions required evidence-backed acceptance ticks, scheduled monitoring
and increasingly extensive local gates. My recorded migration instruction
was ``build all new in src, but migrate what's needed first''
(\nolinkurl{anc/case-evidence-matrix.json}, coordinator turn 66).
Human decisions, approvals,
credentials and unresolved review findings could still block work. At the
same transition, an accepted architecture decision prioritised migration
to a new source layout and froze feature work in the MVP\@. Coordination,
migration and procedural requirements all changed at once.
The recovered history also contains repeated scheduled prompts, so a
message stored in the user field cannot automatically count as a human
intervention. Supplement Section~\ref{app:deferredmeasures} records the
selection rule and explains why the human-intervention and
intervention-demand rates (HIR and IDR) remain unestimated.

\subsection{Data and analysis}

This exploratory single-case study follows the transition from interactive
discovery and MVP use to delivery through issues dispatched by a coordinator. I selected
the case after encountering the unusable replacement and acted as
participant-observer. Case-study guidance and the ACM SIGSOFT Empirical
Standards inform the account~\cite{runeson2009guidelines,sigsoft2021standards}.

The original analysis and later follow-up use separate repository snapshots
(source records \sourceref{R01} and \sourceref{R02} in the end register).
Sources include the knowledge-base
log and index, requirements, architecture decisions, coordinator definition,
issues, pull requests and retained RPI records. My review adds
process clarification and an export of project issue states, retained as
\nolinkurl{anc/project-insights-2026-11-01.csv}. Source dates, historical
counts and extraction rules remain in the ancillary records. The main
account uses them to reconstruct the sequence and handoffs.

I analysed descriptive measures, traced references to recorded lessons and
used AI assistance to interpret selected episodes. I did not systematically
code every log entry or review every specification. Early entries were
reconstructed from history; later entries were written during the project.
The evidence record distinguishes my recollection from committed source and
execution observations. It also records missing links between assessment
scores, releases and deployed tasks.

External repositories and literature were selected for relevance to
inherited faults, instruction maintenance and outcome verification.
They supply contextual comparisons and a focused narrative synthesis.
The published-evidence figures reproduce reported values with source
locators; the external applications and original studies were not rerun.
The ancillary observation record preserves its purposive issue sample,
exclusions and retrieval boundaries. These sources are analysed separately
from the motivating project.

\subsection{What the study measures}\label{sec:constructs}

Here an \emph{agent} combines a model, tools and instructions in a loop that
selects and executes actions. In the case, I retained scope decisions,
approval and delegated merge authority (Section~\ref{sec:coordinator});
the human authors retain responsibility for this study.
A \emph{skill} is a reusable set of procedures describing when and how to
act and check the outcome. It differs from a session history and does not
update model weights. This distinction follows
Jiang et~al.~\cite[Sec.~1]{jiang2026skills}. The pilot retains a handover
note as context; it does not vary skill use as a separate treatment.

\emph{Working behaviour} means completing an intended task through the
running system, including the identity, data and service dependencies needed
for that task. In this case, rejecting an unauthenticated request did not
show that an authorised staff member could sign in and open a case.
\emph{Decay} denotes loss of previously working behaviour or
increasing difficulty of understanding and changing a system. The case
records lost usability during replacement; any decline in intrinsic code
quality remains unmeasured. Deployment drift could produce the same observation.
\emph{Adaptability} was defined in the prospective design as success and cost
on the unforeseen change request under a fixed budget. This measures one
aspect of maintainability\@. \emph{Consolidation} means scheduled structural work intended
to preserve observable behaviour, with tests checking that intention.
The later CR1 view-write failures exposed behaviour that the earlier
workflow panel did not check (Section~\ref{sec:resultsjudging}).

Five measurement categories remain separate. PRs, lines and words describe
\emph{production volume}; checks, reviews and receipts describe
\emph{validation activity}; observed user tasks describe \emph{system
behaviour}; code metrics and the change request probe \emph{internal quality
and changeability}; and corrective help requested or supplied describes
\emph{intervention}. The original observations cover the first three categories. A later
post-hoc comparison adds code metrics as indirect measures of structure,
but no controlled changeability task or systematically coded intervention
dataset.

\subsection{Building the epics and user stories}

Preparation took sustained steering, with no single specification
prompt. I first asked whether better inputs would change the proposed
agents' responsibilities, then asked for distinct scenarios rather than
one photo/GPS example. The retained study considers structured invoices,
contractor-capacity feeds and sensor-validity metadata as well.
The desk-research journey atlas subsequently informed BRD and PRD revisions
and ADR~0003, while leaving quality and approval questions open.
The case evidence index records these exchanges and the requirements
handoff under its author-review context, including PR~\#71;
none was direct stakeholder validation.

Disposable prototypes then made some assumptions tangible. My critique
and an agent-assisted simplicity review produced requirements for
clear ownership, a visible next action, understandable blockers and manual
paths that remained usable without AI\@. The retained prototype review
also records a re-acceptance defect after handover, outside the existing
tests: a material change could leave an earlier approval valid. The
resulting proposals required invalidation and fresh acceptance.
Short feedback cycles reshaped an
MVP around those lessons. The three disposable prototype PRs stayed
unmerged as evidence, and the simplicity review proposed SA-001--SA-010.
I used the resulting MVP intermittently, including sign-in, synthetic
data and model-backed assistant paths.

The backlog manager drew on this accumulated context to generate the work
hierarchy, acceptance criteria and dependencies. Existing-coverage labels
distinguished proposed work from functionality already present in the MVP\@.
The supplied project export records a batch expansion around this handoff,
followed by movement into completed states. It provides a trace of work
organisation; accepted user journeys require their own evidence.
Requirements reconciliation continued afterward, including for scope first
surfaced in backlog stories. Thus preparation and delivery overlapped, and
the issue hierarchy remained an evolving interpretation of the design.

\subsection{Local completion and the usable workflow}

Autonomous delivery changed the feedback path. The coordinator selected
issues and workers satisfied local implementation and review obligations.
At the same time, a source-layout migration replaced the used MVP\@. The
replacement passed bounded engineering checks, including health, restart
and unauthenticated-request rejection, but lacked identity, staff and model
prerequisites needed for my complete workflow. Restoring a
public entry point left sign-in dependencies unresolved.

The earlier setup log distinguishes an application-role assignment from
the internal staff binding: a user could pass tenant and role validation
and still receive \textquotedblleft{}no staff record with this oid\textquotedblright{}.
That recorded
dependency helps explain why opening a browser entry point alone could
not restore the staff workflow.

I continued supplying approvals and resolving technical blockers.
What diminished was the ability to exercise realistic work in the
replacement and use that experience to steer the next change. Missing
prerequisites became further issues, each with research, planning, review
and correction work. Scope additions and validation costs also changed
delivery conditions. These observations locate a concrete interruption of

\section{Consolidation hypothesis and procedure}\label{sec:harness}

Restoring the case's missing identity and staff bindings required
configuration and end-to-end verification. Consolidation addresses a
different concern from the same experience: even with a correct
deployment, repeated feature work may leave a repository that is harder to
extend. The separate experiment narrowed the question to that inherited
state. It tested retained behaviour and a withheld change request, and it
did not treat code cleanup as a remedy for the case's configuration failure.

Practitioners already structure multi-session agent handoffs around clean
repository states: Anthropic prompts each coding session to leave merge-ready
code and update a progress file~\cite{anthropic2025harness}. That account
describes practice without comparing feature-only delivery against
consolidation between feature steps.
Darwin's continuous optimisation is a further precedent for automated
improvement, but its performance evaluations do not isolate that intervention
or test an unforeseen change request~\cite{pavlenko2026factory}
(Section~\ref{sec:factory}). RefactorBench already evaluates refactoring
agents~\cite{gautam2025refactorbench}; the narrower hypothesis concerns retained
behaviour and later adaptation during repeated feature additions.

The consolidation procedure tests one bounded form of reflective
correction, and it changes what persists in the repository. Self-Refine revises
an output and Reflexion retains lessons for later trials
~\cite{madaan2023selfrefine,shinn2023reflexion}; the present intervention
consolidates the software and its handover between different
feature requests. CRITIC's tool feedback is another precedent
~\cite{gou2024critic}. The held-out evaluation remained separate from that
feedback, and the study tests whether the retained changes help with an
unforeseen request. The schedule sets each pause, and the agent cannot reject
features or redirect the product.
After each feature, delivery pauses for a bounded consolidation session.
The agent runs the tests and examines structural diagnostics, then reviews
the latest diff for duplication, complexity, unclear names, dead code,
misplaced responsibilities and tests coupled to implementation details.
It attempts small refactorings through
\texttt{test \&\& commit || revert}, so a change survives
only while the tests remain green. It may add tests of current behaviour,
while the defining example tests stay protected.

The pause also prepares the next session. The agent replaces a design note
of at most 300 words instead of appending to it. The note records where
rules reside and what debt remains.
The pause ends when the quality targets are reached or the time budget
expires, and the next feature begins. The supplement reproduces the
historical v4 prompt, and the current researcher kit defines the amended
prompt. The active B/C templates and their source bindings appear
in Supplement Section~\ref{app:activeprompts}. The intervention combines
refactoring, additional tests and a design-oriented note, so the study
cannot isolate refactoring alone.

The hypothesis draws on Beck's alternation of features and
futures~\cite{beck2026prodacity,beck2025devslow} and \emph{Tidy
First?}~\cite{beck2023tidy}. The procedure costs time, and its benefit remains
an empirical question. Agent
refactorings can be incomplete or incorrect~\cite{gautam2025refactorbench},
and human studies caution against equating a refactoring label with a
quality gain. Kim et~al.\ report developers' refactoring challenges and
benefits~\cite{kim2014refactoring}; Bavota et~al.\ find that observed
refactorings do not consistently target or remove code
smells~\cite{bavota2015quality}. These findings argue for checking outcomes
instead of assuming improvement. Test-commit-or-revert
protects behaviour only to the extent that the tests cover it
~\cite{ma2026building}. Section~\ref{sec:experiment} specifies how
the procedure was evaluated and reports the results.

\section{Discussion}\label{sec:discussion}

\subsection{Observed costs and possible payback}\label{sec:costprojection}

On the measured ten-feature task, consolidation (B) used 1.84 to 2.25 times
the delivery credits of feature-only work (A). The settled means rose from
54.52 to 115.02 on Sonnet~5.5, 112.66 to 253.03 on Gemini~4 Argon and
155.93 to 286.78 on GPT~6.1 Sol. These are means over completely billed
trajectories, whose counts differ across cells; unresolved charges prevent
a complete all-allocation cost comparison. The resource table in
Section~\ref{sec:resultsstructural} retains those denominators.

Consolidation did not consistently reduce change-request cost across the
three models. The settled observations show no demonstrated short-horizon credit payback,
although some consolidation trajectories delivered more complete software.
Those outcomes matter when interpreting the extra spend. The longer-session control
(D) had 50\% more time and twice A's credit allowance, yet spent a similar
amount to A. B and D had matching allowances but did not use matching resources.

This study cannot establish long-term payback. The economic hypothesis is
that early consolidation lowers the cost of enough later features to
offset the cleanup work. The earlier sensitivity model in Supplement
Section~\ref{app:economics} states those assumptions
(Figure~\ref{fig:refactoringeconomics}, Table~\ref{tab:costscenario});
I never fitted its cost growth to this experiment.

Measured consolidation-session spend is recorded in the Supplement
(Section~\ref{app:measurementprovenance}). The economic model also needs
$\delta$, the assumed increase per cycle in implementation cost without
consolidation relative to consolidation. The experiment does not estimate
that long-run increase: with capped budgets, harder work may produce
less complete features without raising spending. Estimating payback would require
longer sequences, comparable delivered quality, residual repair costs and
resolved billing. Human effort, opportunity costs and currency prices were
also not measured. The table shows how assumptions change payback; the
experiment reports the observed short-horizon trade-off.

\subsection{What worked}

For the product described in Section~\ref{sec:method}, the agents were useful
before coding began: they helped me question what to build. Research agents
gathered and analysed source material, while role-based agents challenged
the proposed design. An evidence-assessment task still
needed surveyor judgement; a resident-contact task still needed consent
and a manual route. The prototypes made those boundaries visible in a
case card and resident-decision record. I built and reshaped the MVP
through targeted exchanges and feedback.
These are observations from my use of the tools. I did not measure a
human-only duration or run a controlled comparison of feedback cadences.
The retained author review and case evidence index describe the discovery,
prototype and backlog handoffs.

\subsection{Human judgement and reflective work}

I supplied several kinds of reflective work: choosing what not to build,
recognising the unusable replacement and deciding which earlier lessons
mattered. Naur's theory-building account
describes that retained understanding~\cite{naur1985theory}, and
Beck similarly separates producing code from learning through working
software~\cite{beck2026prodacity}. These case-specific judgements
raise the question of whether agents could make comparable ones.
The experiment asks something narrower: whether bounded post-feature
correction preserves behaviour and later changeability.

An approval record alone cannot establish that a person evaluated the
alternatives independently. In Anthropic's
randomised study, 61 analysts were recruited and 50 used the agent. Those
50 analysts matched their agent's
randomly assigned preference on 86\% of four analytical choices
~\cite[Study design; Results]{herdagdelen2026judgment}. The preferences were
deliberately strengthened in one farming-analysis task with one model; the
rate concerns a different task and setting from coding
~\cite[Our study's limitations]{herdagdelen2026judgment}.
The study did not assess the decisions reported in this case. Its authors suggest
asking experts for their view first or making the best case for each option
~\cite[What this means]{herdagdelen2026judgment}. I propose a separate step:
record the alternatives and a person's reasons before accepting an agent's
recommendation. This study did not test that procedure.

\subsection{Can another agent preserve room for change?}

Room for change here means the options the system supports after the current
feature. Beck's alternation suggests preserving those options during
feature work~\cite{beck2026prodacity,beck2025devslow}. Darwin and
SkillOpt offer agent-guided correction procedures
~\cite{pavlenko2026factory,microsoft2026skillopt}. Ng's
reflection framework argues for evaluating and revising work instead
of accepting first-pass generation as finished
~\cite{ng2024reflection}. I define improvement as a measured advantage in
retained behaviour or later adaptation. A lesson, prompt change or
self-improvement label alone cannot establish that advantage.
The experiment changes the repository and handover while leaving model
training to the provider, and a recorded model name cannot rule out
provider-side changes during collection.

Two results from the experiment illustrate the problem. On GPT~6.1 Sol, some earlier
tests encoded a closed \texttt{READ\_METHODS} list. The ninth feature
added \texttt{view.rank\_cases()}, but the earlier test expected
\texttt{NotAllowed} for methods outside that list, and the study rules
protected accepted test files from edits. Consolidation and visible-specification repair were associated
with more complete feature delivery in that setting.

On Gemini~4 Argon, a view could reject \texttt{view.open\_case}
yet forward newly added \texttt{define\_region} and
\texttt{approve\_handoff} calls. Read-only review had more successful final
extensions than consolidation, despite consolidation's cleaner structural
metrics. Baseline metrics were low, but did not satisfy every stopping
target. The cell summaries establish neither why a session stopped nor
that a particular review action caused the difference. They do show that
structural hygiene and a rule such as ``every
write through a read-only view must be refused'' are separate things.

These observations support testing structural cleanup and checks of intended
behaviour together. Choosing when to interrupt delivery, changing product
goals, restoring a deployment and comparing human with agent steering
remain separate questions in the ancillary research agenda.

\subsection{What this study teaches a future experiment}\label{sec:futureexperiment}

I expected to see decay. Instead, the agents largely preserved what they
had implemented. That result does not explain the larger migration failure
that motivated the study, but it prevents me from treating that experience
as evidence that sequential feature work necessarily degrades software.
A longer, more coupled task could test whether the suspected burden emerges
under different conditions. Stable retention must remain a possible result.
The loss endpoint counted states retained after rollback under immutable-test
rules (Section~\ref{sec:prerun}); the experiment did not compare those rules
with an unrestricted policy. A future design must state whether it measures rejected attempts,
retained failures or both; those are different outcomes.

S1 still changed what needs measuring. Acquiring a feature,
preserving an established contract and adapting to a new requirement need
separate outcomes. GPT A's incomplete-ranking repositories entered CR1 with fewer acquired
contracts to preserve (Table~\ref{tab:crprerequisites}). Several change
requests, evaluated on isolated branches, could probe adaptation without
altering the continuing delivery trajectory. More coupled brownfield work
could show whether implementation burden or loss emerges over longer
horizons, and it would keep genuine acquisition failures visible.
Task calibration must also leave room for the planned useful effect:
the longer-session group (D) averaged 96.96\%, leaving only 3.04 percentage
points for improvement. The original ten-point target remains unmet;
it should not be lowered after observing this dataset. A future study needs
an outcome and target chosen together before collection.

Discovery was disabled in the experiment
(Section~\ref{sec:runtimeboundaries}). A follow-up could compare full RPI with feature-only delivery
and separate review from refactoring, extra tests and handover content
where feasible. The present results do not establish that RPI is better.

The earlier numerical design candidates remain in Supplement
Section~\ref{app:futuredesign}: longer trajectories, branch-isolated
change requests and component comparisons. They offer design inputs for a
future study; its task scale, resource needs and protocol require separate
development and review. The authors are postponing
that study until resource estimates and spending are approved. A later paper
would need a separately reviewed and prospectively registered protocol,
aligned randomisation and uncertainty analysis, and quality-matched costs.
This paper contributes the exploratory findings and the measurement lessons
needed to design that study.
No additional experimental round or judge batch is planned for this paper.
The remaining unknown outcomes, billing and incomplete calibration stay
visible in the present record.

\subsection{Implications for practice}\label{sec:feedbackfirst}

The final report's Minimum Viable Experiment assessment recommends
\emph{adjust}: revise the next study before adopting the full consolidation
package. On this workload, extra single-session allowance
left observed spending and outcomes similar, while unconditional
consolidation roughly doubled delivery credits. The report rates both
strategies \emph{no-go} at this horizon. Similar cell means do not establish
equivalence or explain why sessions stopped early.

In the reported cells, B removed complexity hotspots, C had more Gemini
CR1 successes, and E had more complete GPT feature suites than A.
Those observations motivate a triggered
hybrid, whose candidate commands and thresholds are in Supplement
Section~\ref{app:practicecandidate}. Its efficacy and cost advantage still
need testing, and replacing an established review
workflow with that unevaluated combination would be premature.

For teams considering scheduled consolidation, the relevant comparison is
its added cost at comparable retained behaviour and success on new requirements. In this study, structural
measures improved, but the coverage gain over longer sessions was 1.19
percentage points and change-request costs did not consistently fall.
For the motivating case, a concrete checkpoint would have been staff
sign-in followed by opening an assigned case, with the application-role
and internal-staff bindings checked together. The case also motivates
shorter delivery horizons and carrying those prerequisites into later
briefs or executable checks. These are proposed follow-ups, not measured
improvements. Any later evidence-retention change would require a finite,
archive-backed and restore-verified selection, including adverse reviews.
Mandatory safety, privacy, approval and publication
gates stay in place, and compact context views must retain their source evidence.
This study did not test these practices, the proposed human-checkpoint
cadence or a method for preserving expertise. The ancillary context holds the fuller practice
checklist and framework-builder suggestions.

\section{Conclusion}\label{sec:conclusion}

Across the ten-feature S1 task, previously acquired behaviour was largely
retained. None of the 126 feature-only or longer-session runs had an open
regression at the final checkpoint ($P_{10}$); only one trajectory across
all arms did. The endpoint describes retained states after rejected
increments were reset under protected-test rules. Workflow replay
found no witnessed losses across 626 evaluable
packets. The main failures were features that agents never acquired and a
permission-boundary hole exposed by the
withheld regional-access extension (CR1), as the GPT ranking and Gemini
view-write results in Section~\ref{sec:resultscorrectness} illustrate.

Consolidation (B) removed complexity hotspots at all 63 endpoints, but its
primary coverage advantage over longer feature-only sessions (D) was
1.19 percentage points (conditional 95\% interval [0.10, 2.22]), below the
ten-point minimum useful threshold. Even perfect consolidation endpoints
could exceed the observed longer-session results by only 3.04 points. The unmet target
therefore also exposes a ceiling in the task and measurement design.
GPT~6.1 Sol supplied most of the observed gain by
completing priority ranking after an earlier test had fixed the permitted
view methods. Sonnet~5.5 and Gemini~4 Argon showed small B--D gains whose
intervals spanned zero. Read-only review (C) achieved 16/21 Gemini CR1
successes versus 8/21 with consolidation, while consolidation roughly
doubled settled delivery credits without consistently lowering CR1 cost.
The report proposes testing a combined pass triggered by code metrics or a
halted session: \texttt{./tcr} cleanup with review of rules that must survive
later features. No combined-policy efficacy or cost advantage was measured.

The motivating case concerns a different scale and failure: a migration
interrupted a usable workflow after extensive agent-assisted preparation.
Its five candidate mechanisms link inherited obligations, lessons and
completion signals to opportunities for correction. The experiment did not
test those mechanisms individually. Together with the literature, the case and experiment identify different
ways to evaluate what later work inherits. The next experiment needs a
separate design: longer,
more coupled work, several adaptation probes and comparisons that can
distinguish full RPI delivery from its corrective components
(Section~\ref{sec:futureexperiment}).

These are exploratory findings from one suite and one final change request.
Owner attestation covers all 315 completed trajectories; unregistered
amendments, two unadjudicated GPT~6.1 Sol CR1 test errors, 55 billing holds,
the 313/315 judging snapshot and sixteen execution sources limit inference.
The reported intervals assume independent trajectories within cells;
unmeasured service and scheduling dependence prevents a confirmatory
interpretation. CR1 prerequisite strata and fully billed cost summaries
describe selected subsets with different delivered functionality. Comparing
treatments at matched quality would require a separately defined analysis.
The ten-feature task did not support the expected decay pattern.
Its acquisition and permission-boundary failures instead show why retention,
completeness and adaptation require separate measurements. A follow-up can
test longer loops and RPI-based correction once its protocol and resources
are approved. The present evidence supports structural improvement at
additional delivery cost, without a demonstrated short-horizon payback.

\section{Source and digest register}\label{app:source-register}

Record links such as \sourceref{R17} identify the version used for a claim.
Git commit IDs identify revisions, tree IDs directory contents and blob IDs
individual Git objects. SHA-256 digests identify retained file bytes or an
image. Matching an identifier verifies content identity. Claim support and
independent validation require their own evidence. Unless another repository is named, records refer to
\nolinkurl{jmservera/ama-thought-mve}. Historical and final records remain
separate even when they concern the same file.
