\begin{abstract}
An effort to extend a working prototype produced a solution I could
not use, despite extensive agent-assisted preparation and a daintily crafted feature
delivery plan. This experience raised a question: what does each feature leave
for the next? The case analysis considers five possible process-related causes,
but technical migration and deployment problems could also explain what happened.

To test the question, I designed a study with ten ordered features in one
repository, followed by a withheld change request. Agents kept coding,
consolidated, reviewed without editing, or repaired behaviour against
visible specifications; a control gave them more coding time. They saw the
specifications, not the scoring tests. After each step, a separate evaluator
ran hidden tests in isolated containers and counted passed contracts out
of 127.

Three models each completed 21 repository trajectories in every condition.
All 315 allocated trajectories finished. Sonnet~5.5 and Gemini~4 Argon
averaged 99.18\%--99.74\% test coverage. One trajectory ended with a
previously passing contract still failing, while replay found no losses
of earlier observed capabilities.

Consolidation cleaned up the code: none of its 63 endpoints had a function
above cyclomatic complexity 10. The coverage gain over longer coding
sessions was only 1.19 percentage points (95\% bootstrap interval
[0.10, 2.22]), well below the ten-point benchmark. Most of that gain came
from GPT~6.1 Sol. On Gemini~4 Argon, read-only review passed 16 of 21
held-out change requests; consolidation passed 8. Consolidation also
roughly doubled settled delivery credits and did not consistently reduce
change-request cost.

Tests showed whether features worked. Replay checked whether later changes
broke them; the withheld request tested whether the system could adapt.
A larger study could repeat these checks on longer, more interdependent
projects.
\end{abstract}

\section{Introduction}\label{sec:intro}

I could inspect completed issues and passing checks, but could not sign in
and use the replacement system. Earlier, short exchanges
with agents had produced a working prototype; later, a coordinator and
parallel workers delivered a more formal backlog while migration
dependencies remained unresolved. That interruption, described below,
raised a question broader than any one failed deployment: when each change
looks locally complete, who checks the system that the next change inherits?

On 1~August 2012, Knight Capital's automated router sent more than four
million orders while attempting to fill 212 customer orders. The firm lost
more than USD~460 million. The SEC traced the incident to a defective
function left in the router after a 2005 change, an incorrect deployment for
a new trading programme, and inadequate controls. The new deployment
activated old code that was no longer meant to run~\cite{sec2013knight}.
The failure crossed a feature boundary and a seven-year interval: the
relevant starting point was the accumulated system, not just the latest patch.

Less spectacular versions of the same maintenance problem are familiar.
Cunningham's 1992 account of WyCash described a financial product continually
adapted to market demands. Its mature code was repeatedly revised and
rewritten; the technical-debt metaphor explained why shipping a
first-time implementation required later rewriting as understanding
improved~\cite{cunningham1992wycash}.
Some debt is visible as duplication or awkward dependencies. Some remains
hidden in assumptions about inputs, deployment and earlier behaviour until
another change depends on it. Counting completed changes reveals neither.

Agentic development makes this distinction newly pressing. PhotoCraft, an
early-alpha reimplementation of Photoshop, reports 631 of 631 menu items
live. That count measures dispatch; the project's dated assessment
separately estimates about 76\% feature breadth and 45\%
readiness for real work~\cite{photocraft2026}. A command can be reachable
without the surrounding workflow being dependable. At the repository level,
SWE-Maintain finds that agents solve fewer later tasks when starting from
their own earlier changes than from the developers' changes, even though
each task starts in a fresh session~\cite{pan2026swemaintain}.
A fresh session still receives the code produced by earlier sessions,
including any faults left in it.

The engineering response has a long history: isolation and explicit contracts
limit dependencies; tests and continuous integration expose regressions;
small releases shorten feedback; refactoring preserves room for later
change~\cite{parnas1994aging,beck2002tdd,beck2004xp,fowler2007stamina}.
Recent discussions by Beck, Martin and Fowler revisit these concerns for
agent-assisted work~\cite{beck2026prodacity,martin2026productengineers,fowler2025thoughts}. Beck's
distinction between producing code and learning through working software
sharpens the research question~\cite{beck2026prodacity,orosz2025beck}:
what does a feature leave behind for the next one?

I developed the motivating architectural demonstrator with multiple agents.
Research documents, business and product
requirements and architecture decisions were built through sustained
conversation, challenge and owner decisions. Design Thinking methods,
including what-if scenarios, persona analysis and journey mapping, helped
question the proposed solution; disposable pilots and prototypes exposed
workflow problems before a usable MVP emerged. A backlog agent then converted
that accumulated context into epics and user stories for a delivery coordinator.
I expected this preparation to speed implementation of better-understood
features, with explicit acceptance criteria and review.

Extended autonomous sessions nevertheless left the replacement unusable for
me. Renewed product-use feedback redirected implementation and
refactoring. This sequence motivates investigating how preparation and local
completion checks translate into the behaviour inherited by later work.
The repository, pull requests, append-only log and versioned coordinator
instructions retain the evolving delivery record~\cite{servera2026ama};
the source package pins the evidence used here. The repository may be
temporarily unavailable during the experiment embargo, after which the
approved history and context are intended for release.
My earlier
experience with Aithena, a book-search project with PDF ingestion and
a browser interface discussed separately in the supplement, and the PhotoCraft
inspection selected after the motivating-case analysis have separate provenance in
the ancillary \nolinkurl{anc/supplementary-context.md}.

The initial conjecture was that feature-driven delivery carries
unresolved errors and avoidable change burden forward, and that cumulative
verification and consolidation can reduce that burden. Two kinds of state matter:
the software being changed, and the instructions used to change it. Adding
a corrective rule after every failure can leave prompts, skills and
handover notes with their own maintenance burden. A fresh agent inherits
both kinds of state. Section~\ref{sec:background} distinguishes these
pathways; the case then examines how they interact with completion proxies,
review capacity and product-use feedback.

The experiment must allow evidence against that conjecture. A single
regression would provide little support for progressive decay, whereas
stable behaviour would count against it under the tested conditions. Here
\emph{feature-driven decay} means a measurable loss of previously passing
behaviour or a rising cost and failure burden across sequential changes.
To make the conjecture falsifiable on the ten-feature S1 task and its
withheld change request (CR1), the analysis separates the \emph{decay
premise} from the \emph{consolidation remedy} and evaluates three
testable predictions alongside a treatment-fidelity check:

\paragraph{P1 (Short-horizon decay premise).}
Without a dedicated
post-feature pause (Arms~A and~D), sequential delivery across ten features
induces progressive behavioural loss by the final feature checkpoint
($P_{10}$): previously passing contracts still fail, failures accumulate
across cycles, or replayed workflows lose earlier capabilities.

\paragraph{P2 (Primary coverage gain threshold).}
Scheduled consolidation (Arm~B) exceeds the matched-allowance longer-session control
(Arm~D) in equal-model-weight final hidden-test coverage at $P_{10}$ by at
least the pre-specified minimum useful effect of $\Delta_*=10$ percentage
points (Section~\ref{sec:protocollimits}).

\paragraph{P3 (Change-request adaptability and short-horizon payback).}
Consolidation (Arm~B) raises held-out CR1 success and reduces CR1 or net
credit expenditure relative to feature-only delivery (Arm~A), read-only
review (Arm~C) and longer sessions (Arm~D).

\paragraph{Manipulation check (Structural treatment fidelity).}
Consolidation reduces functions above cyclomatic complexity 10, duplication
and lint density toward its stopping targets. This check asks whether
the intervention changed structure before interpreting its behavioural
results.

The experiment changed the interpretation of the motivating case.
Behaviour was largely retained, and consolidation's coverage gain fell
below the practical benchmark even though structural cleanup occurred.
Table~\ref{tab:predictionverdicts} brings the criteria and results together.
The useful question became which capabilities were never acquired, which
survived, and which failed when a new requirement crossed an old boundary.

Only $\Delta_*=10$ percentage points was fixed in the pre-collection
planning calculation; the public execution manifest
(\nolinkurl{protocol/pilot-estimation.json}) left its formal hypothesis
array empty, and the operational criteria in P1 and P3 structure the
post-collection evaluation rather than claiming a preregistered
confirmatory test.

Three questions guide the investigation:

\begin{itemize}[leftmargin=*]
\item \textbf{RQ1.} Through which retained state can errors and change
burden carry from one feature to the next, and what does existing evidence
show about those pathways?
\item \textbf{RQ2.} How does an exploratory delivery record illuminate that problem,
and which candidate mechanisms and rival explanations does the gap between
completion signals and usable replacement behaviour suggest?
\item \textbf{RQ3.} Does scheduled agent-led consolidation after each feature
improve retained behaviour and future changeability, and at what cost?
\end{itemize}

\noindent The report makes three linked contributions:

\begin{enumerate}[leftmargin=*]
\item A focused synthesis distinguishing conversational self-conditioning,
repository-carried faults and instruction maintenance, with a replot of
published paired-history data (Section~\ref{sec:background}).
\item An exploratory account of the transition from agent-assisted discovery
and challenged requirements to coordinated feature delivery and corrective
product feedback. Five candidate mechanisms and within-case contrasts connect
the interruption of usability to competing explanations
(Sections~\ref{sec:method}--\ref{sec:mechanisms}).
\item A consolidation procedure and an executed 315-trajectory, five-arm
exploratory study with post-collection workflow replay and blinded AI
judging, estimating retained behaviour, future changeability and resource
cost. Its earlier planning drew on the registered-report example of
Lulla et~al.~\cite{lulla2026protocol} and HVE Core's Minimum Viable Experiment method
(Sections~\ref{sec:harness} and~\ref{sec:experiment}).
\end{enumerate}

The case concerns a migration and a configuration I designed, including
delegated delivery and merge decisions. The case suggests hypotheses whose
causal relationships remain to be tested. The primary comparison measures the combined effect of consolidation,
added tests and a handover note against a control with the same time and
nominal-credit limits. The B--A comparison, which adds resources as well
as consolidation, is secondary. Equal limits need not produce equal spending,
and the design does not isolate refactoring or validate the five case
mechanisms individually. An owner-confirmed registered base and disclosed
unregistered amendments frame the completed exploratory collection.
All 315 allocated trajectories are complete and owner-attested unassisted;
the execution record preserves interruptions and recoveries. The case's validity and the pilot's
identification limits are consolidated in Sections~\ref{sec:threats}
and~\ref{sec:protocollimits}.

\section{Case and method}\label{sec:method}

\subsection{Setting}

I developed the motivating architectural training exercise while acting as
architect, developer and product owner.
Its synthetic, multi-role service workflow combined documentary evidence,
approvals, identity, data and external-service dependencies. The exercise
required research, requirements, architecture, a delivery plan and a working
demonstrator. These interdependencies made preservation of a complete user
journey consequential even in a non-production system. No operational
service or real resident data is evaluated here.

\subsection{Workflow and tools}

GitHub Copilot and HVE Core first helped me learn what to
build. Research agents assembled source snapshots and maintained syntheses
in a knowledge base with an index, owner-curated memory and an append-only
log. The Design Thinking coach and stakeholder-role agents then challenged
assumptions through what-if scenarios, persona analysis and journey mapping.
Those exchanges separated bounded AI tasks from deterministic controls and
accountable human decisions. Role-agent answers remained hypotheses for the
exercise; direct stakeholder research was still needed.

As understanding changed, BRD and PRD builders, quality review and the ADR
assistant helped turn conversations and owner decisions into revised
requirements and architecture records. Disposable pilots and prototypes
made candidate workflows tangible. Critiques and my product-use feedback
informed a deployed MVP that I used intermittently and refined
through short feedback loops.

The handoff to autonomous delivery changed how that understanding reached
implementation. A backlog agent converted the accumulated context into
epics, features and user stories, including acceptance criteria, dependencies
and indications of existing MVP coverage. Some stories exposed scope that
still needed requirements reconciliation. A custom coordinator dispatched
implementation and review against this evolving backlog
(Section~\ref{sec:coordinator}).

The intended benefit was accelerated planning and better-grounded feature
delivery. Neither a human-only comparator nor a measured speed or quality
gain was available. The retained documents and conversations matter because
they shaped what workers were asked to build and reviewers were asked to
accept.

\subsection{The coordinator}\label{sec:coordinator}

The coordinator ran through Copilot CLI on a VM. It selected dependency-ready
issues and launched parallel worker sessions in isolated git worktrees.
Each worker received an issue and HVE Core's research, plan, implement and
review (RPI) workflow. The coordinator checked the resulting pull request,
updated the project board and, under owner delegation, merged changes.
Interactive and CLI model configurations changed during the project;
recorded selectors and recalled interface labels are distinguished in the
source package. The delivery record is consequently an evolving workflow.

Early worker sessions implemented directly, prompting me to make
the full RPI sequence and committed tracking artefacts mandatory. Further
instructions required evidence-backed acceptance ticks, scheduled monitoring
and increasingly comprehensive local gates. Human decisions, approvals,
credentials and unresolved review findings could still block work. At the
same transition, an accepted architecture decision prioritised migration
to a new source layout and froze feature work in the MVP. Coordination,
migration and procedural requirements therefore changed together.

\subsection{Constructs and evidential boundaries}\label{sec:constructs}

Here an \emph{agent} combines a model, tools and instructions in a loop that
selects and executes actions. People remain accountable for its use.
A \emph{skill} is a reusable set of procedures describing when and how to
act and check the outcome. It differs from a session history and does not
update model weights. This distinction follows
Jiang et~al.~\cite[Sec.~1]{jiang2026skills}. The pilot retains a handover
note as context; it does not vary skill use as a separate treatment.

\emph{Working behaviour} means completing an intended task through the
running system, including the identity, data and service dependencies needed
for that task. A healthy endpoint or passing repository test covers only
part of that evidence. \emph{Decay} denotes loss of previously working behaviour or
increasing difficulty of understanding and changing a system. The case
records lost usability during replacement; any decline in intrinsic code
quality remains unmeasured. Deployment drift could produce the same observation.
\emph{Adaptability} was defined in the prospective design as success and cost
on the unforeseen change request under a fixed budget. This measures one
aspect of maintainability. \emph{Consolidation} means scheduled structural work intended
to preserve observable behaviour, with tests checking that intention.
Passing finite tests supports only the contracts they cover.

Five measurement categories remain separate. PRs, lines and words describe
\emph{production volume}; checks, reviews and receipts describe
\emph{validation activity}; observed user tasks describe \emph{system
behaviour}; code metrics and the change request probe \emph{internal quality
and changeability}; and corrective help requested or supplied describes
\emph{intervention}. The original observations cover the first three.
A later post-hoc comparison adds code metrics as indirect measures of
structure. It includes no controlled changeability task or systematically
coded intervention dataset. Volume and validation activity describe the
process; measuring decay requires evidence about behaviour or change burden.

\subsection{Building the epics and user stories}

Preparation involved sustained steering rather than a single specification
prompt. Role-agent challenges questioned the requested end-to-end agents;
what-if scenarios tested alternative inputs and responsibilities. Persona
and journey work exposed handoffs, missing information and approval boundaries.
The resulting BRDs, PRDs and ADRs were critiqued and revised through further
conversation. These activities changed the proposed solution before and
during implementation.

Disposable prototypes then made some assumptions tangible. My critique
and an agent-assisted simplicity review produced requirements for
clear ownership, a visible next action, understandable blockers and manual
paths that remained usable without AI. Short feedback cycles reshaped an
MVP around those lessons. I used it intermittently,
including sign-in, synthetic data and model-backed assistant paths.

The backlog manager drew on this accumulated context to generate the work
hierarchy, acceptance criteria and dependencies. Existing-coverage labels
distinguished proposed work from functionality already present in the MVP.
The supplied project export records a batch expansion around this handoff,
followed by movement into completed states. It provides a trace of work
organisation; accepted user journeys require their own evidence.
Requirements reconciliation continued afterward, including for scope first
surfaced in backlog stories. Thus preparation and delivery overlapped, and
the issue hierarchy remained an evolving interpretation of the design.

\subsection{Local completion and the usable workflow}

Autonomous delivery changed the feedback path. The coordinator selected
issues and workers satisfied local implementation and review obligations.
At the same time, a source-layout migration replaced the used MVP. The
replacement passed bounded engineering checks, including health, restart
and unauthenticated-request rejection, but lacked identity, staff and model
prerequisites needed for my complete workflow. Restoring a
public entry point left sign-in dependencies unresolved.

I continued supplying approvals and resolving technical blockers.
What diminished was the ability to exercise realistic work in the
replacement and use that experience to steer the next change. Missing
prerequisites became further issues, each with research, planning, review
and correction work. Scope additions and validation costs also changed
delivery conditions. These observations locate a concrete interruption of
usable behaviour within a broader process of accumulating obligations.
The automated score and failed journey still need release-and-scope linkage
before their disagreement can be assessed as a matched comparison.

\subsection{Case validity and rival explanations}\label{sec:threats}

The five categories overlap in this case. Missing identity and staff
bindings could reflect deferred migration, incomplete deployment acceptance
or a lesson that workers did not apply. The deployment comparison and
session-input trace in Table~\ref{tab:audittrail} could help distinguish
these explanations. Document and citation counts cannot do so. The available
evidence also cannot establish context overflow from a growing read path or
disproportionate cost from an expensive gate alone. Per-change gate time,
avoided defects and human effort were not measured.

The source-layout migration, owner-selected priorities and delegated merging
changed alongside coordination. Scope additions, budget constraints, model/tool
changes and deployment conditions also differ between periods. Any of these changes could help explain the outcome attributed to autonomy. The
\hyperref[sec:supplement]{supplementary rival-explanation register} retains the full
register, separating recorded circumstances from plausible but untested
alternatives. Bird et~al.'s study of co-installed applications on Windows
machines supplies a methodological analogy for checking environmental
influences on reliability~\cite{bird2014extrinsic}. That study concerns environmental influences on reliability; it provides
no diagnosis of this case's agent configuration or sign-in failure.

Construct validity is limited by whitespace counts, lexical indicators and
selectively reviewed records. Appropriate caution can raise boundary-phrase
density; the records cannot show whether a missing reference reflects absent
knowledge or missing documentation. As coordinator designer, participant
and analyst, I selected the episodes and may favour a coherent retrospective
explanation. AI-assisted synthesis shares these source limits and needs
independent checking.
Public records support recomputation but not independent corroboration of
every statement. The single exercise I designed and purposively selected

\section{Consolidation hypothesis and procedure}\label{sec:harness}

Restoring the case's missing identity and staff bindings required
configuration and end-to-end verification. Consolidation addresses a
different concern raised by the same experience: even with a correct
deployment, repeated feature work may leave a repository that is harder to
extend. The separate experiment narrowed the question to that inherited
state. It tested retained behaviour and a withheld change request, without
treating code cleanup as a remedy for the case's configuration failure.

Teams already use recurring agents for cleanup. OpenAI describes replacing
weekly manual clean-ups with background agents that open small refactoring pull
requests, alongside a documentation-gardening agent~\cite{openai2026harness}.
Anthropic asks each session to leave a clean state and update a progress
file~\cite{anthropic2025harness}. These accounts describe practice; neither
compares feature-only delivery with consolidation between feature steps.
Darwin's continuous optimisation is a further precedent for automated
improvement, but its performance evaluations do not isolate that intervention
or test an unforeseen change request~\cite{pavlenko2026factory}
(Section~\ref{sec:factory}). RefactorBench already evaluates refactoring
agents~\cite{gautam2025refactorbench}; the narrower hypothesis concerns retained
behaviour and later adaptation during repeated feature additions.

AutoSaddler's preprint abstract describes optimizing an agent's execution
setup from traces through failure diagnosis,
structured patches and validation-based update
selection~\cite{microsoft2026autosaddler}. Agent-led reflective correction
appears in prior work. This study tests a different intervention:
consolidating the repository between feature steps, then measuring retained
contracts and performance on a withheld change request.

The consolidation procedure tests one bounded form of reflective
correction. It changes what persists in the repository. Self-Refine revises
an output and Reflexion retains lessons for later trials
~\cite{madaan2023selfrefine,shinn2023reflexion}; the present intervention
instead consolidates the software and its handover between different
feature requests. CRITIC's tool feedback is another precedent
~\cite{gou2024critic}. The held-out evaluation remained separate from that
feedback. The study tests whether retained changes help with an unforeseen
request. The schedule sets each pause; the agent cannot reject features or
redirect the product.
After each feature, delivery pauses for a bounded consolidation session.
The agent runs the tests and examines structural diagnostics, then reviews
the latest diff for duplication, complexity, unclear names, dead code,
misplaced responsibilities and tests coupled to implementation details.
It attempts small refactorings through
\texttt{test \&\& commit || revert}~\cite{beck2018tcr}: a change survives
only while the tests remain green. It may add tests of current behaviour,
while the defining example tests remain protected.

The pause also prepares the next session. The agent replaces, rather than appends to, a design note of at most
300 words. The note describes where rules reside and what debt remains.
The pause ends when the quality targets are reached or the time budget
expires, and the next feature begins. The supplement reproduces the
historical v4 prompt; the current researcher kit defines the amended
prompt. The active B/C templates and their source bindings are reproduced
in Supplement Section~\ref{app:activeprompts}. The intervention combines
refactoring, additional tests and a design-oriented note, so the study
cannot isolate refactoring alone.

The hypothesis draws on Beck's alternation of features and
futures~\cite{beck2026prodacity,beck2025devslow} and \emph{Tidy
First?}~\cite{beck2023tidy}. The procedure costs time; its benefit remains
an empirical question. Agent
refactorings can be incomplete or incorrect~\cite{gautam2025refactorbench};
human studies also caution against equating a refactoring label with a
quality gain. Kim et~al. report developers' refactoring challenges and
benefits~\cite{kim2014refactoring}; Bavota et~al. find that observed
refactorings do not consistently target or remove code
smells~\cite{bavota2015quality}. These findings motivate checking outcomes
rather than assuming improvement. Test-commit-or-revert
can protect behaviour only to the extent that the tests cover it
~\cite{ma2026building}. Section~\ref{sec:experiment} specifies how
the procedure was evaluated and reports the results.

\section{Discussion}\label{sec:discussion}

\subsection{Observed costs and possible payback}\label{sec:costprojection}

On the measured ten-feature task, consolidation (B) used 1.84 to 2.25 times
the delivery credits of feature-only work (A). The settled means rose from
54.52 to 115.02 on Sonnet~5.5, 112.66 to 253.03 on Gemini~4 Argon and
155.93 to 286.78 on GPT~6.1 Sol. These are means over completely billed
trajectories, whose counts differ across cells; unresolved charges prevent
a complete all-allocation cost comparison. The resource table in
Section~\ref{sec:resultsstructural} retains those denominators.

Across models, consolidation did not consistently reduce final
change-request cost, so the accounted observations show no short-horizon
credit payback. Some trajectories did deliver more complete software; read
the additional spend alongside those outcomes. The longer-session control
(D) had 50\% more time and twice A's credit allowance, yet spent a similar
amount. Matching allowances for B and D did not produce matching resource use.

This study cannot establish long-term payback. The economic hypothesis is
that early consolidation reduces the cost of enough later features to
offset the cleanup work. The earlier sensitivity model in Supplement
Section~\ref{app:economics} makes those assumptions explicit
(Figure~\ref{fig:refactoringeconomics}, Table~\ref{tab:costscenario});
its cost growth was never fitted to this experiment.

Measured consolidation-session spend is recorded in the Supplement
(Section~\ref{app:measurementprovenance}). The economic model also needs
$\delta$, the assumed increase per cycle in implementation cost without
consolidation relative to consolidation. The experiment does not estimate
that long-run increase: with capped budgets, harder work may produce
less complete features without raising spending. Estimating payback would require
longer sequences, comparable delivered quality, residual repair costs and
resolved billing. Human effort, opportunity costs and currency prices also
remain outside the measurements. The table therefore illustrates how
assumptions change payback, while the experiment reports the observed
short-horizon trade-off.

\subsection{What worked}

Agents contributed useful challenge and rapid iteration. The research phase
assembled a corpus and analysis in days; a human-only
duration was not measured. The role agents' challenge
led me to reject the proposed five end-to-end agents before any code was written. The
agents refused to invent approvals, figures or company facts, and recorded
the limits of their evidence. The MVP was built and reshaped in a day. These episodes included targeted human challenge and feedback. Without a
controlled human-only comparison, they show how the workflow was used
but cannot establish a general advantage for short feedback loops.

\subsection{Human judgement and reflective work}

I supplied several kinds of reflective work: choosing what not to build,
recognising the unusable replacement and deciding which earlier lessons
mattered. Naur's theory-building account
helps describe that retained understanding~\cite{naur1985theory}.
Beck's distinction between visible output and understanding supplies another
framing~\cite{beck2026mathematicians}. These case-specific judgements
motivate a further question: could agents make comparable judgements?
The narrower
experimental question is whether bounded post-feature correction preserves
behaviour and later changeability.

An approval record does not show who formed the judgment. In Anthropic's
randomised study, 61 analysts were recruited and 50 used the agent. Those
50 analysts matched their agent's
randomly assigned preference on 86\% of four analytical choices
\cite[Study design; Results]{herdagdelen2026judgment}. The preferences were
deliberately strengthened in one farming-analysis task with one model; the
rate concerns a different task and setting from coding
\cite[Our study's limitations]{herdagdelen2026judgment}.
This cautions against treating approval alone as evidence of independent
judgment. The study did not assess the decisions reported in this case. The article proposes
asking experts for their view first or making the best case for each option
\cite[What this means]{herdagdelen2026judgment}. Separately, I propose
recording alternatives and a human's reasons before accepting an agent's
recommendation. Its effectiveness remains to be tested.

\subsection{Can another agent preserve room for change?}

Here, room for change means the options the system supports after the current
feature. Beck's alternation suggests preserving those options during
feature work~\cite{beck2026prodacity,beck2025devslow}. Darwin, AutoSaddler and
SkillOpt already provide precedents for agent-guided correction. Ng's
reflection framework also argues for evaluating and revising work instead
of treating first-pass generation as the finished product
~\cite{ng2024reflection}. Here, improvement means a measured advantage in
retained behaviour or later adaptation. A lesson, prompt change or
self-improvement label alone cannot establish that advantage.
The experiment changes the repository and handover while leaving model
training to the provider. A recorded model name cannot rule out
provider-side changes during collection.

The memory presentation's proposed ``dreaming'' pass is a useful contrast:
it curates prior transcripts into persistent context
~\cite{beamnxw2026memorytalk}, whereas this study changes retained code,
tests and the handover. Memory updates can carry an incorrect lesson forward
just as code updates can retain a defect. A self-improvement label therefore
cannot replace the retention and adaptation measures.

The experiment provides two useful contrasts. On GPT~6.1 Sol, some earlier
tests encoded a closed list of permitted view methods. A later feature
needed to extend that list, but the study rules protected accepted test files
from edits. Consolidation and visible-specification repair were associated
with more complete feature delivery in that setting. This points to an
interaction between generated tests, study rules and code structure.

On Gemini~4 Argon, the problem was a view that rejected named write methods
but forwarded newly added ones. Read-only review had more successful final
extensions than consolidation, despite consolidation's cleaner structural
metrics. Baseline metrics were low, but did not satisfy every stopping
target. The cell summaries establish neither why a session stopped nor
that a particular review action caused the difference. They illustrate
the distinction between structural hygiene and a rule such as ``every
write through a read-only view must be refused.'' A small function can
still violate that rule.

These observations support testing structural cleanup and checks of intended
behaviour together. Choosing when to interrupt delivery, changing product
goals, restoring a deployment and comparing human with agent steering
remain separate questions in the ancillary research agenda.

\subsection{What this study teaches a future experiment}\label{sec:futureexperiment}

The result surprised me. I had expected the experiment to expose decay and
was disappointed that it largely retained previously acquired behaviour.
I read this result as a reason to test the suspected burden with longer,
more complex work. The experiment examined a ten-feature horizon across
three current models; future research can vary task duration and complexity
to test this explanation. A follow-up must allow stable retention to remain
a legitimate result.

S1 nevertheless changed what needs measuring. Acquiring a feature,
preserving an established contract and adapting to a new requirement need
separate outcomes. A missing prerequisite can make a later change look
easier because there is less working behaviour to preserve. Several change
requests, evaluated on isolated branches, could probe adaptation without
changing the continuing delivery trajectory. More coupled brownfield work
could test whether implementation burden or loss emerges over longer
horizons, while keeping genuine acquisition failures visible.

The review-only result also changes the treatment question. I suspect that
the review stage of HVE Core's research, plan, implement and review workflow
may already supply useful correction. This experiment evaluated bounded
feature and post-feature sessions with discovery disabled. A future study can
estimate whether the full RPI sequence improves correction over feature-only
delivery, while separating the effects of review, refactoring, extra tests
and handover content where feasible.

The earlier numerical design candidates remain in Supplement
Section~\ref{app:futuredesign}, including longer trajectories, branch-isolated
change requests and component comparisons. They offer design inputs for a
future study; its task scale, resource needs and protocol require separate
development and review. Longer, more complex tasks are expected to require
substantially more tokens; the authors are postponing
that study pending resource estimates and spending approval. A later paper
would need a separately reviewed and prospectively registered protocol,
aligned randomisation and uncertainty analysis, and quality-matched costs.
This paper contributes the exploratory findings and the measurement lessons
needed to design it.

\subsection{Implications for practice}\label{sec:feedbackfirst}

The final report's Minimum Viable Experiment framework recommends
\textbf{adjust}: change the next study instead of adopting the full
consolidation package. On this workload, extra single-session allowance
left observed spending and outcomes similar, while unconditional
consolidation roughly doubled delivery credits. The report calls both
strategies \emph{no-go} at this horizon. Similar cell means do not establish
equivalence or explain why sessions stopped early.

The more promising question is when a particular correction is needed.
Structural cleanup helped with complex functions; review had a stronger
Gemini CR1 outcome; explicit repair offered another route past an
over-constrained test. Those separate observations motivate a triggered
hybrid, whose candidate commands and thresholds are retained in Supplement
Section~\ref{app:practicecandidate}. Its efficacy and cost advantage still
need testing. It would be premature to replace an established review
workflow with that unevaluated combination.

If you adopt scheduled consolidation, measure its added cost against retained
behaviour and success on a new requirement. In this study, structural
measures improved, but the coverage gain over longer sessions was 1.19
percentage points and change-request costs did not consistently fall.
The case also motivates protecting a usable increment, bounding the delivery
horizon and keeping lessons retrievable or executable. Its extensive evidence
trail suggests keeping routine intermediate tracking files out of the
squash-merged product diff after preserving durable findings and original
reviews. Selection must be finite, archive-backed and restore-verified,
including adverse reviews; mandatory safety, privacy, approval and publication
gates remain intact, and compact context views must retain their source evidence.
These practices, the proposed human-checkpoint cadence and preservation of
expertise remain untested. The ancillary context retains the fuller practice
checklist and framework-builder suggestions.

\section{Conclusion}\label{sec:conclusion}

Across the ten-feature S1 task, previously acquired behaviour was largely
retained. None of the 126 feature-only or longer-session runs had an open
regression at the final checkpoint ($P_{10}$); only one trajectory across
all arms did. Workflow replay found no witnessed losses across 626 evaluable
packets. The main failures were features that agents never acquired and a
permission-boundary hole exposed by the
withheld regional-access extension (CR1). Stable retention can therefore
coexist with incomplete or unsafe-to-extend software.

Consolidation (B) removed complexity hotspots at all 63 endpoints, but its
primary coverage advantage over longer feature-only sessions (D) was
1.19 percentage points (95\% interval [0.10, 2.22]), below the ten-point
minimum useful threshold. GPT~6.1 Sol supplied most of that gain by
completing priority ranking after an earlier test had fixed the permitted
view methods. Sonnet~5.5 and Gemini~4 Argon showed small B--D gains whose
intervals spanned zero. Read-only review (C) achieved 16/21 Gemini CR1
successes versus 8/21 with consolidation, while consolidation roughly
doubled settled delivery credits without consistently lowering CR1 cost.
The report's \emph{adjust} recommendation
motivates testing a combined pass triggered by code metrics or a halted
session. It would pair \texttt{./tcr} structural cleanup with review of
rules that must remain true as features change. The
combined policy has no measured efficacy or cost advantage in this study.

The motivating case concerns a different scale and failure: a migration
interrupted a usable workflow after extensive agent-assisted preparation.
Its five candidate mechanisms connect inherited obligations, lessons and
completion signals to opportunities for correction. The experiment did not
test those mechanisms individually. Together with the literature,
the two accounts motivate evaluating the system left for the next change.
They also explain why the next experiment needs a new design: longer,
more coupled work, several adaptation probes and comparisons that can
distinguish full RPI delivery from its corrective components
(Section~\ref{sec:futureexperiment}).

These are exploratory findings from one suite and one final change request.
Owner attestation covers all 315 completed trajectories; unregistered
amendments, two unadjudicated GPT~6.1 Sol CR1 test errors, 55 billing holds,
the 313/315 judging snapshot and sixteen execution sources limit inference.
The study also clarifies what future evaluations should measure. It began
with a decay hypothesis, found mostly stable retention and showed why
acquisition, adaptation and structural quality need separate measures.
A future paper can build on those distinctions to test
longer development loops and RPI-based correction, once a new protocol
and the larger resource commitment are approved. For practice, measure three
things: whether the system completes its intended task, whether it accepts
the next change, and what each improvement costs.

\section{Source and digest register}\label{app:source-register}

Record links such as \sourceref{R17} identify the retained version used for
a claim. Git commit
IDs identify repository revisions; tree IDs identify directory contents;
blob IDs identify individual Git objects. SHA-256 digests identify retained
file bytes or an image. Each identifier applies to a different kind of object. A matching digest
checks content identity; readers must still assess whether the content
supports a claim and whether it has been independently verified. Unless another repository is named, records refer to
\nolinkurl{jmservera/ama-thought-mve}. Historical and final records remain
separate even when they concern the same file.
