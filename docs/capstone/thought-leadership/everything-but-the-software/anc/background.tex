\section{Background}\label{sec:background}

\subsection{Accumulation and inherited state}\label{sec:decay}

Maintenance alongside growth is a recurring concern in software evolution
~\cite{lehman1980laws,lehman1997metrics,parnas1994aging}. Lehman's 1997
formulation states that quality declines without maintenance, but supplies
no data for or against that law. Eick et~al.\ found mixed evidence in more
than fifteen years of change history~\cite{eick2001decay}; a systematic
review likewise found uneven support across systems~\cite{herraiz2013laws}.
Counting features or changed lines cannot establish decay. A regression
requires previously working behaviour that is still required to fail.
An unimplemented capability is an acquisition failure, and a failure that
continues across changes is persistence. Showing that one failure caused a
distinct later defect requires tracing the dependency.

Cunningham describes shipping first-time code and rewriting it as
understanding improves~\cite{cunningham1992wycash}. Fowler's design
stamina is explicitly a hypothesis~\cite{fowler2007stamina}.
Reported debt costs depend on setting and measurement method: a
vendor-associated 39-codebase study reports 124\% longer issue resolution in
low-quality files~\cite{tornhill2022codered}.

\paragraph{What survives the next session?}\label{sec:inheritance}
A fresh session can inherit code, tests and deployment assumptions from the
repository, as well as instructions and handover notes. Either channel can
preserve a sound decision or carry a mistake forward
(Figure~\ref{fig:stateinheritance}). ``Software entropy'' is used here only
as an analogy for maintenance burden; the measured outcomes are retained
behaviour, adaptation and resource use.

\subsection{Evidence within and between features}\label{sec:empirical}

Conversational benchmarks identify dependence on erroneous histories.
Zhang et~al.\ study false justifications after
wrong answers~\cite{zhang2023snowball}; Sinha et~al.\ vary erroneous prior
state updates in a controlled execution task
~\cite[Secs.~2.2--3, Figs.~5--6]{sinha2025illusion}.

Pan et~al.'s SWE-Maintain more directly tests repository inheritance:
100 sequences of three maintenance tasks from 50 Python repositories.
Later tasks are matched across developer-written and agent-written histories,
with a fresh session for each task.
Across 1,996 paired later events, agent history reduces current-task
resolution by 5.6 points; requiring both current and earlier tests to pass gives
a 14.0-point gap. Unweighted mean current-task gaps grow from 4.0 to
7.2 points between the second and third events. In the selected
619-event clean-history subset, the current-task difference is
$-1.1$ points, interval $[-3.8,+1.6]$, and cumulative event resolution
differs by $+2.7$, interval $[-0.5,+6.1]$
~\cite[Secs.~4.1--4.2, Tables~2--3]{pan2026swemaintain}.
The smaller difference in the clean-history subset is consistent with
inherited behavioural failures contributing more than complexity alone.
However, the authors selected that subset; they did not randomly repair
the repositories. The comparison therefore cannot estimate the benefit of
a repair intervention or establish how widely the pattern applies.

Their \texttt{python\_unidiff} example reuses line-splitting logic that
loses terminators in a later constructor; Figure~1's caption introduces
it and Section~5.1/Figure~5 supplies the detail
~\cite{pan2026swemaintain}. SlopCodeBench and SWE-CI also evaluate agents over successive changes
~\cite{orlanski2026slopcodebench,chen2026sweci}. Evidence of downstream harm
is not uniform. Borg et~al.\ found no significant maintainability difference
for late-2024 assistants in a two-phase study where the second phase was
randomised~\cite[Secs.~1, 4]{borg2025echoes}. Differences in tool generation and collaboration
setting limit direct comparison.

\subsection{Instruction maintenance and evaluation}\label{sec:instructiondebt}

Instruction files themselves require
maintenance~\cite{nigh2025agentsmd,rajasekaran2025context}.
Mohsenimofidi et~al.\ assign 242 labels across nine categories to 169 commits.
A commit can receive several labels: 78 include instruction additions,
59 modifications and 23 removals
~\cite[Sec.~4.3, Table~2]{mohsenimofidi2026context}.
Chatlatanagulchai et~al.'s sampled maintenance labels likewise include
addition and pruning~\cite{chatlatanagulchai2026readmes}.
I use \emph{instruction debt} for obsolete, duplicated, conflicting or poorly
routed directives. This names a possible maintenance burden; the commit
counts alone do not measure its effect on development.

\begin{figure}[!htbp]
\centering
\includegraphics[width=0.94\linewidth]{fig-instruction-maintenance.png}
\caption{Labels in 100 sampled post-adoption commits, from
Chatlatanagulchai et~al., Sections~4.2.2--4.2.3. Labels overlap and
count edit types, not net token growth or effects on agent success.}\label{fig:instructionmaintenance}

\end{figure}

In their two benchmark comparisons, Gloaguen et~al.\ report 20\% and 23\%
higher inference cost with LLM-written context files. Success was lower by
0.5 and 2 percentage points, respectively; the success differences from
the no-file baselines were not statistically significant. Developer-written files outperform
LLM-written ones on CTXbench ($p=0.038$)
~\cite[Sec.~4.2, Tables~2--3]{gloaguen2026agentsmd}.
SkillOpt and Jiang et~al.\ provide counterevidence to treating retained
instructions as inherently harmful: evaluated procedural guidance can
help, while retrieval and downstream success remain distinct
~\cite{microsoft2026skillopt,jiang2026skills}.

\paragraph{Tests and review.}\label{sec:evaluationwork}
Evaluation needs to distinguish the requested outcome from the checks
used to accept it. RefactorBench tests refactoring tasks
~\cite{gautam2025refactorbench}, and SWE-Sharp-Bench supplies reproducible
repository evaluation~\cite{mhatre2025swesharp}. CRBugBench examines the
limits of automated review~\cite{yang2026crbugbench}; observations of
developer-agent collaboration describe practice without isolating its
causal effects~\cite{kumar2025agents}. In Building to the Test, seven of
twelve oracle-in-the-loop runs left a required library dead or absent
~\cite{ma2026building}. ImpossibleBench examines test exploitation more
broadly~\cite{zhong2026impossiblebench}. Protecting tests against edits is
therefore separate from checking that they cover the intended behaviour.
AgentRx provides a precedent for traceable failure diagnosis
~\cite{microsoft2026agentrx}.

\paragraph{Bounded correction.}\label{sec:factory}
Pavlenko et~al.'s factory optimises human-architected systems against
measurable objectives; productivity estimates cover application work,
excluding infrastructure and onboarding
~\cite{pavlenko2026factory}. That evaluation does not isolate the present
between-feature intervention and later change probe.

\paragraph{Reflection and self-improvement.}
Ng's reflection design-pattern letter explicitly recommends Self-Refine,
Reflexion and CRITIC~\cite{ng2024reflection}, attributing methods developed
by their respective authors. Self-Refine iterates feedback and revision with the same model
without training~\cite[Sec.~2]{madaan2023selfrefine}. Reflexion retains
linguistic feedback in episodic memory for subsequent trials rather than
updating model weights~\cite[Sec.~3]{shinn2023reflexion}. CRITIC uses
external tools to check and revise an output
~\cite[Sec.~3]{gou2024critic}. These methods provide ways to revise work using feedback. Their
repeated-trial budgets and feedback differ from this experiment: hidden
evaluator outputs never reach the development agents. Whether a retained
revision helps with a different, later feature remains an empirical question.

Ng coauthored MedAgentBench, which evaluates task completion in an
interactive medical-record environment rather than chatbot answers alone
~\cite[arXiv v2, Secs.~2.3--2.4]{jiang2025medagentbench}.
Its evaluation of observable action outcomes informs the measurement focus
of this protocol.

\paragraph{Engineering rationale.}\label{sec:practitioners}\label{sec:theory}
Beck's alternation of features and tidying aims to restore future
options~\cite{beck2023tidy,beck2025devslow,beck2026prodacity}.
Extending that metaphor to acceptance criteria is my interpretation.
Beck separates producing code from learning
through working software~\cite{beck2026prodacity}.
Tests, short releases, explicit design responsibilities and usable
increments motivate the checklist
~\cite{beck2002tdd,beck2004xp,
naur1985theory,brooks1987silver,royce1970,gall1975,cockburn2004crystal,
hunt1999pragmatic,agile2001manifesto}.
Monitoring burden and completion proxies qualify the rationale
~\cite{bainbridge1983ironies,simkute2024ironies,tankelevitch2024metacognitive,
lee2025critical,goodhart1975,strathern1997improving,cohen2006review}.
Spec-driven tools structure handoffs; the intended outcomes still need
execution checks~\cite{delimarsky2025speckit,boeckeler2025sdd,agarwal2026sdd,waseem2025vibe}.
