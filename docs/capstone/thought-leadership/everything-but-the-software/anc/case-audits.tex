\subsection{Measures and lexicon}\label{app:measures}

\paragraph{Log entries.} The knowledge-base log
(\texttt{docs/reference/log.md}) was split into entries at each second-level
heading that begins with a date. An entry belongs to the date in its heading.
Word counts use whitespace tokenisation of the entry, heading included.

\paragraph{Evidence-boundary phrases.} Each entry was searched, case-insensitively and
on word boundaries, for these patterns: \emph{unmet}; \emph{not accepted};
\emph{not inferred}; \emph{is inferred}; \emph{remain{(s)} open};
\emph{remain{(s)} unproved}; \emph{remain{(s)} unverified}; \emph{not claimed};
\emph{not established}; and \emph{no} followed, within forty letters, spaces,
commas, slashes or hyphens, by \emph{is} or \emph{was} and then
\emph{claimed} or \emph{inferred}. Density is matches per 1,000 words.

\paragraph{Reference tracing.} An entry cites the simplicity requirements if
it contains an identifier from SA-001 to SA-010 or the word
\emph{simplicity}. It cites the development profile if it contains
\emph{deploymentProfile}, \emph{development profile} or
\emph{allowPublicNetworkAccess}.

\paragraph{Repository counts.} Issue and pull-request counts come from the
GitHub search API on 24 October 2026 (for example,
\texttt{is:pr is:merged merged:>=2026-10-15}). Document sizes are whitespace
word counts at the original case snapshot (\sourceref{R01}).

\paragraph{Proposed measures.} \emph{Time to first human use}: elapsed time
from the start of a delivery cycle to the first time a person uses the running
increment for its purpose\@. \emph{Age of the last usable increment}: time since
a person last verified that the deployed system could be used for its main
journey\@. \emph{Behaviour-changing merge ratio}: the share of merged pull
requests that change what a user can observe in the running increment.
\emph{Cost per accepted outcome}: total model, tool and cloud cost divided by
the number of outcomes a human accepted in the same period. Predeclare the
outcome unit, counting rule, attribution and period. With zero accepted
outcomes the ratio is undefined; report the total cost and zero count.

\subsection{An assumed payback model}\label{app:economics}

The earlier cost model assumes that consolidation reduces a growing
implementation premium (Section~\ref{sec:costprojection}). Its parameters
were not fitted to the ten-feature observations. For example, its
$k=5,\delta=0.5$ scenario means spending five credits on consolidation
every cycle while the assumed excess implementation cost without it
increases by half a credit per successive cycle. Those assumptions give
break-even at cycle 21; the experiment does not estimate that growth rate.

Let $N\geq1$ be an integer number of feature cycles, $k$ the assumed average consolidation
investment in AI credits per cycle, and $\delta\cdot(t-1)$ the assumed excess
feature-implementation cost in A relative to B at cycle $t$, excluding
B's consolidation session. Shared baseline implementation costs cancel.
Under the explicit simplifying assumptions of constant $k$, a linearly
growing relative premium $\delta\geq0$, and comparable delivered behaviour,
the cumulative net difference is
\begin{equation}
\Delta C(N)=C_A(N)-C_B(N)
=\sum_{t=1}^{N}\bigl[\delta(t-1)-k\bigr]
=\delta\frac{N(N-1)}{2}-kN.
\label{eq:costprojection}
\end{equation}
The first term sums the assumed extra implementation cost without
consolidation; the second subtracts B's consolidation investment.
A positive value means A costs more within this assumed model.
Experimental savings would require measured, quality-matched costs.
For $k>0$ and $\delta>0$, the first cycle count with $\Delta C(N)\geq0$ is
$N_{\mathrm{BE}}=\lceil1+2k/\delta\rceil$; when $\delta=0$, the investment never pays back in
this credit-only model.
The parameter $\delta$ describes how the cost gap between A and B grows;
it does not measure either arm's total debt.

\subsection{Retained follow-up design candidates}\label{app:futuredesign}

The numerical candidates behind Section~\ref{sec:futureexperiment} are
retained here for a separate study. Their task scales, thresholds, allocations
and analysis choices require design review, feasibility estimates, spending
approval and prospective registration. They do not amend the completed
experiment, and a longer task could still show stable retention.

\paragraph{Longer trajectories and greater coupling.}
In the assumed cost model, break-even depends on investment $k$ and the
relative cost-growth slope $\delta$: $N_{\mathrm{BE}}=\lceil 1+2k/\delta\rceil$
for positive parameters (21 cycles at illustrative $k=5,\delta=0.5$).
Measured consolidation sessions cost $5.82$--$12.59$ credits, but the pilot
does not estimate long-run $\delta$ or when coupling and context limits matter.
Its ten greenfield features produced roughly 440--780 Python source lines.
A follow-up could extend
trajectories to $N=30$--$40$ sequential feature and schema-evolution cycles
on a multi-module brownfield service repository ($3{,}000$--$10{,}000$
source lines) with persistent storage, cross-cutting permission invariants
and scheduled interface migrations, recording retention and cost slopes at
$P_{10},P_{20},P_{30}$ and $P_{40}$.

\paragraph{One final change request and unequal starting functionality.}
Evaluating adaptation on one held-out CR1 after $P_{10}$ produced wide
binomial intervals ($\pm18.8$ to $\pm48.0$ percentage points within models)
and coupled retention obligations to whether F9 ranking had been acquired.
A follow-up protocol could schedule $K\geq4$ orthogonal change requests in
a Latin-square design across checkpoints $P_{10},P_{20},P_{30}$ and $P_{40}$.
Each change request should execute on an isolated branch forked from $P_t$
so adaptation measurement does not alter the main delivery trajectory, and
should be scored both unconditionally and on a core contract set whose
prerequisites are verified before the fork.

\paragraph{Separating the parts of consolidation.}
Arm~B combined behaviour-preserving code refactoring, new agent-authored
tests under an immutable test-file rule and \texttt{DESIGN.md} replacement,
while Arm~C changed both editing rights and checklist content. A $2\times2$
factorial core crossing \emph{behaviour-preserving code refactoring} (with
test files locked) against \emph{explicit invariant and boundary review}
(\texttt{REVIEW.md} targeting authorization, state transitions and
cross-module contracts), paired with a controlled factor comparing
\emph{immutable versus specification-revisable agent tests}, could help
distinguish test-rule effects from refactoring and boundary review.
Component fidelity, interaction effects and other treatment differences
would still need explicit controls.

\paragraph{Decision thresholds, dependence and recovery rules.}
The earlier candidate thresholds were $\geq5\%$ open-regression loss among
acquired contracts by $P_{30}$ or per-cycle implementation-credit growth
of $\delta\geq0.5$ credits per cycle for P1, a task-calibrated minimum
useful B--D coverage gain $\Delta_*$ for P2, and cumulative net credits
$\Delta C(N)>0$ at matched behavioural coverage for P3.
These criteria await protocol review and approval; no estimates have been
collected under them.
A new protocol should justify its thresholds and align randomisation and
variance estimation, considering $(\mathrm{model},\mathrm{replicate})$
blocks, a block bootstrap or a mixed model as appropriate to the actual
allocation and dependence. Bounded transport retries, missing-data rules
and the primary estimand must be settled before collection.

\paragraph{Full RPI versus corrective components.}
I also propose comparing the full research, plan, implement and review
workflow with feature-only delivery.
Testing the package would not by itself identify review's contribution.
A component comparison must specify instructions, editing and test rights,
handover, context, sessions and budgets, and record actual resource use.
No RPI variant, allocation, effect threshold or spending is approved here.

\subsection{Untested hybrid practice candidate}\label{app:practicecandidate}

The report proposes combining the structural cleanup, semantic review and
audited repair represented separately by Arms~B, C and E.
Automated \texttt{./tcr} refactoring with \nolinkurl{tools/quality.py}
eliminated all complexity-$>10$ hotspots across all 63 Arm~B trajectories
and was associated with greater GPT~6.1 Sol F9 acquisition. Read-only review
(\texttt{REVIEW.md} in Arm~C) had higher observed Gemini~4 Argon CR1 success
($76.2\%$ versus $38.1\%$), and Arm~E's audited
\texttt{REPAIR.json} rule achieved $95.2\%$ CR1 success on GPT~6.1 Sol.
The proposed combined step would be triggered when cyclomatic complexity
exceeds 10, duplication reaches $3\%$, lint is nonzero, a feature session
halts uncommitted, or periodically every three to five features. It would
include C's semantic-invariant checklist and an audited test-assertion
escape hatch. The commands and thresholds come from the report's proposal. The combined
policy's efficacy, stopping behaviour and cost have not been measured.
