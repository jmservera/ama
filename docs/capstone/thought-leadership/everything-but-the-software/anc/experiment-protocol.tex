\section{Experiment: design and results}\label{sec:experiment}

To address RQ3, we compared scheduled correction with feature-only delivery
and longer sessions on the same task. The five-arm exploratory study and
post-collection evaluation completed in November 2026. Its planning drew on
agent-configuration protocols and empirical-study guidance
~\cite{lulla2026protocol,baltes2026guidelines,wohlin2012experimentation}.

\subsection{Task and comparison groups}\label{sec:protocolsummary}

Each run starts with a fresh repository. An agent develops it through
ten ordered features, then receives the withheld change request, CR1.
That complete development run is the experimental unit, called a
\emph{trajectory}. A \emph{cell} contains runs using the same model and
comparison group, or arm. The analysis treats trajectories as independent
within cells; shared execution conditions limit that assumption
(Section~\ref{sec:protocollimits}).

The task, S1, is a standard-library Python package called \texttt{workbench}.
It represents synthetic retrofit cases through an API, rather than the
deployed application's browser and sign-in path. Its features cover lifecycle,
handoffs, consent, permissions, ranking and audit. A resident's withdrawal of
consent pauses installation; a safety hold takes precedence over that
pause. Contractor views must hide contact and vulnerability fields and
refuse every write. CR1 adds postcode-prefix regions, region-scoped users
and manager-approved cross-region handoffs.
The notation $F_t$ denotes the state after feature $t$. In B, C and E,
a consolidation, review or repair session follows; $P_t$ denotes the
state after that follow-up, called a \emph{post-step}. These states
coincide in feature-only arms A and D, which have no follow-up session.
Thus $P_{10}$ is the final ten-feature repository before the withheld extension.
Every selected model, GPT~6.1 Sol, Sonnet~5.5 and Gemini~4 Argon,
runs every arm. The scheduler randomises model order within each replicate, then arm order
within each model, using seed 2027. Its parallel dispatcher can admit later
eligible trajectories as workers become free; a five-arm scheduling group
is therefore not a synchronized execution batch. Feature steps, tests, checkpoints and agent sessions provide repeated
observations within a trajectory. Counting them as separate replicates
would overstate the sample size. The selected number $n$ applies
\emph{per model per arm}, equally across all fifteen cells.

\subsection{Development and evaluation execution boundaries}\label{sec:runtimeboundaries}

The runtime separates the model connection from execution of the code
an agent produces (Figure~\ref{fig:runtimeboundaries}). The trusted host runs the Python
experiment controller and JavaScript Copilot SDK/CLI transport. Prompt
preparation and the authenticated model connection remain on that host.
The development model can request \texttt{isolated\_exec}; a Python broker
runs each requested command in a fresh isolated container, returning bounded
stdout, stderr and exit status through the transport to the model.
For the next call, the broker restores validated filesystem/Git state into
a fresh writable isolated workspace. Each command therefore starts in a
new container, with no surviving candidate processes or process memory.
The host checkout remains protected. The host/model conversation continues
across calls.
Only validated committed regular content crosses feature/CR checkpoints;
the host canonicalises history rather than retaining arbitrary actor
commit metadata.
Visible-test verification and hidden measurements use separate evaluator
containers after development steps.

The supplementary post-run path begins with a stopped local study archive.
Host Python selects recorded checkpoint HEADs and asks the broker to replay
fixed API workflows through \nolinkurl{judging/execute.py}.
Candidate snapshots and evaluator code are mounted read-only.
The replay collects bounded observations, failures and errors in anonymised
evidence packets, each a record for one trajectory at one endpoint.
Host Python then invokes the configured adapter; the JavaScript
\nolinkurl{copilot-judge.mjs} establishes a separate tool-free Copilot
session. The judge receives the packet and returns ordinal ratings,
rationales and evidence citations for host-side validation and reporting.
It has no command tools or candidate-repository access. Its model connection
is outside the replay container; candidate isolation does not place the
AI judge or host orchestration inside that sandbox.

The broker's candidate-execution containers disable networking, use a
read-only root filesystem and set \texttt{no-new-privileges}, with CPU,
memory, process and time limits. Docker uses \texttt{--cap-drop=ALL}
but re-adds four for its protected supervisor; the candidate child runs
as UID/GID 1001 with cleared effective, permitted and inheritable
capabilities. Those four supervisor capabilities remain at the container level even
though they are cleared for the candidate child.
Development workspace mounts remain writable; replay snapshot/evaluator
mounts are read-only. Copilot authentication stays with the trusted host transport.
An isolation or collection failure leaves the checkpoint unavailable.
If collection succeeds and the candidate fails, that failure remains in
the evidence. It does not automatically make the checkpoint unavailable
or assign a zero judge rating. These boundaries describe the inspected
source. Their enforcement was not adversarially proven or verified across
every archived execution version.

\subsection{Outcomes and retained-contract loss}\label{sec:decaymeasurement}

The primary outcome is the proportion of all 127 feature contracts passed
at $P_{10}$, before CR1. Each contract checks a required behaviour through
a fixed hidden test, such as refusing a write through a contractor view
or producing the same ranking from the same state.
We call this \emph{behavioural coverage}; it is
not instrumented line or branch coverage. A higher score can reflect acquisition, retention
or repair, so the analysis examines those outcomes separately.
Retained-contract loss and CR1 adaptation are distinct secondary outcomes,
with legacy identifiers H2 and H6 retained only for data traceability.
HIR/IDR definitions are in the supplementary appendices;
comprehension is not measured.

\paragraph{Who measures, and what ``quality'' means.}
During development, models implement features, consolidate code, write
review notes or repair defects as assigned treatments.
The separate host evaluator (\sourceref{R05}) runs fixed hidden
contracts and code-analysis tools, writes \texttt{measure.json} and computes
the numerical summaries. It does not call a separate LLM-as-judge. Table~\ref{tab:measurementprovenance} separates
outcomes, structural proxies and resource observations.
Complexity, duplication and lint describe selected code properties. They
did not establish CR1 read-only enforcement in Gemini's cleaned repositories
(Section~\ref{sec:resultscorrectness}). Overall architecture quality,
readability and comprehension require other evidence. The active metric
dictionary contains no maintainability-index score.

\paragraph{How AI review enters the experiment.}
Arm C's model reads \nolinkurl{reports/quality.md} and the feature diff, then
rewrites \texttt{REVIEW.md} in at most 300 words using a checklist of
duplication, complex functions, names, dead code, responsibilities and
behaviour-focused tests. The review can vary between model sessions. The kit retains the note
without converting it into a numerical quality score. Arm B uses a similar checklist to guide changes.
Its complexity $\leq10$, duplication $<3\%$ and zero configured-lint-warning
targets are requested stopping conditions and treatment-fidelity checks.
\texttt{make check} runs tests and generates the metrics report; the report
writer does not itself assert that all three structural targets are met.
The runner enforces the time budget, protected tests and retained green
code, rather than accepting an AI statement as an independent quality verdict.
The exact checked-in B/C examples, parameter substitution and saved-prompt
limitations are in Supplement Section~\ref{app:activeprompts}.

The earlier design specified the risk sets and reporting rules below.
The inspected analyzer exports a more conservative summary, as explained
after Equation~\ref{eq:decayloss}. The distinction is a reporting gap,
not evidence that the richer export was completed.

For trajectory $r$, $F_t$ is the retained state after feature step $t$ and
$P_t$ the state after its assigned post-step; these source states coincide
in A and D. Let $\mathcal{R}_{r,t}$ contain eligible, unchanged contracts
that passed at least one earlier end-of-cycle checkpoint $P_u$, $u<t$.
Superseded contracts leave this risk set. This \emph{risk set} includes only contracts that could now be lost because
they worked before and are still required. At $F_t$ and $P_t$, let
$\mathcal{O}^{p}_{r,t}\subseteq\mathcal{R}_{r,t}$ contain contracts with
observed binary results $S^p_{r,t}(q)$, $p\in\{F,P\}$. Report
\begin{equation}
L^p_{r,t}=\sum_{q\in\mathcal{O}^{p}_{r,t}}
\mathbf{1}\{S^p_{r,t}(q)=0\},\qquad
d^p_{r,t}=\frac{L^p_{r,t}}{|\mathcal{O}^{p}_{r,t}|}.
\label{eq:decayloss}
\end{equation}
Here $L$ counts observed failures among previously acquired contracts, and
$d$ divides that count by the observed risk-set size. The fraction is
undefined when its denominator is empty. Missing earlier checkpoints can
leave acquisition unknown, so the proposed report retains per-contract
results and that uncertainty; a missing observation is not an acquisition
failure.
Publish the full risk set, observed subset and missing count
$M^p_{r,t}=|\mathcal{R}_{r,t}|-|\mathcal{O}^p_{r,t}|$ alongside it.
The full-risk loss count lies between $L^p_{r,t}$ and
$L^p_{r,t}+M^p_{r,t}$; missing evaluations cannot be treated as passes.
Never-acquired contracts remain acquisition failures.
Retain onset, recovery, recurrence and uncertainty across missing
checkpoints. Recovery does not erase an episode. Distinguish same-cycle
post-step losses and rejected attempts from losses in retained code.

\subsection{Supplementary post-run workflow assessment}\label{sec:postrunjudging}

After collection, a fixed panel replayed API workflows against archived
S1 checkpoints. This supplementary assessment was designed and run after
development; it left the treatment budgets and original coverage, retained-contract-loss
and CR1 endpoints unchanged. Development agents were neither rerun nor
allowed to repair their repositories. The 9 November proposal at
\sourceref{R36} remains a historical source record; the completed instrument,
runtime and assessment lineage are recorded in Supplement
Section~\ref{app:postrunjudging}.

The panel exercised ten feature workflows, a delivery/reopening journey
and a separate CR1 workflow. For each scenario, the evaluator looked for an
earlier successful execution at an eligible end-of-cycle checkpoint in the
same development run. The report calls that passing execution a
\emph{witness}. A failing final scenario counted as witnessed loss only
if it had passed earlier. A scenario that never passed remained an
acquisition failure. Post-CR1 loss could include a
failure already present at $P_{10}$, so it did not isolate damage caused
by CR1. These scenarios complemented the hidden contracts by exercising
longer workflows with a different, narrower set of checks.

A separate, tool-disabled judge model, \texttt{gpt-6-luna}, rated each
evaluable endpoint twice in fresh sessions. It received anonymised
execution evidence and returned four separate ordinal 0--4 ratings:
functional completeness, workflow coherence, error recovery and API
usability. Ratings required final-observation citations, with null values
where evidence was insufficient. They concern the exercised API tasks;
no human interface usability study was performed. The packets also exposed
earlier passing witnesses and retention labels, allowing historical
anchoring despite anonymisation: a judge could see that a scenario had
worked earlier before rating its final state. The judge shares a provider/model family
with the development model \texttt{gpt-6.1-sol}.

The assessment provides supplementary exploratory evidence. Development-time
review remained an intervention, separate from outcome judging. A
\emph{complete-frame contrast} requires observations for all allocated
trajectories in both compared arms for every development model; each model
contributes equally. Repeated ratings, scenarios
and checkpoints remained nested within trajectories. Results, missingness
and the human spot-check are reported in Section~\ref{sec:resultsjudging};
judging costs are accounted for separately.

\subsection{Replication and uncertainty}\label{sec:protocollimits}

The 2 November planning record offers $n\in\{12,21,33\}$ independent
repository trajectories per model per arm, with \textbf{12 as the default};
current execution selects 21. That record calls for the choice, rationale,
planning SD, power/precision trade-off, date and source-bound configuration
to be recorded before collection. It does not establish that the current
amendments were prospectively registered. Selecting a sample size does not
establish that its associated SD assumption is true.
The saved allocation is immutable on resume. Outcome-driven sample-size
changes, additions and replacements are prohibited; interim coverage,
loss, CR1 success or other outcomes cannot determine $n$.

Servera Bondroit selected a minimum useful absolute coverage gain of ten
percentage points, approximately thirteen test-weighted contracts.
Coverage scores $Y$ are expressed on the 0--100 scale. Let
$\overline{Y}_{ma}$ be mean final coverage for model $m$ and arm $a$.
The primary estimand, the quantity the study aims to estimate, is the
difference in mean coverage averaged equally over the $M=3$ selected models.
Each model contributes one-third of the result, regardless of its coverage
level. The estimator calculated from the observed trajectories is
\begin{equation}
\widehat{\Delta}_{BD}=\frac{1}{M}
\sum_{m=1}^{M}(\overline{Y}_{mB}-\overline{Y}_{mD}).
\label{eq:primarycontrast}
\end{equation}
For balanced cells of $n_{\mathrm{cell}}$ independent trajectories and a
common within-cell variance $\sigma^2$, its planning variance is
$2\sigma^2/(M n_{\mathrm{cell}})$, with $n_{\mathrm{cell}}=n$.
For one two-sided comparison with $\alpha=0.05$, target power
$1-\beta=0.80$ and target difference $\Delta_*=10$ points, the normal
planning minimum, conditional on the assumed SD, is
\begin{equation}
n_{\mathrm{plan}}(\sigma)=
\left\lceil\frac{2{(z_{1-\alpha/2}+z_{1-\beta})}^2\sigma^2}
{M\Delta_*^2}\right\rceil.
\label{eq:samplesize}
\end{equation}

Actual within-cell variability was unknown at planning. Target power
depends on independent trajectories,
the common variance, normal approximation and equal-model estimand; it is
not guaranteed by any offered choice. In particular, default $n=12$ is
\emph{not} an 80\%-power design under the existing SD of 25 points.
The bounded score's worst-case SD is 50, requiring 131 per cell under
the same approximation; that is outside the offered allocation choices.
These planning requirements and assumptions are retained from the earlier
record. Neither the registered base nor selection of $n=21$ establishes
their validity for evolving-source exploratory data.

The reported independent-cell analysis uses a bootstrap that samples whole
trajectories with replacement within each model/arm cell.
The 2.5th and 97.5th percentiles of 10,000 resulting estimates give each
95\% interval. The inspected v6 code uses independent arm/model draws; it
does not preserve joint scheduling-block draws.
The inspected primary analysis requires metadata for every allocated
trajectory across the five arms and all models, known unassisted status
and observed final coverage for the contributing B/D trajectories.
Otherwise it reports the primary estimate unavailable. All allocations and
costs remain in the record; a secondary summary of only observed models or
complete cases cannot replace the primary estimate. An earlier missing H2
checkpoint can coexist with an observed final coverage or CR1 endpoint.
This availability rule also needs explicit adoption or prospective
revision in the approved study record.
Model-specific estimates and other contrasts are secondary, with no
family-wide coverage claim.
Retain scheduling-block identifiers. The earlier source-bound review
identified an unresolved choice between this independent-trajectory
variance/bootstrap scheme and model/replicate blocking.
Trajectories with the same scheduling label may share execution conditions,
but the label alone cannot establish their dependence or independence. Scheduling-only blocks with independent
inference require justification; block-aware analysis would require a
separately approved, disclosed choice and aligned planning variance.
Shared block/service effects remain unmeasured; the v6 source freeze
does not resolve this choice. We preserve the analysis actually performed
as a conditional exploratory summary. Its nominal 95\% coverage depends
on within-cell trajectory independence and does not account for
execution-epoch confounding or shared provider conditions. An interval
excluding zero is therefore not a confirmed causal or generalisable
treatment effect.
Public run identifiers allow the model/replicate scheduling groups and
source epochs to be reconstructed. Retained operator metadata also contain
start times and controller durations for every attempt (Supplement
Section~\ref{app:executiondetail}). Those intervals describe controller activity. They do not show whether
requests shared provider conditions or whether their errors were independent. The reported companion intervals retain the analysis actually
performed; a dependence-sensitive comparison would be a separately
disclosed post-collection analysis.
No dependence-sensitive reanalysis or additional experimental round is
included in this paper. The incomplete outcome-access chronology and
dependence justification are recorded limitations; a deeper study needs
prospective timing, source and exposure records and inference aligned

\subsection{Resource and information boundaries}\label{sec:prerun}

The experiment distinguishes resources an agent could use from resources
it actually consumed. A larger allowance may leave spending unchanged
when a session exits early; a transport interruption may leave a charge
unknown even after the development work is complete. The results report
observations and unresolved liabilities separately. Historical planning
scenarios remain in Supplement Section~\ref{app:resources}, including
Table~\ref{tab:pilotresources}; they retain the earlier full-calibration
assumption and do not establish that historical launch gates were met.

The actual aggregate envelope remains 300,000 AI credits, with a
270,000-credit local admission ceiling: the controller must stop admitting
new work when spending and reserved liabilities reach that amount.
Prior spending and provisions for
unknown historical usage remain charged or held against remaining
admission; unknown usage is never zero or free headroom.
Original 300-credit sessions use a 270-credit soft limit; D's
600-credit feature uses 540. A retry shares the original allowance.
In-flight responses can overshoot; these are not provider billing caps.
No verified dollar conversion is available.

The historical plan required the selected allocation, calibration and
all-attempt liabilities to fit the remaining envelope and deadline before
collection. It prohibited outcome-driven resizing or silent reductions to
fit the budget. Its detailed arithmetic remains in the Supplement.
The launcher inspected on 5 November enforces attempt and aggregate admission but does
not compute or approve that full-allocation forecast. A dated researcher
forecast and approval are required separately; a nonempty calibration
note is insufficient.
Proposed progression criteria are infrastructure failures at
most 5\%, no missing primary observations, complete billing/model/help
records, zero oracle contradictions in triplicate reference checks,
and no information-boundary failure. Hidden-test mutation assessment
must report its actual mutant denominator and unresolved equivalence.
These operational feasibility criteria cover infrastructure and measurement
readiness before full collection.

Only current and previous visible specifications and examples reach
candidate tools. Hidden tests, scores, identifiers, messages, reference
code and future CR1 remain external. Candidate commands use no-network
containers; the trusted host SDK's provider connection is different.
The earlier plan called for a researcher-managed protected workspace
without the original case repositories, manuscript or session-context
caches. Cabezas Martin's current execution role is separate from design
and manuscript preparation; coauthorship supplies no evidence of blindness
or actual access restrictions. Record actual access and prior exposure.
The earlier repository-privacy and later approved-release plans remain
historical intentions, not inspected current visibility.
OSF status and GitHub privacy are separate; neither removes prior public
or model exposure. The historical registered-freeze path and current
disclosed unregistered path have different registration status.
This manuscript update neither verifies operational approvals nor changes
information boundaries, budgets, configuration or launch permissions.

Unsuccessful feature increments are reset; later features and scheduled
B/C/E post-steps continue on retained green state. Hidden denominators
still include undelivered features. One infrastructure-only retry shares

Contradictory valid oracle results halt collection.
