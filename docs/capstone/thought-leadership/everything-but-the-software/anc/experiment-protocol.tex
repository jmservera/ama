\section{Experiment: design and results}\label{sec:experiment}

To address RQ3, we compared scheduled correction with feature-only delivery
and longer sessions on the same task. We completed the five-arm exploratory study and post-collection evaluation in November 2026, following planning informed by
agent-configuration protocols and empirical-study guidance
~\cite{lulla2026protocol,baltes2026guidelines,wohlin2012experimentation}.

\subsection{Execution status and disclosed amendments}\label{sec:studyexecution}

We completed the five-arm exploratory study under an OSF-registered base
and disclosed unregistered amendments. Data availability identifies the public
repositories and OSF registrations; the Supplement preserves the amendment chronology,
sixteen execution versions and recovery decisions without treating public
version control as retrospective registration.

Each of three models, GPT~6.1 Sol, Claude Sonnet~5.5 and Gemini~4 Argon,
ran all five arms at medium effort, with 21 trajectories per model and arm:
$3\times5\times21=315$. The scheduler used seed 2027; we divided execution and collection from design and analysis as stated in Author contributions. Section~\ref{sec:threats} explains the resulting
limits on inference.

\subsection{Task and comparison groups}\label{sec:protocolsummary}

Each agent starts with a fresh repository, develops it through ten ordered features and then receives the withheld change request, CR1;
that complete development run is the experimental unit, called a
\emph{trajectory}. A \emph{cell} contains runs using the same model and
comparison group, or arm, and the analysis treats trajectories as independent
within cells; shared execution conditions limit that assumption
(Section~\ref{sec:protocollimits}).

The task, S1, is a standard-library Python API package called \texttt{workbench}, covering synthetic case lifecycle, handoffs, consent, permissions, ranking and audit, with consent withdrawal pausing installation unless superseded by a safety hold. Contractor views must hide contact and vulnerability fields and refuse every write, requirements that CR1 extends with postcode-prefix regions, region-scoped users and manager-approved cross-region handoffs.
The notation $F_t$ denotes the state after feature $t$, and in B, C and E,
a consolidation, review or repair session follows; $P_t$ denotes the
state after that follow-up, called a \emph{post-step}. These states
coincide in feature-only arms A and D, which have no follow-up session, so $P_{10}$ is the final ten-feature repository before the withheld extension.
Every selected model, GPT~6.1 Sol, Sonnet~5.5 and Gemini~4 Argon,
runs every arm; using seed 2027, the scheduler randomises model order within each replicate and arm order within each model. Its parallel dispatcher can admit later
eligible trajectories as workers become free; a five-arm scheduling group
is therefore not a synchronised execution batch. Feature steps, tests, checkpoints and agent sessions provide repeated
observations within a trajectory. Counting them as independent replicates would overstate the sample size.
The selected number $n$ applies
\emph{per model per arm}, equally across all fifteen cells.

Because these comparisons change several conditions together, they cannot
isolate refactoring or any one of the case mechanisms.

specific contradictory specification and a recorded explanation.
Accepted Python test files are immutable in full, including imports, fixtures and module/class constants, with additions confined to new files; E has only its explicit specification-bound correction exception, with immutable example tests protected in every arm.

\subsection{Development and evaluation execution boundaries}\label{sec:runtimeboundaries}

The trusted host runs the controller and authenticated Copilot SDK/CLI
transport; a broker executes each requested command in a fresh
container and returns bounded output and exit status
(Figure~\ref{fig:runtimeboundaries}). Validated filesystem and Git state
carry into the next writable workspace, but candidate processes and process
memory do not; the host/model conversation continues across calls.
Only validated committed regular content crosses feature/CR checkpoints,
and visible-test verification and hidden measurement run in other
evaluator containers after development steps.

For supplementary assessment of a stopped local study archive, host Python selects recorded checkpoint HEADs and asks the broker to replay
fixed API workflows.
With candidate snapshots and evaluator code mounted read-only, the replay collects bounded observations, failures and errors in anonymised
evidence packets, each a record for one trajectory at one endpoint.
Host Python then invokes a tool-free judge session, which returns ordinal
ratings, rationales and evidence citations without command tools or
candidate-repository access, with its model connection and the host orchestration
operate outside the replay container.

Candidate commands used network-disabled containers with bounded resources;
the trusted host held authentication and model transport, and the Supplement
gives the capability and mount configuration, including the distinction
between supervisor and candidate privileges. Isolation failures made a
checkpoint unavailable, whereas observed candidate failures stayed in the
assessment. This was source inspection rather than adversarial security evaluation.

\subsection{Outcomes and retained-contract loss}\label{sec:decaymeasurement}

The primary outcome is the proportion of all 127 feature contracts passed at $P_{10}$, before CR1. Each contract uses a fixed hidden test to check required behaviour, such as refusing a write through a contractor view or reproducing a ranking from the same state.
We call this \emph{behavioural coverage}, distinct from instrumented line or
branch coverage, and distinguish acquisition, retention and repair when
interpreting an increased score.
Retained-contract loss and CR1 adaptation are distinct secondary outcomes,
with legacy identifiers H2 and H6 used for data traceability.
The supplementary appendices define HIR/IDR; comprehension was not measured.

\paragraph{Who measures, and what ``quality'' means.}
During development, models implement features, consolidate code, write
review notes or repair defects as assigned treatments.
The host evaluator runs fixed hidden contracts and code-analysis tools,
then computes numerical summaries without calling an LLM-as-judge.
Supplement Table~\ref{tab:measurementprovenance} distinguishes outcomes, structural proxies and resource observations.
Complexity, duplication and lint describe selected code properties without verifying CR1 read-only enforcement in Gemini's cleaned repositories
(Section~\ref{sec:resultscorrectness}). Overall architecture quality, readability and comprehension require other evidence, and the active metric dictionary contains no maintainability-index score.



The evaluator records errors, skips and timeouts rather than treating a
missing or non-binary endpoint as a pass; Supplement
Section~\ref{app:measurementprovenance} specifies raw fields and tool settings.

\paragraph{How AI review enters the experiment.}
Arm C's model reads the quality report and feature diff, then
replaces its review note in at most 300 words using a checklist of
duplication, complex functions, names, dead code, responsibilities and
behaviour-focused tests. The review can vary between model sessions, and the kit archives the note without converting it into a numerical quality score. Arm B uses a similar checklist to guide changes, with complexity $\leq10$, duplication $<3\%$ and zero configured-lint-warning
targets serving as requested stopping conditions and treatment-fidelity checks.
\texttt{make check} runs tests and generates the metrics report without
asserting that all three structural targets have been met.
The runner enforces the time budget, protected tests and retained green
code, rather than accepting an AI statement as an independent quality verdict.
Supplement Section~\ref{app:activeprompts} gives the checked-in B/C examples, parameter substitution and saved-prompt limitations.

For trajectory $r$, $F_t$ is the accepted state after feature step $t$ and
$P_t$ the state after its assigned post-step; these source states coincide
in A and D. Let $\mathcal{R}_{r,t}$ contain eligible, unchanged contracts
that passed at least one earlier end-of-cycle checkpoint $P_u$, $u<t$.
This \emph{risk set} excludes superseded contracts and includes only behaviour that could now be lost because it worked before and is still required. At $F_t$ and $P_t$, let
$\mathcal{O}^{p}_{r,t}\subseteq\mathcal{R}_{r,t}$ contain contracts with
observed binary results $S^p_{r,t}(q)$, $p\in\{F,P\}$. Observed loss is
\begin{equation}
L^p_{r,t}=\sum_{q\in\mathcal{O}^{p}_{r,t}}
\mathbf{1}\{S^p_{r,t}(q)=0\},\qquad
d^p_{r,t}=\frac{L^p_{r,t}}{|\mathcal{O}^{p}_{r,t}|}.
\label{eq:decayloss}
\end{equation}
Here $L$ counts observed failures among previously acquired contracts, and
$d$ divides that count by the observed risk-set size. The fraction is undefined when its denominator is empty, and missing earlier checkpoints can leave acquisition unknown. The Supplement specifies richer reporting of those histories; missing observations cannot count as acquisition failures.

With $M^p_{r,t}$ missing evaluations, full-risk loss lies between
$L^p_{r,t}$ and $L^p_{r,t}+M^p_{r,t}$; never-acquired contracts are
acquisition failures rather than losses.


The final export marks all 6,300 F/P rows as having complete observation and risk histories, and the analyser withholds loss when either history is
incomplete; the Supplement distinguishes this implemented rule from the
richer reporting requirements proposed for future incomplete histories.

\subsection{Supplementary post-run workflow assessment}\label{sec:postrunjudging}

Designed after development, a fixed panel replayed API workflows against archived S1 checkpoints; it left the treatment budgets and original coverage, retained-contract-loss
and CR1 endpoints unchanged. Development agents were neither rerun nor allowed to repair their repositories, and Supplement Section~\ref{app:postrunjudging} records the instrument and
assessment lineage.

The panel exercised ten feature workflows, a delivery/reopening journey and a CR1 workflow, looking in each scenario for an
earlier successful execution at an eligible end-of-cycle checkpoint in the
same development run. We call that passing execution a \emph{witness} and count a failing final scenario as witnessed loss only if it passed earlier. A scenario that never passed counted as an acquisition failure, while post-CR1 loss could include a
failure already present at $P_{10}$, so it did not isolate damage caused
by CR1. The scenarios complemented hidden contracts through longer workflows with a different, narrower set of checks.

A tool-disabled judge model, \texttt{gpt-6-luna}, rated each
evaluable endpoint twice in fresh sessions. It received anonymised
execution evidence and returned four ordinal 0--4 ratings:
functional completeness, workflow coherence, error recovery and API
usability. Ratings required final-observation citations and null values for insufficient evidence, addressing the exercised API tasks rather than constituting a human interface usability study. The packets also exposed
earlier passing witnesses and retention labels, allowing historical
anchoring despite anonymisation: a judge could see that a scenario had
worked earlier before rating its final state. The judge shares a provider/model family
with the development model \texttt{gpt-6.1-sol}.

The assessment supplies supplementary exploratory evidence, distinct from development-time review as an intervention. A
\emph{complete-frame contrast} requires observations for all allocated
trajectories in both compared arms for every development model; each model
contributes equally. Repeated ratings, scenarios
and checkpoints remained nested within trajectories. Results, missingness
and the human spot-check are reported in Section~\ref{sec:resultsjudging};
the Supplement accounts for judging costs.

\subsection{Replication and uncertainty}\label{sec:protocollimits}

We chose the ten-percentage-point minimum useful gain before collection, with conditional sample-size calculations and alternative allocations preserved in the Supplement; the executed selection was 21 per model and arm.

Coverage scores $Y$ use the 0--100 scale, with $\overline{Y}_{ma}$ denoting mean final coverage for model $m$ and arm $a$.
The primary estimand, the quantity the study aims to estimate, is the
difference in mean coverage averaged equally over the $M=3$ selected models,
each contributing one-third of the result regardless of its coverage level.
We estimate this difference from the observed trajectories as
\begin{equation}
\widehat{\Delta}_{BD}=\frac{1}{M}
\sum_{m=1}^{M}(\overline{Y}_{mB}-\overline{Y}_{mD}).
\label{eq:primarycontrast}
\end{equation}
The reported pooled within-cell SD was 3.1278 percentage points with
300 degrees of freedom (Supplement Section~\ref{app:resultsdetail}); this
describes the completed data without supplying a retrospective power claim.

The reported independent-cell analysis uses a bootstrap that samples whole trajectories with replacement within each model/arm cell, with the 2.5th and 97.5th percentiles of 10,000 resulting estimates giving each
95\% interval. Resampling treats trajectories within cells as independent and gives each
selected model equal weight; it does not jointly resample scheduling blocks.
Model-specific and other contrasts are secondary, exploratory and
unadjusted for multiple comparisons. For fully observed CR1 cells we report
success counts and binomial uncertainty; unknown outcomes receive
identification bounds instead. The coverage planning calculation supplies no power guarantee for CR1, and Section~\ref{sec:threats} consolidates the
dependence, selection and generalisation limits.

\subsection{Resource and information boundaries}\label{sec:prerun}

Beyond the session ceilings in Table~\ref{tab:protocolsummary}, the controller enforced aggregate admission against spent credits and
reserved liabilities; unknown charges never became free headroom.
The Supplement records the aggregate envelope, retry rules, historical
launch criteria and limits of the information-access evidence.

Candidate tools received only current and earlier visible specifications and examples, while hidden tests, scores, reference code and the future change request stayed external; discovery of skills and other tools was disabled. The trusted host's authenticated model connection did not expose
the evaluator through the candidate command tool.

Unsuccessful feature increments are reset; later features and scheduled
B/C/E post-steps continue on accepted green state. Hidden denominators
still include undelivered features. One infrastructure-only retry shares
the original budget; poor performance never justifies replay.
Contradictory valid oracle results halt collection.
Assisted and incomplete trajectories and all their costs are recorded,
without replacements or success-conditioned primary analyses.
Consequently, a zero loss count does not exclude broken edits, because rejected or transient failures belong to an attempt outcome; the retention endpoint measures the state allowed to survive.
Immutable accepted tests and rollback are part of every tested policy.

contracts had to pass while preserving the feature contracts that passed

\subsection{Structural quality, code volume and resource consumption}\label{sec:resultsstructural}

Consolidation's clearest advantage was structural cleanup
(Table~\ref{tab:resultsstructural}). Cyclomatic complexity counts independent
control-flow paths through a function; the threshold applies to each function.
No functions exceeded cyclomatic
complexity 10 at any of the 63 B endpoints. Relative to A, lint density
fell by about 92\% on Sonnet and reached zero on GPT\@. The targets were
not uniformly achieved: Sonnet B still averaged 2.26 lint warnings per
1,000 source lines despite the zero-warning target. These metrics
measure the intervention's structural targets. Broader architecture and
correctness require distinct assessments.

Gemini's baseline metrics were already low, but some functions exceeded
complexity 10 and lint was nonzero. Its baseline therefore did not satisfy
every B target. The observed comparison supports a narrower conclusion:
structural measures can improve while a semantic permission defect persists.

\subsection{Post-collection workflow replay and anonymised AI judging}\label{sec:resultsjudging}

The workflow replay found no witnessed endpoint losses among 626 evaluable packets, with failures mainly concerning ranking and the delivery journey
where ranking had never been completed.
The 630 allocated packets covered both $P_{10}$ and CR1, with four
unavailable because judging preceded completion of the interrupted runs
(Section~\ref{sec:threats}). Replay used 3,457 recorded checkpoints and the twelve-scenario
panel described in Section~\ref{sec:postrunjudging}.

Zero workflow losses and the hidden-contract regression count answer
different questions, because the workflow panel exercised selected journeys whereas the hidden suite checked additional invariants. In particular, the workflow's
\texttt{privacy:3} scenario checked refusal of \texttt{view.open\_case},
but did not exercise \texttt{view.define\_region} or
\texttt{view.approve\_handoff}. Those new methods could still write through a view that passed the first check, a coverage gap that explains why near-perfect workflow ratings can coexist with
poor hidden-suite CR1 success.

The \texttt{gpt-6-luna} judge completed two fresh ratings per
evaluable packet: 1,252 calls costing 418.64 settled AI credits in
the completed assessment. Its complete-frame differences in functional completeness
and API usability favoured B by about 0.06 on the 0--4 scale at $P_{10}$
(Supplement Table~\ref{tab:resultsjudgecontrasts}), largely reflecting GPT's greater
ranking completion. These differences are small descriptive summaries on an ordinal scale, for which the companion supplies exploratory bootstrap intervals. At CR1,
all four intervals for these two dimensions include zero; no practical-importance threshold was established, and the intervals are
not adjusted for multiplicity: their stated coverage applies to each
comparison individually. The Supplement retains the detailed
contrasts, all cell means, judge-version accounting, incomplete-frame bounds
and scenario abstentions.

\FloatBarrier
Our human-calibration spot-check used one human rater to score 90 rows, of which 79 were scorable and represented sixteen distinct
requirement/evidence contexts. Guidance was clarified after initial AI
scoring, the review remained in progress and AI-assisted triage focused
inspection on failures or mismatches. There were no numeric disagreements of two or more points, although one disagreement concerned a
\texttt{ValidationError} rejection at the last step: did that demonstrate
error recovery when no subsequent action was observed?
The high agreement and strong ceiling
concentration do not provide independent inter-rater reliability; Supplement Table~\ref{tab:resultscalibration} gives the raw and context-weighted
