## Defect found: GET /api/assistants 503 without cause

The first staff probe got `503 "Assistant service unavailable"` on `/api/assistants` and `503 "service busy saving other work"` on `/api/briefing`. Six retries over a minute returned 200 for `/api/assistants` every time and 200 for `/api/briefing` five times and one 503 ([06-retry.json](./issue-350-live-r9-2026-11-23/raw/06-retry.json)). The container log shows `/api/briefing` logging `cause=sql-write-lock-busy` with `Retry-After: 5`, whereas `/api/assistants` logged only `status=503` with no cause. Several workers share this demo, so a held SQL write lock is the likely trigger (issues #2237 and #2245).

Cause in code: the GET branch for `/api/assistants*` in `src/api/src/zava_forward/api/server.py` caught every `Exception` and answered a fixed 503 without a log line and without `Retry-After`, so the shared lock-busy handling for safe methods never ran. Fix: re-raise when `is_write_lock_busy(e)` so the common path answers 503 with `Retry-After: 5` and logs the cause; any other failure still answers the same assistant message and now logs the exception class and path only. The POST branch is unchanged because a failed POST may follow a committed step. Test: `test_assistants_registry_busy_lock_503_retry_after_and_other_failures_logged` in `src/api/tests/test_error_logging.py` fails without the change and passes with it; `test_error_logging` passes (14 tests), `mypy` is clean and `ruff check` and `ruff format --check` pass in `src/api`.

Not fixed: `/api/assistants/forecast` returned 503 on all six tries after 13 to 18 s with `Retry-After: 30`, the designed bounded `ForecastTimeout` (10 s budget in `assistants.py`). Issue #2304 owns the statement-count work; whether the deployed image holds it is not provable here (image `commit=unknown`, registry not reachable from this host).
