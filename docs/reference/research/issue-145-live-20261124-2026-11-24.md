## Defect fixed: restore resurrected suspended and revoked releases (R3)

`assistant_release.change` writes release status only to SQL, so a point-in-time restore to before a suspension returned the release to `active` and dispatch admission would resume. Erasure already had a register outside the database; release changes did not.

Fix in `src/core/src/zava_forward/core/recovery.py`: `record_release_change` writes a write-once register entry (release id, status, time; no free text) in the document backend under `_release_changes` before the SQL change, and `reapply_release_changes` moves restored releases back to the strongest recorded status (revoked outranks suspended). `assistants.change_release` and the serving-attestation suspension call the recorder first, so an unwritable register blocks the change. Tests in `src/core/tests/test_recovery.py` use a SQLite release table: restore to active then reapply gives suspended and revoked, a second run changes nothing, invalid or unknown changes write nothing, and a failing Blob write blocks. The release, assistants, suspension and call-site suites still pass (`src/api`, 496 tests, SQL Server cases skipped without a server). This is SQLite emulation, lower-tier evidence; it was not run against a live Azure SQL restore.
