## Defect: SQL list paths disagree with the in-memory paths on ownership

Observed live: the signed-in user's own queue is 16 cases in `/api/cases?view=mine` and `/api/me` (`counts.mine`), but 133 in `/api/cases.csv`, in `flag=nodecision` and in the stats team row. The CSV rows are all owned by that user, with 133 distinct references. Paging all 443 open cases through the SQL path (whose payload comes from the case body) gives owner counts 133, 124, 53, 48, 31, 21, 15, 15 and 3, while filtering by owner through the SQL path gives a different count for 8 of the 9 owners. Stage, area and wave agree everywhere.

Cause: `SqlStore.page_cases` and `counts` filter on the derived `cases.owner_code` column, whereas the CSV and `flag=nodecision` paths use the in-memory store, which reads the body. `SqlStore._migrate` rebuilt derived columns only when the ranking policy, schema or support encoding changed, so a body written without its columns was never repaired. How the deployed rows drifted is not established: Azure SQL is not reachable from this workstation and the only repository writer that edits bodies directly, `infra/scripts/initialize-workbench-staff.py`, changes the owner label, not the code.

Local fix (`src/core`): `SqlStore._repair_identity_columns` compares stage, area, wave, owner code, closed and contractor with the body on open and rebuilds the derived row of any disagreeing case. The test `test_identity_columns_that_disagree_with_the_case_body_are_repaired` failed before the change (own queue 0 against 12) and passes after it. The fix is not deployed: building and rolling out an image is a production change outside the demo authorisation, so the live disagreement stays until the owner releases it.
