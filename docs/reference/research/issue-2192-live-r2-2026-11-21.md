## Live observations

* ca-resident-demo (revision 0000019 at the time) serves the checkbox and carries the `ZF_DEMO_SENSOR_CONSENT*` settings, pointing at the same SQL server and database (`retrofit`) as the employee app.
* Resident page: native `input type=checkbox` wrapped in its `label`, `aria-describedby` linking the status and the "does not change your repairs" text, starting unticked. Keyboard Space toggled it, the status text changed to "Staff can see your readings." and back to "Staff cannot see your readings. New readings are not stored for your home.", focus stayed on the checkbox, and the choice survived a reload. The test resident was returned to its initial (declined) state.
* Employee API `GET /api/cases/{id}/sensors` on ca-cutover-test-demo-api for all 50 cases, before, after grant and after restore: no case changed state (45 `consent-withheld`, 5 `ok`).

## Defect found

The resident checkbox writes consent for the showcase `sensor_home_id` (`SYN-NE-001458-FLAT1`, seeded under issue 1072), while the employee view reads home id equal to the case id (`Assistants.sensors` calls `sensor_view.view(db, case_id, ...)`). The keys never met, so a withdrawal on the live resident page could not change the employee view.

Fix (local commit, not deployed): `sensor_consent.apply` sets the resident's sensor home and then the resident's case-id home, skipping a case that has no controls under its own id. Test `test_withdrawal_also_reaches_the_case_id_home_the_employee_view_reads` covers it.
