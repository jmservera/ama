* Revision `0000086` (created 04:54Z) served the first probe; at 06:01Z a further revision `0000088` replaced it (deployed outside this run).
* Thread creation: 16 of 16 API creates returned 200 across both probes ([05:25Z](./issue-2245-live-20261126T052140Z/probe-chat-result-0525.json), [06:02Z](./issue-2245-live-20261126T052140Z/probe-chat-result-0602.json)). No 500 has been seen since 2026-11-22.

* Widget ([05:25Z text](./issue-2245-live-20261126T052140Z/probe-widget-result-0525.json), [screenshot](./issue-2245-live-20261126T052140Z/screens/widget-held-0525.png); [06:02Z text](./issue-2245-live-20261126T052140Z/probe-widget-result-0602.json), [screenshot](./issue-2245-live-20261126T052140Z/screens/widget-held-0602.png)): "Model calls: 0", with the plain notice that the allowance is used up. The banner and the reply agree; no AI claim is made for a rules reply.
* Logs at both times: `AI_LIMIT_BREACH reason=call-budget-limit route=workflow-only`, so the ledger refused the call before the model.

## Defect found and fixed

The reply said "The daily demo allowance ... resets at 00:00 UTC", but the meter at HEAD seeds one 20-call budget per UTC hour ([chat_demo_meter.py](../../../src/core/src/zava_forward/core/chat_demo_meter.py)), so the promise is wrong for that source. The wording now reads "hourly demo allowance ... renews at the start of the next UTC hour" (`chat_panel.py`, test `test_chat_panel.py::test_budget_hold_reply_names_the_allowance_not_unavailability`). Hold semantics are unchanged.

## What the live result does and does not show

* The call budget stayed exhausted at 06:02Z, one minute after the hour boundary. With an hourly meter a fresh budget should exist then, so either the deployed image still uses the day-wide budget, or other workers using the same demo API consumed 20 calls in the new hour. The logs cannot tell these apart and the image digest cannot be mapped to a commit (ACR access denied; no deploy record in the repository). The hourly meter is therefore unproven live.
* A visible "Model calls: 1" was not reproduced in this run; it was proven on revision 0000079 in the [earlier note](./issue-2245-live-2026-11-26.md).
