## Results

* Eight fresh sign-ins, 07:14 to 07:18 UTC ([probe-result-071740.json](./issue-2257-live-r2-2026-11-23/probe-result-071740.json)): 8 of 8 loaded 443 markers, 0 showed "Map unavailable", 0 `requestfailed` events, every `/api/map` returned 200. Runs 1 to 3 took about 4.5 s; runs 4 to 8 took 15 to 19 s, which fits database lock contention, not a failure.
* Injected connection reset ([recovery-proof-result.json](./issue-2257-live-r2-2026-11-23/recovery-proof-result.json), screenshots `map-after-reset-*.png`): first `/api/map` aborted, second returned 200, 443 markers, no error message.
* API console log ([console-window.txt](./issue-2257-live-r2-2026-11-23/console-window.txt)): `map sensor summary unavailable exc=ProgrammingError` at 07:09:04 and 07:16:44 UTC. The 07:16:44 line falls inside probe runs 6 and 7, and both runs still loaded the map. Before the hardening the same condition returned a JSON 500 and the map failed (2026-11-23 note, 3 of 3 logged `/api/map` ProgrammingError lines).
* The same log shows `GET /api/briefing status=503 exc=ProgrammingError cause=sql-write-lock-busy` at 07:09:06 and 07:10:04 UTC. That cause tag identifies the database application lock as the concurrent contention source for the ProgrammingError class on this revision. The overlay log line does not carry the cause tag, so its exact driver message is still not proven to be the lock.
