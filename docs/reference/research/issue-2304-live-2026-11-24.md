## Why it still fails

* No write lock is involved: the forecast reads on its own autocommit connection under `rel.read_only()`.
* The 10 s budget started after the connection to Azure SQL was open, and a statement already in flight cannot be cut. Total time was connection time plus 10 s plus the last statement, which explains 13 to 17 s instead of 10 s.
* Every request began from nothing and the work was thrown away on a timeout, so a retry could never succeed if the full read needs more than the budget. Even trivial reads cost 5 to 6 s on this system (`/api/stats`, `/api/assistants`), so the remaining round trips are slow under shared load.
* The live statement trace was not captured: SQL has public access disabled and is not reachable from this host.

## Fix

`Assistants.forecast` in `src/core/src/zava_forward/core/assistants.py`:

* The computation runs in a background job per staff identity and period (`_forecast_job`), capped at `FORECAST_BUDGET_SECONDS` (120 s). A request waits at most `FORECAST_WAIT_SECONDS` (8 s) counted from the start of the request, so connection time is inside the bound.
* A finished job returns fresh figures. A late job leaves the request with the last good answer, marked `stale_seconds`, for up to `FORECAST_STALE_SECONDS` (900 s). With no answer to show, the request raises `ForecastTimeout`, which the API maps to the existing 503 named state; the job keeps running, so the retry is answered from its result.
* Concurrent requests join the running job, so a slow system does not accumulate load. Permission and validation errors still reach the caller; failures are never cached.

Limit: a stale answer can precede a revocation or case edit by up to 900 s, and only when a fresh answer was late. Fresh answers are never delayed by the cache, so existing tests that change state between reads still see the change. Figures are counts only.
