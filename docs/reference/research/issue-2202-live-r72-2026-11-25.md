## Defect found and fixed locally

At 17:43:57 UTC, while the receiver job was running, `GET /api/cases/ZF-2025-0331/sensors` returned 503 and the tab stayed on "Loading home sensors" ([screenshot](./issue-2202-live-r72-2026-11-25/diag-sensors-tab.png)). The same minute `GET /api/assistants/proposals` and `POST /api/chat/threads` failed with `cause=sql-write-lock-busy`. The sensor reads (`AssistantService.sensors` and `map_sensors`) used `transaction()`, which takes the application-wide exclusive write lock, though they write nothing. They now use `_read_connection()`, the lock-free read path the forecast already uses. A regression test asserts neither read touches `transaction()`; the three map-failure tests inject failure through `_read_connection`.

Local validation (focused plus FULL-tier targeted tests, no `rpi-checks.py --all`): `test_map_sensors`, `test_quality_sensors`, `test_sensor_trend_summary`, `test_iot_seed_to_quality_ui_bridge` (236 tests OK, 94 skipped for no SQL Server), `test_sensor_consistency` and `test_sensor_staleness_ui_badge` (61 OK); `mypy` in `src/api` clean; `mypy` in `src/core` shows the same 3 environment errors as before the change (missing OpenTelemetry stubs, one unused ignore); `ruff check` and `ruff format` clean. The fix is not deployed: a new image is a production change and the registry refuses this identity, so the 503 is unproven fixed live. The receiver holding the write lock for about 25 minutes per run is the wider cause and belongs to #2320.
