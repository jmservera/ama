Refs #185. Scope: the synthetic demo, desktop only, resource group `ama`. Owner decisions of 2026-11-18 apply: live Azure authorised (cap USD 700, no drills, no Key Vault rotation, no production change).

## Method and boundaries

* Run 2026-11-19 10:37 to 10:45 UTC with the Azure CLI under the existing managed-identity login. No credential file was read or printed.
* The demo hub `iot-cutover-test-rzsrg` (B1) has public network access disabled and local auth disabled. From this VM its data plane answers 401002 (`az iot hub device-identity list --auth-type login`). Reaching it would need a posture change or a new role assignment on its private path, which is a production change and was not made. The roles at its scope show `IoT Hub Registry Contributor` for the operator identity only; the API identity holds the Event Hubs receiver role, not registry write.
* Instead a throwaway Free-tier hub (`iot-thr185-30198`, F1, uksouth) was created in `ama`, the operator identity was given `IoT Hub Registry Contributor` on it, and the shipped adapter ran unmodified over Entra tokens. The hub was then deleted (`az iot hub delete`); `az iot hub list -g ama` now shows only `iot-cutover-test-rzsrg`, and zero role assignments reference the throwaway scope.
* Evidence is in `.copilot-tracking/evidence/2026-11-19/issue-185-live/`: `live_registry.py`, `live-run-output.json`, `post-teardown-independent-count.txt`, `log-secret-pattern-hits.txt`, `log-logger-summary.txt`.

## Observed

| Step | Result |
| --- | --- |
| Plan 3 homes to identities | Three `SYN-` identities, one per stock home, no duplicates in either direction |
| `provision()` through `AzureIotHubRegistry` with SAS enrolment | Three identities created disabled with the run marker; `list_run` returned the same three |
| Ownership tag read back | `run_of` equals the run for all three |
| `teardown()` | Receipt `verified_zero_residual` true; `list_run` empty |
| Independent reread (fresh client, all identities, not marker-filtered) | 0 identities on the hub |
| Debug log of the whole run (13,896 bytes, urllib3, msrest, msal, uamqp loggers) | 0 matches for base64 key shape, `SharedAccess`, JWT prefix, `sig=` or `Bearer ` values |

## Per-criterion result

| Criterion | State on #185 | Result of this run |
| --- | --- | --- |
| Approach decided with credential owner | Ticked | Not re-tested |
| One identity per home and stock home ID | Ticked | Re-observed on a live hub (above) |
| Credentials issued and stored without appearing in source or logs | Unticked | Partly proven. Issuance without key exposure: the Hub generated the keys and none reached the run log. Storage is unproven: the adapter by design never reads the generated keys, and the repository has no durable store (the shipped `SymmetricSasCredentialStore` is in-memory and the run used the test `FakeStore`). Storing needs a design change that reads hub keys into Key Vault, which is a security-sensitive FULL-tier change and Key Vault writes were outside this run; no source was changed |
| Teardown removes all simulated identities | Unticked | Proven for the registry on a live throwaway hub (zero residual by two independent reads). Not proven on the demo hub (private, unreachable) nor for durable credential revocation (no durable store exists). The box stays unticked until the demo hub run or an owner acceptance of the throwaway-hub evidence |

## Follow-ups
