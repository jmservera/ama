## New finding: a server 500 on fresh sessions

Eight fresh sign-ins ([probe-result-014731.json](./issue-2257-live-2026-11-23/probe-result-014731.json), 01:44 to 01:47 UTC): 7 loaded 443 markers; run 5 showed "Map unavailable" after `GET /api/map` returned a JSON 500. The API console log records `exc=ProgrammingError` for `/api/map` at 00:47:00, 00:54:52 and 01:46:19 UTC. The server logs only the exception class by design, so the driver message is unknown. App Insights and Log Analytics tables hold no matching exception. Forty sequential and six parallel `/api/map` reads in one warm session all returned 200 ([load-probe-result.json](./issue-2257-live-2026-11-23/load-probe-result.json)), so the failure needs fresh-session overlap and is not reproducible on demand.

The client does not retry a JSON 500; `test_workspace_scripts` pins that, so this task leaves it alone.

## Code change

`AssistantService.map_sensors` ran the optional sensor overlay in a SERIALIZABLE transaction whose own failure escaped and failed the whole map. It now returns the existing `unavailable` state per home and logs the exception class only. Test: `test_a_failing_sensor_transaction_keeps_the_map_available`. Whether the live ProgrammingError came from this path is not proven; the change is hardening, not a verified root-cause fix, and it is not deployed.
