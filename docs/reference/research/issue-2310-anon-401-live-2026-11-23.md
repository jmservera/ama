Scope: synthetic demo, desktop only, head `5c2532b632`, deployed revision `ca-cutover-test-demo-api--0000055`. Refs #2310 and #350. Owner decision 2026-11-18 authorises live Azure in resource group `ama` but no production changes. The probe was read-only: anonymous `curl` requests and `az containerapp auth show`. No Azure resource was created or changed, so nothing needed deletion, and no sign-in value was read. Tier: focused (documentation and evidence only, no `src` change).

## Finding

The code defect named by the issue does not exist in the application. `do_GET` in `src/api/src/zava_forward/api/server.py` sends every `/api/` path without a user to `401 {"error": "Please sign in."}` regardless of `User-Agent` or `Accept`, and only non-API page paths redirect (302 to `/sign-in`). The tests were added by #1005 (commit `d29535aca0`): `ProxyHttpTests.test_anonymous_api_is_401_for_browser_style_requests_and_pages_still_redirect` in `src/api/tests/test_auth.py`.

The live deployment behaves differently. Anonymous requests to `/api/me` and `/api/cases` with a Chrome `User-Agent`, `Accept: application/json` and `Sec-Fetch-Mode: cors` receive `302` to `login.microsoftonline.com`, because the Container Apps authentication layer in front of the app is configured with `unauthenticatedClientAction: RedirectToLoginPage` (browser mode; `infra/modules/containerapps.bicep` line 302 selects `Return401` only when `entraBearerOnly` is set). The request never reaches application code. Excluding `/api/*` at the edge would change the production authentication boundary, which the owner decision forbids for this demo, so no change was made.

## Follow-up

Owner decision needed: whether the demo should return 401 to anonymous fetches at the edge (for example by setting `entraBearerOnly` for an API-only host, or a platform-level path rule) or accept the 302 that the browser follows to sign-in. The workbench client already handles a 401 from the application; with the edge redirect an expired session instead produces a cross-origin redirect on `fetch`. This is an infrastructure change and was not made here.

## Second run addendum (2026-11-23)

A regression test, `ProxyHttpTests.test_anonymous_api_never_redirects_for_any_method_accept_or_unknown_path` in `src/api/tests/test_auth.py`, now pins 401 without a Location header for GET, HEAD and POST on `/api/me`, `/api/cases` and an unknown `/api` path, with three Accept values and a session cookie, and pins `/sign-in` 302 to the Entra login URL. `tests.test_auth` (42 tests) and the two sibling auth suites (48 tests) pass. The live edge 302 was not re-probed and stays an owner decision.

## Third run addendum (2026-11-23)

A probe of the in-process server showed anonymous PUT, PATCH, DELETE and OPTIONS on `/api/cases` answered 501, because only GET, HEAD and POST had handlers. `make_handler` now routes PUT, PATCH and DELETE through `_unsupported_method`: anonymous `/api/` requests get 401 `{"error": "Please sign in."}` with no Location header; signed-in and non-API requests keep the stdlib 501. OPTIONS is unchanged. Test `ProxyHttpTests.test_anonymous_api_put_patch_delete_return_401_not_501` fails without the change (verified by stashing server.py) and passes with it. Auth suites: 93 tests OK; ruff and mypy clean. The live edge still answers 302 for all verbs; not re-probed and not changed (owner decision).
