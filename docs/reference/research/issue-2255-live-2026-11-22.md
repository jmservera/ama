Scope: synthetic demo, desktop, API `ca-cutover-test-demo-api` (resource group `ama`). Read-only probe, no deploy, no data change. Refs #2255.

## Findings

* The live revision `ca-cutover-test-demo-api--0000050` was created 2026-11-22T13:55:15Z. PR #2241 (`43a9da2649`) merged 2026-11-22T14:48:25Z, so the live API predates it.
* Probe `docs/reference/research/issue-2255-live-2026-11-22/probe_hazard_fields.py` (result `probe-hazard-fields-result.json`, no credentials in output) read `/api/cases?flag=hazard` (22 cases) and each case detail. All 22 hazards carry `noticed`, `referred`, owner and priority, but `aware_at`, `response_due_at`, `resident_update_due_at` and `responded_at` are null on all 22. Live `clock_status|clock_basis` is `fail_closed_missing_timestamp|missing_timestamp_fail_closed` for 22 of 22.
* In `src/core/src/zava_forward/core/taskqueues.py`, `project_safety_clock_and_owner` derives the deadline only from `response_due_at` or `aware_at` plus a window. A hazard with only a `noticed` date is deliberately fail-closed; `test_queue_clock_shows_time_remaining_overdue_or_missing_awareness` asserts that. The hazard service stays the timing authority.
* Conclusion: redeploying main would not make any of the 22 cases show a running clock. The cause is the seeded demo data, not a code defect. The retrofit-flow generator records the awareness date (`h["aware"]`) but only exports it as `hazard_observed_date`/`noticed`, and the seed path (`seed_merge`) is insert-only, so existing live rows are not updated.
* Mapping `noticed` to awareness in src was rejected: it would invent a day-precision awareness time and contradict the fail-closed design and its test.

## Local validation

`test_workbench_hazard_clock_owner` and `test_hazard_api` (12 tests) pass from `src/api`. The same projection returns `running`/`overdue` when `aware_at` is present, and hazard JSON bodies persist in the SQL store, so supplying the fields in data is sufficient.

## Acceptance criteria

The issue states one expectation: some synthetic hazard records carry an awareness time and response target so the clock shows elapsed time against the target.

| Criterion | Status | Evidence |
| --- | --- | --- |
| Live data path would populate the clock after redeploy | Disproved | 22 of 22 live hazards lack `aware_at` and `response_due_at` |
| At least some synthetic hazards carry awareness and target | Unproven, needs data | Requires an owner-authorised update of the private demo data or a re-seed; not done (no estate change authorised) |
| Clock displays elapsed time against target | Unproven live | Proven only in local unit tests when the fields exist |

## Follow-up

Add `aware_at` and a `response_due_at` to a subset of generated hazards (the generator already holds the awareness time), then apply them through an owner-authorised private data path, since `seed_merge` does not update existing cases.
