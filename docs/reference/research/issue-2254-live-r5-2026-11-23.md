Refs #2254. Runs 1 to 4 proved the 23 versus 22 safety count repaired on main (a6c0910c97) and equal across tile, map and list on the live demo. This run closes the same defect class for sibling filters, which no earlier run covered.

## Finding

`SqlStore.page_cases` answers the Show only filters from stored columns (`FLAG_SQL`: `hazard`, `support`, `days`, `fstatus`). `_repair_identity_columns` rebuilt `hazard` but not `support`, `days` or `fstatus`. A case body edited without its derived columns therefore left the `support`, `long`, `funding` and `fundingprog` filters disagreeing with body-derived counts, which is the 2254 failure for another flag.

## Change

* `src/core/src/zava_forward/core/sqlstore.py`: `support`, `days` and `fstatus` join the repaired columns. `decision` is deliberately excluded: it depends on current consent context and `page_cases` already bypasses it.
* `src/core/tests/test_sqlreads.py`: `test_stale_support_long_wait_and_funding_columns_are_repaired_issue_2254`.

## Evidence

* With the change reverted the test fails (`0 != 21 : long`): [test-before-fix-reverted.txt](issue-2254-live-r5-2026-11-23/test-before-fix-reverted.txt).
* With the change, `tests.test_sqlreads` runs 19 tests, OK: [test-with-fix.txt](issue-2254-live-r5-2026-11-23/test-with-fix.txt).
* `ruff check` passes; `mypy` reports 3 errors identical before and after the change (missing OpenTelemetry stubs and one unused ignore), so none is caused by it.

## Limits

The change is not deployed, so no live proof of it exists; the live equality of tile, map and list was proven in [run 4](issue-2254-live-r4-2026-11-23.md) on revision 0000055. The original stale live row cannot be inspected because SQL public access is disabled.
