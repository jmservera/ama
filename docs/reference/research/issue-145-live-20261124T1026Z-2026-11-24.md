## Defect fixed: restore resurrected spent allowance (R3)

`assistant_allowance.used_calls` and `reserved_tokens` live only in SQL. A point-in-time restore returns them to older, lower values, so calls already spent reappear as headroom. Recording each spend outside SQL would add a blob write to every admission, so the fix is fail closed: `recovery.close_allowance_after_restore(db)` in `src/core/src/zava_forward/core/recovery.py` marks every pool exhausted. A rotated authority inherits the highest consumption (`_pool`), so rotation does not reopen it, and a second run closes none. An operator reviews and re-seeds before assistant calls resume; the manual route stays open. The runbook and core README now say so. Test `test_restore_does_not_resurrect_spent_allowance` passes with the other 23 `test_recovery` tests on SQLite. This is lower-tier emulation: not run against a live Azure SQL restore, and wiring the call into an automated post-restore sequence is not done (the step is a documented runbook action, like the other reapply functions).
