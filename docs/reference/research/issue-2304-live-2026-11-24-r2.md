## Live observation (revision 0000065)

Outputs: [baseline-r0000065.json](./issue-2304-live-2026-11-24/baseline-r0000065.json), [stale-r0000065.json](./issue-2304-live-2026-11-24/stale-r0000065.json), screenshots beside them.

* Every forecast GET answered 200 after 8.1 to 9.4 s; the `stale_seconds` field rose 12, 21, 30, 38, 47 across consecutive calls, so a last-good answer existed but no new job finished.
* One call joined a finishing job and took 3.39 s, which puts the job at roughly 60 to 80 s.
* Revision 0000064 returned the named 503 at 8 to 9 s because no last-good answer existed yet: the job that would create it needed far longer than the 8 s wait.

## Root cause: CPU, not SQL

[profile_forecast_local.py](./issue-2304-live-2026-11-24/profile_forecast_local.py) runs `_forecast_compute` on a SQLite store with 448 open cases under cProfile.

| Run | Seconds (profiled) | SQL statements |
| --- | --- | --- |
| Before | 80.2 | 20 |
| After | 1.4 | 20 |

Before the fix, 72 of 80 s went to one chain: `_task_id` and `_due` call `release_reference` per case and capability (10304 calls), which calls `runtime_binding` and `rel.assessment`, which call `ai_registry.get`, which rebuilds the whole registry each time (`tasks()`, `_entry`, `monitoring_coverage.task_declaration`, 267969 deep copies). On a 0.5 vCPU container this is the 60 to 80 s job, and it also starves other requests, which fits the 33.77 s and 135 s outliers seen earlier (the AI report is covered by #2303). Live per-statement SQL timing is not captured: SQL has public access disabled and is not reachable from this host.

## Fix

* `ForecastReads.once` (`forecast_reads.py`) computes a value once per forecast run.
* `Assistants.release_reference` uses it only when the connection is a `ForecastReads` view, so the release reference is read once per assistant instead of once per case. The view is one read-only run that never records, so the value is the same for every case; write paths are unchanged.
* Test `ForecastStatements.test_registry_builds_do_not_grow_with_open_cases` (`src/api/tests/test_assistants.py`): registry builds are equal for 0 and 40 extra cases (before the fix 2075 against 235 and the test fails).
* Start-up warm: considered and not built. The cache key is per staff identity and period and the scope depends on that person's authorisation, so a start-up job has no identity to compute for; with the fix a cold compute is seconds, inside the 8 s wait.
