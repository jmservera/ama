Refs #185. Scope is the synthetic desktop demo, authorised by the owner on 2026-11-18 (resource group `ama`, cap USD 700, no drills, no Key Vault rotation, no production changes). The owner chose symmetric device keys generated by the Hub and ruled out X.509 for the demo. Nothing here is production evidence.

## Method

The hub `iot-cutover-test-rzsrg` (SKU B1) has public network access Disabled, so the run used a throwaway Container Apps job `job-185-probe` in `cae-cutover-test-demo`, with the `id-cutover-test-api` managed identity and a temporary IoT Hub Registry Contributor role on the hub. The driver stayed outside the repository, passed to the job as an environment variable, and printed device ids and HTTP codes only. The raw output was not retained in the repository; the HTTP results below are operator-observed and the Azure cleanup was not independently re-queried.

The driver:

* Created three devices `SYN-185-A01` to `A03` through the registry REST API (2021-04-12) with `authentication.type = sas` and no keys supplied, with `If-None-Match: *`. Before creating, it found no pre-existing device with those ids.
* Read the Hub-generated primary and secondary keys from the response into memory only, computed a per-device SAS token and sent one device-to-cloud message per device.
* Sent one message with a random wrong key for contrast.
* Deleted every device with the registry API and read each id back.
* Compared its own complete output with every key (full and first 16 characters).

## What this does not prove

* Production credential ownership, rotation, durable secret storage and the X.509 path remain unproven.
* The driver is not repository code, so the criteria are proven operationally, not by a repeatable repository command. A repository adapter for SAS provisioning is separate work.
* Only three identities were created, not N homes at scale. Messages were sent over HTTPS, not MQTT, and routing to Event Hub was not re-read in this run (proven separately in the #188 note).
