Scope: synthetic demo, desktop only, local proof. No live Azure change was made and no credential was read.

## What changed

* Consent lives in the per-sensor `consent` field of `sensor_consumer_control` (index and marker beside it). The existing reader `sensor_view.consent` already turns a decline into the employee state `consent-withheld`.
* `SensorConsumer.set_home_consent` grants or withdraws consent for one home through the same atomic seam as `configure`, waits for any live dispatch, rewrites the marker and writes a row to `sensor_consent_audit` in the same transaction.
* The resident showcase gets `POST /demo/sensor-consent` (same-origin, CSRF, session-bound, resident only) and a native checkbox in the sensors card. It is off unless a separate sensor-writing SQL principal is configured with `ZF_DEMO_SENSOR_CONSENT=1`; the read-only showcase principal is not widened.

## Limits

* The live ca-resident-demo app was not updated: that needs an image build, a new SQL principal with sensor write rights and a configuration change. The checkbox is therefore proven against a local SQLite store, not the Azure SQL database.
* No person-run assistive-technology test was done (not needed for the demo, owner decision 2026-11-18).
