## Flake 1: `_region_passed`, `_classes_executed` and `check_skips` with interleaved logs

The gate parses `unittest -v` output. A test prints `name (mod.Class.test) ... ` and then `ok` on its own line. Logs from threads (HTTP server, workers) write to the same stderr between those writes.

Reproduced with [unittest-noise-repro.py](./issue-2190-live-20261121-evidence/unittest-noise-repro.py): a thread logging one line per loop while 300 trivial tests run under `python3 -m unittest -v`, then `_classes_executed` over the captured output. Result: `False` on 3 of 3 runs although every test printed `ok` and the run ended `OK`.

Two mechanisms, both in the parser and not in the tests:

* Log lines written after the `ok` line and before the next header make `region[-1]` a log line, so `_region_passed` demands `ok` on the last line and fails. This was the cause in every real run (the noise printed 40 or more lines per test region).
* A log line that itself contains ` ... ` is taken as a new test header (`(.+?) \.\.\. `), which splits the region of the real test and leaves its `ok` in a different region. Probed by hand: `_classes_executed` returned `False` for `waiting ... retry` inside a passing test.

Residual, not changed: `ok` followed by log text on the same line, and a log line ending in `FAIL` or `ERROR`, stay rejected. They cannot be told apart from a real result, so rejecting is the safe side.

## Flake 2: `late_success` assertion at `employee_chat_browser_check.py:130`

Reproduced: 1 failure in 15 runs of `python3 -m checks.employee_chat_browser_check` with 14 busy-loop processes on 8 cores ([runs](./issue-2190-live-20261121-evidence/chat-check-runs-before.txt), [failure](./issue-2190-live-20261121-evidence/chat-check-failure-run11.txt)). Idle runs pass in about 10 s.

Explanation from the failure payload: `('ask', 'route', before, after)` differ only in `workspace`. `before` held the short status `Resident Liaison Officer. My assigned cases.`; `after` held the long list status written at `app.js:984` when the route's case list fetch resolved. The route transition navigates, and the case list read ends after the snapshot is taken. Under load the read ends later than the snapshot, so the two snapshots differ for a reason unrelated to the late success being tested.

## Flake 3: `TimeoutError` in `test_rai_release_readiness_api_218`

Reproduced: with 24 busy-loop processes, 9 of 12 runs failed with `urllib` `TimeoutError: timed out` ([runs](./issue-2190-live-20261121-evidence/api218-under-load-before.txt)). Unloaded the module takes 14 to 19 s for 4 tests.

Explanation: a per-request timing wrapper shows `GET /api/ai/report` costs 2.4 to 2.8 s on an otherwise idle process (every other call is 0.02 to 0.07 s). The test gives each `urlopen` a flat 10 s timeout, which is a socket-read budget. Under CPU contention a 2.5 s request exceeds 10 s.

## Fix and post-fix evidence

* Flake 1: `_region_passed` accepts `ok` on any region line while every failing pattern still scans every line; a shared header matcher requires `name (dotted.id) ... ` so log text with ` ... ` cannot start a region; the exact-test and required-test parsers now merge docstring headers. The same real noisy run now returns `True`. Two new tests in `tools/test_rpi_checks.py`: the accepting one fails before the change (3 subtest errors) and passes after, the rejecting one keeps FAIL, ERROR, skipped, expected failure, missing `ok` and a log line ending `FAIL` rejected. 120 gate tests pass.
* Flake 2: `late_success` waits for network idle before taking its `before` snapshot; the comparison is unchanged. Under the same 14-process load: 1 of 15 failed before, 0 of 30 failed after ([after](./issue-2190-live-20261121-evidence/chat-check-runs-after-fix.txt)). Idle runs still pass.
* Flake 3: both `urlopen` calls use `REQUEST_TIMEOUT_S = 120`. Under 24 busy loops: 3 of 12 passed before, 12 of 12 passed after ([after](./issue-2190-live-20261121-evidence/api218-under-load-after.txt)). A new test pins the budget and that `_raw_request` passes it.

Residual risk: an `ok` followed by log text on the same line, and log text ending `FAIL` or `ERROR`, are still rejected; a run that hits those shapes fails closed.
