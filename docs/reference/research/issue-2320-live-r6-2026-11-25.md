Scope: synthetic demo, desktop 1440x900 Chromium via Playwright, resource group `ama`, app `ca-cutover-test-demo-api`. Azure use was read-only. Sign-in values were read at run time and never printed. Refs #2320. Follows the [revision 0000069 re-check](./issue-2320-live-r5-2026-11-25.md).

## Cause of the 5 to 7.6 s tail

A briefing GET answers from a cache keyed by the store version. Any write by another client changes the version, so the next GET misses, runs `run_text_task` and then `add_record`, which takes the Python `store.lock` and opens a SQL transaction. `mssqlstore.BEGIN` waits up to 15000 ms on `sp_getapplock`. While a concurrent forecast writer holds that lock, the briefing waits (5 to 7.6 s in the 70-request run) and holds `store.lock` for the whole wait. The #2377 fallback turned the 15 s timeout into an unrecorded answer rather than a 503, but did not shorten the wait.

## Fix

`SqlStore.write_wait(ms)` (no-op on SQLite) and `_Conn.write_wait(ms)` set a thread-local cap on the lock timeout for `BEGIN`. `Store.briefing` runs its recording step inside `write_wait(2000)`; a busy lock now fails within 2 s into the existing unrecorded fallback. Other threads and other writers keep the 15 s wait. Tests: `test_write_wait_caps_this_threads_lock_timeout_then_restores_it` (core) and `test_briefing_caps_its_write_lock_wait_and_a_cached_read_takes_no_lock` (api).
