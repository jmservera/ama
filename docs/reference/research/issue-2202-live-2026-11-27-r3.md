## Finding: chat ask 500 under write-lock contention

One of eight chat POSTs (the combined "tie" question) returned 500 and the widget retry (attempt 2) succeeded. The API log shows `POST /api/chat/threads/<id>/ask status=500 exc=ProgrammingError cause=sql-write-lock-busy` at 09:11:00, three seconds after a `GET /api/assistants/rai-metrics` 503 with the same cause; the receiver job was holding the SQL write lock. Revision 0000131 was created 02:58 UTC, before the answer-save retry of #2448 (merged 05:21 UTC), so the deployed image has no retry on the answer save either. The log cannot say whether the question save or the answer save timed out.

In source the question save in `chat_panel.py` had no retry at all, though it is the same lock-first single transaction. The fix adds one helper, `_retry_lock_busy`, used by both saves (two retries, only for the lock-busy error), and a regression test that fails without the change. It is not deployed: the goal authorises no Azure change, and the demo needs a rebuild of the API image from main to carry both retries.
