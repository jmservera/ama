Refs #2191, #184, #165. Synthetic desktop demo in resource group `ama`; owner decisions of 2026-11-18 apply (cap USD 700, no drills, no Key Vault rotation, no production change). This note supersedes the open item of the [live coverage note](./issue-2191-live-coverage-2026-11-21.md). Sign-in files were read at run time and no credential, key or token was printed.

## Correction to the earlier finding

The earlier note said 445 per-device secrets could not be held by a job. That was untested. Throwaway jobs `job-2191-secrets-120` and `job-2191-secrets-450` were created with 120 and 450 secrets and read back as 120 and 450; both were deleted. No bundled-certificate code change is needed.

## What was done

* A throwaway read-only job listed the store: 443 homes. `tools/demo_consent_mix.py select` chose 222 (50.1%), evenly spread.
* 222 self-signed EC certificates were generated in a 0700 directory. A throwaway job as `id-cutover-test-api`, with a temporary Registry Contributor role, registered the 222 thumbprints on the hub (`registered 222 failed 0`, final registry count 222) and deleted 9 stale device identities of the old 20 home cohort. Both temporary role assignments (that identity and the deploying login) were removed; the readback shows 0.
* The consent mix was applied through `SensorConsumer.configure` in a throwaway job.
* `job-live-simulator` was redeployed from `infra/live-simulator-job.bicep` with the same image digest and 445 secrets (222 certificate pairs and `control.json`), with the new `failureRate` parameter at 0.1. `job-live-receiver` was redeployed with a `control.json` that adds the 9 retired homes, so retained backlog from the removed devices is mapped (and rejected for consent) instead of refused by an image that may predate the receiver fix of #2210.
* Key material and parameter files were shredded; no throwaway job remains (job list: the three demo jobs plus the two live jobs).

## Defect found and fixed

`SensorConsumer.configure` refused more than 100 controls (`INVALID_CONTROL_BATCH`), so the first consent run for 222 homes failed in the live job. `src/core/.../sensor_consumer.py` now uses `MAX_CONTROLS = 500`, the same cap as the live control file. Test `test_configure_accepts_a_cohort_of_half_of_all_homes_and_refuses_over_the_cap` passes with the change and fails without it; the 39 tests of `test_sensor_consumer` pass. The deployed image predates this fix, so the live consent run used a runtime shim that rewrites the four limit literals in memory; the image needs a rebuild through the documented registry window before the cap is fixed in what is deployed. Configuration is not re-run by the simulator or receiver, so the demo is unaffected.

## Limits

* The cohort holds exactly half rounded up. If more homes are added the share drops below 50% until the cohort is rebuilt; 449 secrets (224 homes) is the largest size tested.
* The receiver was not observed through a full window after the change in this run; the rows above show ingestion continuing. The receiver executions had alternated between Succeeded and Failed before the change (issue 2201).
* Failure rate is a random seeded skip; it simulates missing readings, not device faults.
* The certificates expire after 14 days; the control expires 2026-12-04.
