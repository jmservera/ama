Scope: synthetic demo, desktop only. Tier FULL for the coordinator (a file under `src/api` changed); `rpi-checks.py --all` was not run here. No live Azure (the issue forbids it), no secrets used, no push. Builds on [r8](issue-1830-live-r8-2026-11-23.md), where the same check passed.

## Findings

* `python3 -m unittest test_rpi_gate_timing test_rpi_preflight` in `tools/`: 62 tests OK.
* `rpi-checks.py --preflight api:test_production_config_a11y_check`: 3 tests OK, labelled development feedback, not a receipt. `api:test_does_not_exist` and `'api:test_x;id'` are BLOCKED. A direct `rpi-preflight.py` run refuses by design (fail-closed, no capability policy), so the supported entry is `rpi-checks.py --preflight`.
* Direct `checks/map_fullscreen_browser_check.py` (axe-core 4.10.3, sha256 prefix `880970c081707360`, matches the pin) failed 5 of 5 at head with `expanded dialog shows the same home summary` or `reopened dialog selects the same home` at 320 or 390 px width, host load average about 12.
* Cause, observed with a throwaway diagnostic: the home card renders `Loading sensor readings…` before the readings return, and the check read `card.inner_text()` while that state was showing, so the first and later reads differed. The check, not the app, raced.
* Fix in `src/api/checks/map_fullscreen_browser_check.py`: wait for the loading text to clear before each of the three reads. Reruns: pass (436 checks) at load 17, then pass, fail, pass, pass at load 21 to 32. The one failure was `filter label and focus fit at 390x568`, an earlier check that this change does not touch; its cause is not established.
* `ruff check`, `ruff format --isolated --line-length 100 --check` and `python3 -m mypy` in `src/api`: clean. The scenario manifest does not reference this script, so no recipe hash changed.
