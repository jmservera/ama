title: Issue 2244 law store start-up takes the SQL write lock on every boot (run 4)

Scope: synthetic demo, desktop only. Refs #2244. Earlier runs covered the SQL store retry and read-only check, the law store retry and the StartUp probe window.

## Finding

`lawstore.MssqlDb.__init__` called `BEGIN IMMEDIATE` (the `zavaforward_write` applock) on every start, before its `IF OBJECT_ID ... IS NULL` DDL, whether or not the tables and append-only guards existed. Acceptance criterion C2 (skip the write lock when the schema is current) was therefore unmet for the law store, so a long writer still delayed every API start by up to the 211 s retry budget.

## Change

`MssqlDb._schema_current()` reads `sys.tables`, `ledger_type_desc` (ledger databases) and `sys.triggers` (otherwise). When all five tables and their guards exist the lock is skipped. Any gap, including a wrong ledger kind, takes the existing locked path, which still raises its `SystemExit` message.

## Evidence

* `src/core/tests/test_mssql_startup_lock.py` `LawDbReadOnlyStartupTests`: current trigger and ledger schemas take no lock; missing table, missing trigger and wrong ledger kind do. 20 tests OK; 54 law store tests (`test_regulatory_output_guard`, `test_rulecards`, `test_source_monitor`) OK; ruff clean; mypy shows no lawstore finding (pre-existing errors elsewhere).
* No live Azure action: nothing created, nothing to delete. Live proof needs a deploy, which is owner-gated.
