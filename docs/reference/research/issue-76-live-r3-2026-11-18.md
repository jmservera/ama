## Why not seed a safeguarding item

The earlier passes ([first](./issue-76-live-task-queue-evidence-2026-11-18.md), [second](./issue-76-live-r2-2026-11-18.md)) left safeguarding unproven. Safeguarding items sit in the case record in the demo SQL store; the API exposes no endpoint that writes one (`safeguarding_items` is read by `taskqueues.safeguarding_clocks`, `projection.py` and `store.py`). Proving the criterion live would therefore mean writing demo data, or deploying a throwaway app with a seeded dataset. Neither was done: the first is a change to the shared demo record, and the second needs registry, identity and SQL wiring that the owner decisions do not cover for one display line.
