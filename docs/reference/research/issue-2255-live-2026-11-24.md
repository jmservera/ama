Scope: synthetic desktop demo, issue #2255. The hazard service (`taskqueues.hazard_clock`) already prints a running clock when a hazard has `aware_at` and `response_due_at`; the 22 live cases lacked both. New tool `src/core/src/zava_forward/core/demo_hazard_clock_seed.py` (inspect, apply, revert) writes them for open hazards that have neither, marked `demo_clock_seed` for exact revert. Offsets of 6, 30, 80 and 200 hours cycle against a 168-hour operational reference window (a synthetic demo assumption, not a regulatory deadline).

| Criterion | Status | Evidence |
| --- | --- | --- |
| Some synthetic hazards carry awareness time and response target | Proven in code and tests | `test_apply_shows_running_clock_and_is_idempotent`, 3 tests pass |
| Clock shows elapsed time against target | Proven in code and tests | Test asserts "6 hours elapsed" and "service response due" text |
| Hazard service stays timing authority | Proven | No change to taskqueues or workflows; tool writes only fields the service reads |
| Seed is reversible and skips recorded timing | Proven | `test_revert_restores_exactly`, existing `aware_at` untouched |
| Live queue (ca-cutover-test-demo-api) shows the clock | Unproven | Needs `apply` on the private-network SQL store, a data write the 2026-11-18 owner decisions do not authorise; no live probe was made. Owner step: run `python -m zava_forward.core.demo_hazard_clock_seed inspect` then `apply` in the demo API replica |
