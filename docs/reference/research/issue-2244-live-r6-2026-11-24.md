## Defect found and fixed

On a populated store the base still queued for the global write lock three more times at every start: `_seed`, `_migrate_recommendations` and `_ensure_queue_membership` each issued `BEGIN IMMEDIATE` although they would change nothing. Any long writer therefore still stretched start-up past the StartUp window (run 5 recorded about 4 minutes and a liveness restart on 2026-11-23). Changes in `src/core`:

* `_seed` returns early when `cases` has rows.
* `_ensure_queue_membership` returns early when the `queue_context` meta equals the fingerprint.
* `_recommendations_current` (new, read-only) lets `_migrate_recommendations` return early when the ordinal column, both indexes and both meta markers are present; `_rec_order_indexes_present` exists in both stores.
* Test `PopulatedStartupLockCountTests` counts `BEGIN IMMEDIATE` on a reopen: fewer than the first open and at most 2.

Validation: `test_mssql_startup_lock` and `test_sqlstore` run, 42 tests OK; `ruff check` clean; `mypy` in `src/core` reports 3 errors (missing OpenTelemetry stubs and one unused ignore) that are identical with and without this change. The full gate is not run here; the coordinator runs it.
